# Domain — ticket lifecycle and the unattended pipeline

What the system is, what each status means, and which of those meanings are load-bearing. Read before changing anything that moves a ticket between statuses, assigns one, or draws the pipeline.

Support ticket system that ingests email, classifies tickets with Claude, and drafts/sends replies grounded in a knowledge base. Two roles: **admin** (manages agents) and **agent** (works tickets).

**Ticket lifecycle** (`TICKET_STATUS` in `@ticket/shared`, and the Postgres enum's declaration order, which is what "sort by status" means):

```
New ──► Processing ──► Resolved         the knowledge base answered it
 │           └───────► Open             it declined; a human's turn
 └──────────────────► Open ──► Resolved ──► Closed
```

- **`New`** is where every ticket arrives and where it stays until something moves it. Only the auto-reply pipeline does that automatically, so a deployment with no `OPENAI_API_KEY` leaves everything in `New` — which is the honest reading of "nobody has triaged this". Hence `BACKLOG_STATUS` (`New` + `Open`): every dashboard number meaning "not dealt with" counts both, and scoping one to `Open` alone would report a clean desk in front of an untouched inbox.
- **`Processing`** means a worker is composing a reply *right now*. `GET /api/tickets` refuses to return it — that is the concurrency control, not cosmetics: without it an agent opens a ticket the model is mid-reply on and the customer gets two answers. It lasts seconds. `CLIENT_TICKET_STATUS` keeps it out of the list filter and `AGENT_SETTABLE_STATUS` keeps it out of `PATCH /:id/status`, because a person who could set it could hide any ticket from everyone with nothing scheduled to release it.
- Nothing promotes `New → Open` implicitly. Replying still has no status side-effect, as it never had.
- **Every ticket leaving the pipeline gets an owner.** Resolved by the machine ⇒ assigned to the assistant's own account; handed back ⇒ assigned to whoever the handoff setting names. Both are the same column an agent uses, and that is the point: before it, the automated half of the desk was the half with an empty Assignee cell, which is exactly what an untouched ticket looks like. The one exception is load-bearing — a release to `New` (a retry is coming, or the recovery sweep freed a stuck claim) assigns **nobody**, because the claim in `auto-reply-ticket.ts` only takes tickets whose `assignedToId` is null and naming an owner there would put the ticket beyond the retry already scheduled for it.

**The whole unattended path is drawn at `/pipeline`** (admin-only, `apps/web/src/pages/PipelinePage.tsx` + `PipelineRail.tsx`, served by `apps/api/src/routes/pipeline.ts`). Six stops — received, classified, eligible, drafted, checked, resolved — with every exit hanging off the side, live counts on each, and a panel that posts an email through the real ingestion path so one ticket can be watched descending it. It is reconstructed entirely from columns that already existed (`classifiedAt`, `category`, `status`, `autoResolvedAt`, `autoReplyDecline`, and the messages' `direction`/`automated`/`citedArticleIds`) — **no migration, no simulated-ticket flag, nothing written for the page's benefit.** Two invariants keep the picture honest and both are enforced by types: `DECLINE_STAGE` in `@ticket/shared` is a `Record<AutoReplyDecline, PipelineStage>`, so a tenth decline reason is a compile error until somebody says where it belongs on the diagram; and `pipelineStageCounts` derives the six stop numbers in one place, because two implementations of "how many were still on the rail" would disagree on exactly the day it mattered.

The page has one **known blind spot, and it says so on screen rather than inferring around it**: a customer replying to a machine-resolved ticket clears `autoResolvedAt` (see `ingest.ts`), so a reopened ticket cannot be shown as "auto-resolved, then reopened". It is reported as `notOffered` — nothing further is scheduled, which is true — rather than as `pending`, which would show a finished ticket as being worked on forever.

**Who ends up with it** is the one thing on that page an admin can change, and it is a card between the switches and the rail (`PipelineHandoff.tsx`, `routes/automation.ts`, `src/automation.ts`). Two rows, deliberately asymmetric. Filing a *resolved* ticket under the assistant is fixed in code — it is a record of what happened, not a routing rule, and pointing it at a colleague would file a machine's work under a person's name. Deciding who inherits the ones it could **not** finish is a staffing question with no right answer, so it is a setting: `admin` (the longest-serving one, resolved when the ticket is handed back rather than stored, so it survives a change of staff), a named person, or nobody. `resolveHandoffUser` in `src/automation.ts` is the only implementation of that choice, and the API sends back `resolvedTo` — the answer the *next* handed-back ticket will actually get — because "an admin" names nobody on screen and a target pointing at a since-deleted colleague silently degrades to an admin. The row lives in `automation_settings` (singleton, id 1) and **may not exist**: no row reads as `admin` everywhere, so nothing has to be seeded for the default to work.

**The assistant is a `User` row with `automated: true`, not a third `UserRole`.** A role decides what an account may do and this one does nothing: no `Account` row, so there is no password to check and nothing can sign in as it; `PATCH`/`DELETE`/`POST /api/users/:id/invite` all 403 on it (the invite would create the missing credential row via the reset flow, the delete would clear the assignee on every ticket it ever resolved); and `ASSIGNABLE_USER` in `routes/tickets.ts` excludes it, so a ticket can *show* the assistant as its assignee while nobody can *choose* it. `prisma/seed.ts` is the **only writer of that column anywhere**, and it looks before it creates — that single-writer property is what keeps there being exactly one, since Prisma cannot express the partial unique index that would say so in the database (it would live only in the migration and be dropped as drift by the next `migrate dev`). Widening `UserRole` instead would have put a machine into every place the codebase asks "admin or agent?", Better Auth's own config included, to describe something that is not a permission level. It is also **not** the author of the replies it is assigned to: those keep `authorId: null` + `automated: true`, because "nobody wrote this" is what an agent reading the thread needs told and it is a different fact from "this ticket is filed under the assistant".

**"No `Account` row" stopped being unique to it.** Every colleague is now created without a credential and gains one by accepting an invitation, so an invited-but-not-yet-accepted agent passes that same test — the absent credential is evidence, not the guarantee. Worse, the invitation mechanism *creates* credentials: `/request-password-reset` is public, so anyone could name the assistant's address and mint a link that makes it signable-in, through a route that never touches `routes/users.ts`. **`sendResetPassword` in `auth.ts` therefore refuses any `automated` or soft-deleted account, and that guard is load-bearing** — it stands exactly where "it has no password" used to. See `docs/adr/0002` (amended) and `docs/adr/0011`.

A reopen re-routes. A customer replying to a machine-resolved ticket clears `autoResolvedAt` and, if the ticket is still assigned to the assistant, hands it to the handoff target (`ingest.ts`) — an open ticket owned by something that cannot read it is worse than an unowned one, because every "unassigned" view an agent works from would skip it. Narrowed to the assistant's own account, so a ticket a *person* resolved and a customer reopened stays theirs, and conditional on the reopen having fired, so the two lookups are paid for by a reopen rather than by every reply on every thread.
