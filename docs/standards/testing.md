# Testing standards

## Commands

- `bun run --filter @ticket/web test` — run web component tests once (CI). Also `test:watch` (headless TUI) and `test:ui` (Vitest UI dashboard, best for authoring).
- `bun run --filter @ticket/api test` — run API unit tests. Runner is **`bun test`**, not Vitest: the API workspace already runs on Bun and carries no test runner, and `mock.module` covers what these need. Provider and session are mocked and the database runs in-process, so no `OPENAI_API_KEY` and still no server to start.

For E2E test commands (`test:e2e`, `db:test:*`), see the `playwright-e2e-author` agent.

## API tests (`apps/api`)

- Tests: **`bun test`** (`bun run --filter @ticket/api test`), files next to the source as `*.test.ts`. `mock.module(specifier, factory)` must be registered *before* the module under test is imported, so the module under test comes in through a dynamic `await import(...)` at the top of the file rather than a static import. Spread the real module into the factory (`{ ...actual, generateText }`) when only one export is being replaced — the constants and error classes the code branches on have to stay real or the test asserts against its own stub. `../db` and `../middleware/auth` are the two mocks almost every route test needs: the first opens a database connection at import, the second pulls in `../auth`, which throws without `BETTER_AUTH_SECRET`.
  - **The database is not mocked — it is real, and it runs in this process** (`docs/adr/0014`). `import { Prisma, prisma, resetDb } from "../test/pg"` and bind it with `mock.module("../db", () => ({ Prisma, prisma }))`; call `await resetDb()` in `beforeEach`. That is a genuine `PrismaClient` on a genuine Postgres — PGLite, compiled to WASM — so `where`, `select`, `orderBy`, `$transaction`, unique constraints and a conditional `updateMany` all mean what Postgres means by them, and this repo's own migrations are what built the schema. **Write new API tests this way; do not add a new hand-written `prisma` fake.** What it costs, measured on both platforms because they differ by ~4x: on CI, ~2.65s once per run and ~26–39ms per route test (suite 0.85s → 4.09s with one file converted, projecting ~10s once all of them are); on a Windows dev machine, ~3.4s once and ~150ms per route test (4.07s → 10.0s). If a converted file feels slow locally, that is the machine, not the approach — check CI before optimising anything. `src/test/pg.ts` carries the caching, the reset and the reasoning; nothing above it knows PGLite exists, which is what keeps a swap to a real server a one-module change.
    - **A rule Postgres enforces rather than a module goes in `src/schema.test.ts`** (#169) — a cascade, a `SetNull`, a `Restrict`, a partial index. It mocks nothing and has no module under test, because there isn't one. The split is by *who* enforces the rule, not by which table it is about: `routes/tutorials.test.ts` covers `PUT /:pageKey` writing `updatedById`, and `schema.test.ts` covers what becomes of that row when the editor's account is deleted. Asserted from inside the route test, a schema rule reads as though the route were responsible for it, and nobody can tell afterwards which assertions would survive the route being deleted. `src/test/fixtures.ts` seeds the rows both kinds of file need — the colleagues, (since #189) the customer and the ticket they opened, and (since #172) the assistant's account, which is a `user` row like the others and is what the two `rejectAssistant` refusals are read against. **Rows only**: the header constants stay beside the per-file `../middleware/auth` stub that reads them, for the registry reason below. Since #173 each colleague also carries a **pinned `createdAt`**, and the order of them is load-bearing: `now()` is transaction time, so `createMany` used to stamp every row with the same instant, and both `GET /api/users`'s "oldest first" and `automation.ts`'s longest-serving-admin fallback were reading a five-way tie.
    - **A route test does not stand up its own server** (#189). `serveRouter(mount, router)` from `src/test/route-app.ts` registers the `beforeAll`/`afterAll` and returns a `url(path)` builder — `const url = serveRouter("/api/tickets", ticketsRouter)`, then `fetch(url("/unread"))`. It replaced ten byte-identical copies of the same app-and-`listen(0)` block, and takes the `node:net` / `node:http` / `express` imports with it. What it deliberately does **not** cover is the `Sent<T>` type and the `get`/`post`/`patch` helpers beside it: those close over each file's own default headers and verbs, and one helper for all of them would be a lowest common denominator every caller worked around.
    - **`resetDb` deletes with `session_replication_role = 'replica'`**, and that is load-bearing rather than tidy. The delete list is built from `pg_tables`, which is in no useful order, and one relation in this schema is `onDelete: Restrict` — `KnowledgeArticleRevision.article`, which is what makes an article undeletable through the ORM (ADR-0006). Before the flag, the *first* test to leave a revision behind broke `resetDb` for every file that ran after it, and the failures appeared everywhere except the file that caused them (found writing `jobs/sweeps.test.ts`, #158: 15 red tests in `routes/tickets.test.ts`). Restored to `origin` immediately, so nothing a test does is exempt from a constraint.
    - **A stub for a module two test files both need lives in `src/test/`, not copied into each of them.** `enqueueEmail` inserts the outbox row *into the caller's transaction* and then hands pg-boss a job, so its stub keeps the insert (through the `Prisma.TransactionClient` it is given) and drops the nudge — and both `outbound.test.ts` and `routes/users.test.ts` need exactly that, so `src/test/send-email.ts` is where it is and `stubSendEmail()` is how it is registered — and **every file that installs it resets its switch in the same `beforeEach` that calls `resetDb()`**, not only the file that flips it, or the second file is relying on the first happening to reset first. Two copies would not do, and the reason is sharper than tidiness: unlike the four identical `../middleware/auth` stubs, this one holds **state** — the `failAfterWriting` switch a rollback test flips — and two copies are two boxes, of which the process-wide registry keeps one, leaving the other file's switch inert. Moving the seam one module down to `./jobs/boss` would run the real `enqueueEmail`, and is the thing not to do: `jobs/sweeps.test.ts` already registers a `./boss` factory, so that would put a second, differently-behaved factory on a specifier another file owns. What that seam buys is not optional, either — the real `enqueueEmail` wraps its insert in `prisma.$transaction` and then calls `getBoss()`, which throws with no queue started and **rolls the row back**, so an outbox row is unobservable without it.
    - **`auth.ts` is loadable by a unit test now, and `routes/users.test.ts` loads it for real** (#172). It used to be the one module a unit test could not reach — it opens a Better Auth instance over a Prisma adapter and reads two environment variables at import — and both halves of that are answered by ADR-0014: `mock.module("../db", …)` points the adapter at the in-process Postgres, and the variables are set in the test file above the `await import("../auth")`. The reason to bother is that the two claims that router exists to make are unreachable through a fake. **ADR-0011's claim is an absence** — `POST /api/users` creates an account with *no* `credential` row, which is what stops anyone but the owner knowing the password and what `sendResetPassword` reads to tell an invitation from a reset; a fake `createUser` can only record that it was called. And **ADR-0009's outbox row is written two modules below the route**, by `sendResetPassword`, so asserting it against a stub would have been asserting a copy of `auth.ts` written in the test file. Two costs, both bounded and both worth naming: Better Auth's admin plugin answers `UNAUTHORIZED` to `createUser`/`adminUpdateUser` whenever headers are present with no session behind them, so the file mints a real one in `beforeAll` (one scrypt hash, one `signInEmail`, ~700ms) and **replays the session row** in `beforeEach` rather than signing in again — `resetDb()` truncates it, and the cookie is signed over the token, so the same token stays valid; and the route's own guard is still the shared `../middleware/auth` stub while Better Auth's permission check is not, so a request carries both the `x-test-*` headers and a genuine cookie, which must name the same admin.
    - **A feature's config guard is its own one-line export, and that is a testability rule rather than a style one** (#174). `ai/polish.ts` has `isPolishConfigured()` and `ai/summarize.ts` has `isSummarizeConfigured()`; both are one line over `isAiConfigured` in `ai/provider.ts`, because there is one key behind every AI feature and "can polish" and "can summarise" are the same question. A route that skips them and calls `isAiConfigured` directly — which the summary endpoint did until its tests were written — forces its test file to register `mock.module("../ai/provider", …)`, and `jobs/sweeps.test.ts` already owns that specifier with a **stateful** stub. Two stateful copies are the `../test/send-email` situation two bullets down: two boxes, of which the registry keeps one, leaving the other file's switch inert. The one-line guard gives each route's test a specifier nothing else touches, so neither file has to know the other exists. Same shape for any shared module a route consults through a narrow question.
    - **"How many times did one request read that row" is `dbCalls` from `src/test/pg`.** Against a hand-written client the counts came free, because every method *was* a `mock()`; #115's guard-shape rule (`rejectAssistant` takes the row its caller already read, not an id it fetches for itself) is invisible to every other kind of assertion, because a route that reads a row twice returns exactly the same response. The client is wrapped in a proxy that increments a counter and hands back the delegate's own return value **untouched** — not a client extension, which was tried and discarded: an extension replaces each operation's `PrismaPromise` with an ordinary one, and the *array* form of `$transaction` needs the former to batch, so `prisma.$transaction([...])` then fails with a validation error naming a column from another model. It does not see operations issued on the `tx` handle inside an interactive `$transaction`. And it **throws on an operation name the client does not have**, because every assertion it backs is a `toBe(n)` and half of them are `toBe(0)`: a mistyped key would satisfy the assertion instead of failing it, and a test that has quietly stopped counting reads exactly like a route that has quietly stopped querying.
  - **No test file mocks the Prisma client any more** (#152 and its follow-ups), and the migration is done: every `../db` factory in `apps/api` binds the one shared client from `../test/pg`. It went in batches. The four leaf route tests went in #169 (`routes/{changelog,dashboard-layout,new-features,tutorials}`), each one router over one or two tables of its own; the two knowledge-base readers went together in #170 (`routes/knowledge`, `ai/knowledge-base`) — batched because a converted file and an unconverted one reaching the same modules is the registry hazard below rather than half a migration; the two on the ticket write path went in #171 (`outbound`, `routes/activity`); `routes/users` went alone in #172; and `automation` went in #173, which **split the file in two** — `automation.test.ts` for the resolution rules and `routes/automation.test.ts` for the router — because the merge that put them together was a workaround for the registry hazard and the conversion is what removes it; and `routes/ai` closed it in #174. #171 is what the migration was for twice over: `routes/activity.ts`'s five-way `UNION ALL` is now **executed** rather than string-matched, so a mistyped column alias, the `CASE` reading the wrong side, and `ts()`'s `::timestamptz AT TIME ZONE 'UTC'` landing a day out are all failures instead of assertions nobody could write; and `outbound.ts`'s two rows — the message and the outbox row beside it — are asserted to commit or roll back together, which is ADR-0009's whole claim. `routes/tickets.test.ts` and `routes/knowledge.test.ts` are the files to copy from: the two that exercise a transaction and a relation, and the second is the one that asserts a **rollback** — a `$transaction` that fails partway leaves nothing behind, which is the assertion a fake client cannot make and the reason ADR-0006's audit rule is testable at all. **#174 is the one worth reading for what the two seams can and cannot each see.** `routes/ai.test.ts`'s nested `messages` query had been asserted as the *arguments* it was called with — `where: { direction: inbound }`, `take: 1`, `select: { textBody: true }` — and against a real database the first becomes a fact about which sentence reached the model (an outbound reply is not a candidate at all), alongside a `[createdAt desc, id desc]` tie-break that no argument assertion could reach at all. The other two do not survive, and **the honest move is to record that in the file rather than write a comment implying otherwise** — both measured by mutating the route and re-running. `take: 1` was never coverage: the handler reads `messages[0]`, so the file is green at `take: 5`. `select: { textBody: true }` is the sharper case, because it is a real loss: it is ADR-0008's "never render email HTML" rule reaching into a prompt, the handler only ever reads `textBody`, so `htmlBody: true` beside it is green too — the column never reaches the response and **no test at the database seam can observe it**. A hand-written client could watch a query the caller cannot otherwise inspect; a real database cannot. That is the one thing ADR-0014 costs, it is worth knowing before reaching for a fake to "get the assertion back", and the answer if such a select must be guarded is a check that reads the query, not a route test pretending to. The registry hazard below is what the whole migration was for, and it is now closed for `../db`: every file binds the same client, so no file can be handed a stranger's. It still applies in full to every other specifier a factory replaces, so keep reading it.
  - **The registry is one process wide and nothing resets it between files.** Every test file's `mock.module` calls and every module they import share it, so two files that mock the same specifier and import the same module are not independent: the module binds to whichever fake was registered when it was first imported, and the other file's tests then run against a stranger's stub. Two consequences, both learned the hard way. A factory that does not spread the real module *is* that module for every file loaded afterwards — `routes/ai.test.ts`, `routes/automation.test.ts`, `routes/knowledge.test.ts`, `routes/activity.test.ts`, `routes/tutorials.test.ts` and `routes/users.test.ts` therefore ship the **same** `../middleware/auth` stub, identical headers and defaults, and export `requireAuth` and `requireAdmin` whether or not the file under test uses both. And when two suites would need the same module bound to different fakes, put them in **one file** — which is why `automation.test.ts` covered `automation.ts` and `routes/automation.ts` together until #173, and why it does not any more: both halves now bind `../db` to the one shared client, so there was nothing left for two files to disagree about and they are two files again, each named after the module it covers. The failure mode to watch for is a file that passes alone and fails in the suite; run `bun test <a> <b>` in both orders before believing a new mock. Converting a file onto `../test/pg` takes `../db` out of this: every converted file binds the specifier to the *same* shared client, so sharing it is a no-op rather than a stranger's stub. That is the whole point of ADR-0014, and since #174 it is true of the whole suite — there is no unconverted file left for a converted one to collide with. **`../db` is the exception, not the rule**: `../middleware/auth`, `../ai/polish`, `./boss` and every other specifier a factory replaces are still one registry deep, so a new mock still gets `bun test <a> <b>` in both orders before it is believed.
  - **Every `../db` (or `./db`) factory must export `Prisma`**, whether or not the file under test touches it — which since #174 means the `Prisma` that `../test/pg` re-exports for exactly this reason: `import { Prisma, prisma, resetDb } from "../test/pg"`, then `mock.module("../db", () => ({ Prisma, prisma }))`. (A hand-written factory would take it from `await import("../generated/prisma/client")`; there is none left, and there should not be a new one.) `routes/activity.ts`, `routes/ticket-stats.ts` and `routes/ticket-effectiveness.ts` import it as a *value* (`Prisma.sql` composes their raw queries), so a factory that leaves it out can be the one in force when one of those modules is linked, and the run dies with `SyntaxError: Export named 'Prisma' not found in module .../src/db.ts`. **This is intermittent, and that is the point** — it depends on the order `bun test` reaches the files in, so the same commit can go red on one run and green on a re-run of that same run (measured: run 33737874918, 210 pass / 2 errors, then 237 pass on re-run with no code change). Five factories were missing it and were fixed together; don't reintroduce one.

## Component tests (`apps/web`)

- Component tests: **Vitest** + **React Testing Library** + **jsdom**. Test files live next to the component as `*.test.tsx` (e.g. `apps/web/src/pages/UsersPage.test.tsx`). Vitest config is inlined in `apps/web/vite.config.ts` (`globals: true`, `environment: "jsdom"`); jest-dom matchers and RTL `cleanup` are wired in `apps/web/src/test/setup.ts`. Mock module boundaries with `vi.mock`: stub `@/lib/api` (axios) and `@/lib/auth-client` (`useSession`) so tests don't touch the network or the session. (`@/lib/theme` used to be listed here and does not exist — the app is dark-only. The one thing that does read `localStorage` is `@/lib/use-row-density`, which needs no stub: it is wrapped in try/catch and jsdom provides storage.) Prefer accessible queries (`getByRole`, `getByLabelText`) over class/text selectors. Don't try to E2E-style log in here — that lives in Playwright (see the `playwright-e2e-author` agent).
  - **Rendering: `renderRoutes(routes, { initialEntries? })` from `@/test/render`** — the suite's only *shared* render helper since #159. It mounts a `createMemoryRouter` — the same *kind* of router `App.tsx` builds — so the entry URL decides which route matches, a route's `loader` runs before its component, and `useNavigation()` reports the pending state in between. It provides a fresh `QueryClient` (`retry: false`, `gcTime: 0`) and a `TooltipProvider`, and returns the live `router` alongside RTL's result, which is where a URL-state assertion should read from (`router.state.location.search`) rather than from a probe component rendered beside the page. A test about a *component* rather than a page mounts it as the one route the default entry URL matches — `renderRoutes([{ path: "/", element: <ChangelogPopover /> }])`. A second helper, `renderWithQuery`, used to mount a plain `MemoryRouter` beside it; it resolved `useLocation`/`<Link>` and nothing else, which is why nothing the prefetch work added was testable below E2E until #148, and it is now deleted.
    - **A component that needs none of it still uses bare RTL `render`, and should.** `MiniBarList`, `StatTile` and `AssistantEffectivenessCard` take plain props and touch neither the router nor the query client; the three dashboard tests mount them under a `TooltipProvider` alone, because providers a component does not use hide the fact that it does not use them. #159 deleted the *second* helper, it did not make `renderRoutes` mandatory — reach for it when the router, the query client or a tooltip is actually in play. A file that mounts the same subject several times may wrap the route object in a local one-liner (`Tutorial.test.tsx`, `table-frame.test.tsx`); that is formatting, not a third helper.
    - **The two behaviour differences a converted test can trip over**, both found migrating the last ten callers. A **navigation is asynchronous** on a data router — it is allowed to run loaders — so an imperative `navigate()` fired from outside React (a toast action, say) needs `await act(async () => …)` rather than a bare `act()`, or the router's state advances and React never renders it (`use-assignment-toasts.test.tsx`). And rendering is a little heavier, which widens any race a test already had: `ProjectMapPage.test.tsx`'s search assertions had to move into a single `waitFor` describing the **settled** state, because typing past a 150 ms debounce renders transient results that satisfy half of a split assertion.
  - **A route's `loader` can be mounted as-is, and tested without a DOM.** `renderRoutes` points the prefetching loaders at the client it creates (`setPrefetchQueryClient`, restored by `setup.ts`'s `afterEach`), so what a loader primes is what the page reads — before #157 they wrote into the app-wide singleton and no test could see it. For the narrower question of what a loader *requests*, `runLoader(loader, url, { params, queryClient })` from `@/test/run-loader` builds the `request`/`params` pair React Router would pass and returns the client it primed; `*.loader.test.ts` next to each loader is where that lives. Two gotchas, both about the test client's `gcTime: 0`: an entry nothing observes is collected the moment it settles, so a test that reads the cache after a bare loader run — or that mounts a page *behind* a loader — passes its own `queryClient` with a real `gcTime` (the app's is five minutes). And the page tests deliberately mount their routes *without* their loaders: `staleTime: 0` makes the page refetch what the loader just primed, which would double every call count they assert.
  - **HTTP: the shared stub at `@/test/api-stub`**, installed with one line — `vi.mock("@/lib/api", () => import("@/test/api-stub"))` — and then `const ticketsGet = apiStub.get("/api/tickets")` per endpoint, `apiStub.reset()` in `beforeEach`. Each accessor returns a plain `vi.fn` scoped to that method and path, so every mock ergonomic and every assertion still applies (`mockResolvedValueOnce`, `mockReturnValue(new Promise(() => {}))`, `toHaveBeenCalledTimes`, `mock.calls[n]`) — with counts and indices now **per path**, which is what removes the `calls.filter(([url]) => url === …)` dance a second endpoint used to force. Paths may be react-router patterns (`/api/tickets/:id`), matched literal-first — `/api/tickets/assignees` and `/api/tickets/unread` keep their own counters beside a `/api/tickets/:id` that would otherwise swallow them. Two things it does that a hand-rolled `mockGet` cannot: an unregistered request throws by name instead of resolving `undefined` four assertions from where it matters, and **the per-page `<Tutorial>`'s request is answered by default**, so no page test branches for a callout it never exercises. Both earned their keep on `TicketDetailPage.test.tsx`, whose catch-all had been answering `/api/tickets/:id/activity` with a *ticket* — a request no assertion had ever noticed being wrong.
    - **Every test in the web suite is on it** (#155 page tests, #156 the rest): there is no hand-rolled request routing left anywhere, so a new test declares paths rather than writing another `if (url === …)`. One stub and one render helper is the whole contract — page tests render their own route at the URL a navigation would use, and the component, dialog and hook tests mount theirs at `/` (#159).
    - **A test that registers a path the stub already answers by default takes over that path, and only for itself.** `Tutorial.test.tsx` is the file this exists for — it is *about* the callout every other test wants silenced, so it takes `/api/tutorials/:pageKey` and its `/seen` pair as ordinary handles and overrides them per test. `reset()` puts the "nothing to show" default back, which is what stops it deciding what a page test sees.
    - **Declaring an endpoint the file has no opinion about is now part of the setup.** A request the stub does not recognise throws, so a component that fetches four things needs four answers even in a test about one of them — `AppSidebar.test.tsx` gives all four a resting value in `beforeEach` and each test overrides the one it is about. Under the old catch-alls an unanswered query resolved `undefined` and failed quietly somewhere else, which is the trade this is the good half of.

Radix floating-layer widgets need a click-the-trigger approach rather than `selectOptions` — see [frontend.md](frontend.md).

## E2E

- Testing: see the `playwright-e2e-author` agent for the E2E setup (Playwright config, test DB, alt ports, env file, run/seed scripts).

## Scripts and environment

**Every script and all three seeds are catalogued in `SCRIPTS.md`** — what each writes, which of the three environments it belongs to, and the fresh-machine and first-deploy orders. Go there before guessing at a command; the sharp part is which ones may point at production (`db:seed` and `db:seed:kb` yes, `db:seed:tickets` and `db:migrate` never).
Bun env gotchas: `bun --env-file=X x ...` and `bun --env-file=X run <script that calls bun>` do **not** propagate the env to the child — the inner `bun` re-loads default `.env`. For Prisma CLI use `dotenv-cli`. Workspace filter syntax is `bun run --filter <pkg> <script>`, not `bun --filter <pkg> run <script>`.
