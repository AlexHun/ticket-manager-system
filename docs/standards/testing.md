# Testing standards

## Commands

- `bun run test` (repo root) — both unit suites, `@ticket/api` then `@ticket/web`, sequentially so a failure is legible rather than interleaved. ~5.5 min on a Windows dev machine, and this is exactly what `.husky/pre-push` runs; see [conventions.md](conventions.md) for why the suites are on push rather than commit.
- `bun run --filter @ticket/web test` — run web component tests once (CI). Also `test:watch` (headless TUI) and `test:ui` (Vitest UI dashboard, best for authoring).
- `bun run --filter @ticket/api test` — run API unit tests. Runner is **`bun test`**, not Vitest: the API workspace already runs on Bun and carries no test runner, and `mock.module` covers what these need. Provider and session are mocked and the database runs in-process, so no `OPENAI_API_KEY` and still no server to start.

For E2E test commands (`test:e2e`, `db:test:*`), see the `playwright-e2e-author` agent.

## Component tests (`apps/web`)

- Component tests: **Vitest** + **React Testing Library** + **jsdom**. Test files live next to the component as `*.test.tsx` (e.g. `apps/web/src/pages/UsersPage.test.tsx`). Vitest config is inlined in `apps/web/vite.config.ts` (`globals: true`, `environment: "jsdom"`); jest-dom matchers and RTL `cleanup` are wired in `apps/web/src/test/setup.ts`. Mock module boundaries with `vi.mock`: stub `@/lib/api` (axios) and `@/lib/auth-client` (`useSession`) so tests don't touch the network or the session. (`@/lib/theme` used to be listed here and does not exist — the app is dark-only. The one thing that does read `localStorage` is `@/lib/use-row-density`, which needs no stub: it is wrapped in try/catch and jsdom provides storage.) Prefer accessible queries (`getByRole`, `getByLabelText`) over class/text selectors. Don't try to E2E-style log in here — that lives in Playwright (see the `playwright-e2e-author` agent).
  - **Rendering: `renderRoutes(routes, { initialEntries? })` from `@/test/render`** — the suite's only _shared_ render helper since #159. It mounts a `createMemoryRouter` — the same _kind_ of router `App.tsx` builds — so the entry URL decides which route matches, a route's `loader` runs before its component, and `useNavigation()` reports the pending state in between. It provides a fresh `QueryClient` (`retry: false`, `gcTime: 0`) and a `TooltipProvider`, and returns the live `router` alongside RTL's result, which is where a URL-state assertion should read from (`router.state.location.search`) rather than from a probe component rendered beside the page. A test about a _component_ rather than a page mounts it as the one route the default entry URL matches — `renderRoutes([{ path: "/", element: <ChangelogPopover /> }])`. A second helper, `renderWithQuery`, used to mount a plain `MemoryRouter` beside it; it resolved `useLocation`/`<Link>` and nothing else, which is why nothing the prefetch work added was testable below E2E until #148, and it is now deleted.
    - **A component that needs none of it still uses bare RTL `render`, and should.** `MiniBarList`, `StatTile` and `AssistantEffectivenessCard` take plain props and touch neither the router nor the query client; the three dashboard tests mount them under a `TooltipProvider` alone, because providers a component does not use hide the fact that it does not use them. #159 deleted the _second_ helper, it did not make `renderRoutes` mandatory — reach for it when the router, the query client or a tooltip is actually in play. A file that mounts the same subject several times may wrap the route object in a local one-liner (`Tutorial.test.tsx`, `table-frame.test.tsx`); that is formatting, not a third helper.
    - **The two behaviour differences a converted test can trip over**, both found migrating the last ten callers. A **navigation is asynchronous** on a data router — it is allowed to run loaders — so an imperative `navigate()` fired from outside React (a toast action, say) needs `await act(async () => …)` rather than a bare `act()`, or the router's state advances and React never renders it (`use-assignment-toasts.test.tsx`). And rendering is a little heavier, which widens any race a test already had: `ProjectMapPage.test.tsx`'s search assertions had to move into a single `waitFor` describing the **settled** state, because typing past a 150 ms debounce renders transient results that satisfy half of a split assertion.
    - **RTL's `waitFor` has its own 1000 ms default, and Vitest's `testTimeout` does not govern it.** This is the trap in every debounced-search flake here: `testTimeout` is already 15 s in `vite.config.ts`, so a red assertion looks like it had fifteen seconds and did not, it had one — 700 ms of margin over `SEARCH_DEBOUNCE_MS`, on pages that keep growing filter chips and columns. Pass `{ timeout: 5_000 }` explicitly when waiting on anything debounced; raising `testTimeout` again will not help. (`TicketsPage.test.tsx` "writes the settled search to the URL", fixed 2026-08-13.)
    - **One isolated run cannot establish determinism.** The same flake failed once in isolation, which read as "deterministic, therefore a real break", and the bisect that followed passed on every variant because the flake simply did not fire again. Repeat an isolated run at least three times before concluding anything from it, and check _which_ test went red before blaming the change in front of you.
  - **A route's `loader` can be mounted as-is, and tested without a DOM.** `renderRoutes` points the prefetching loaders at the client it creates (`setPrefetchQueryClient`, restored by `setup.ts`'s `afterEach`), so what a loader primes is what the page reads — before #157 they wrote into the app-wide singleton and no test could see it. For the narrower question of what a loader _requests_, `runLoader(loader, url, { params, queryClient })` from `@/test/run-loader` builds the `request`/`params` pair React Router would pass and returns the client it primed; `*.loader.test.ts` next to each loader is where that lives. Two gotchas, both about the test client's `gcTime: 0`: an entry nothing observes is collected the moment it settles, so a test that reads the cache after a bare loader run — or that mounts a page _behind_ a loader — passes its own `queryClient` with a real `gcTime` (the app's is five minutes). And the page tests deliberately mount their routes _without_ their loaders: `staleTime: 0` makes the page refetch what the loader just primed, which would double every call count they assert.
  - **HTTP: the shared stub at `@/test/api-stub`**, installed with one line — `vi.mock("@/lib/api", () => import("@/test/api-stub"))` — and then `const ticketsGet = apiStub.get("/api/tickets")` per endpoint, `apiStub.reset()` in `beforeEach`. Each accessor returns a plain `vi.fn` scoped to that method and path, so every mock ergonomic and every assertion still applies (`mockResolvedValueOnce`, `mockReturnValue(new Promise(() => {}))`, `toHaveBeenCalledTimes`, `mock.calls[n]`) — with counts and indices now **per path**, which is what removes the `calls.filter(([url]) => url === …)` dance a second endpoint used to force. Paths may be react-router patterns (`/api/tickets/:id`), matched literal-first — `/api/tickets/assignees` and `/api/tickets/unread` keep their own counters beside a `/api/tickets/:id` that would otherwise swallow them. Two things it does that a hand-rolled `mockGet` cannot: an unregistered request throws by name instead of resolving `undefined` four assertions from where it matters, and **the per-page `<Tutorial>`'s request is answered by default**, so no page test branches for a callout it never exercises. Both earned their keep on `TicketDetailPage.test.tsx`, whose catch-all had been answering `/api/tickets/:id/activity` with a _ticket_ — a request no assertion had ever noticed being wrong.
    - **Every test in the web suite is on it** (#155 page tests, #156 the rest): there is no hand-rolled request routing left anywhere, so a new test declares paths rather than writing another `if (url === …)`. One stub and one render helper is the whole contract — page tests render their own route at the URL a navigation would use, and the component, dialog and hook tests mount theirs at `/` (#159).
    - **A test that registers a path the stub already answers by default takes over that path, and only for itself.** `Tutorial.test.tsx` is the file this exists for — it is _about_ the callout every other test wants silenced, so it takes `/api/tutorials/:pageKey` and its `/seen` pair as ordinary handles and overrides them per test. `reset()` puts the "nothing to show" default back, which is what stops it deciding what a page test sees.
    - **Declaring an endpoint the file has no opinion about is now part of the setup.** A request the stub does not recognise throws, so a component that fetches four things needs four answers even in a test about one of them — `AppSidebar.test.tsx` gives all four a resting value in `beforeEach` and each test overrides the one it is about. Under the old catch-alls an unanswered query resolved `undefined` and failed quietly somewhere else, which is the trade this is the good half of.

Radix floating-layer widgets need a click-the-trigger approach rather than `selectOptions` — see [frontend.md](frontend.md).

## Scripts and environment

**Every script and all three seeds are catalogued in `SCRIPTS.md`** — what each writes, which of the three environments it belongs to, and the fresh-machine and first-deploy orders. Go there before guessing at a command; the sharp part is which ones may point at production (`db:seed` and `db:seed:kb` yes, `db:seed:tickets` and `db:migrate` never).
Bun env gotchas, and they compound — fix one and the next one bites. **A nested `bun` re-loads the default `.env` over whatever the parent set**, so `bun --env-file=X run <script that calls bun>` does not propagate: the inner Bun auto-loads `apps/api/.env` on top. **`dotenv-cli` does not save you when the child is Bun** — `dotenv -e .env.test -- bun prisma/seed.ts` sets the env correctly and then Bun clobbers it; on 2026-05-15 that had `db:test:seed` silently writing to the **dev** DB while logging that the agent already existed. The fix is to call Bun with `--env-file=` **directly** (`bun --env-file=.env.test prisma/seed.ts`), because passing the flag is what disables Bun's auto-`.env` load. `dotenv-cli` is still right for the Prisma CLI, which is not Bun. Separately, **`--env-file` deliberately excludes `NODE_ENV`** — a `.env.test` containing `NODE_ENV=test` does nothing, and `process.env.NODE_ENV` reads `undefined` — so set it from the shell or Playwright's `webServer.env`. That one matters because the `disableOriginCheck` gate in Better Auth is keyed on it (see [backend.md](backend.md)).

Workspace filter syntax is `bun run --filter <pkg> <script>`, not `bun --filter <pkg> run <script>` — the flag belongs to `run`. `--filter` now runs with the workspace as cwd (re-measured 2026-08-16 on Bun 1.3.13; it did not before), but **the root `db:test:*` scripts still use an explicit `cd apps/api &&` and should stay that way**: the old failure wiped and reseeded the dev DB with the test `BETTER_AUTH_SECRET` and threw nothing, and the blast radius is not worth trusting a version floor for anything that opens a database connection.
