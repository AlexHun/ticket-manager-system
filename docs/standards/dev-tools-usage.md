# Dev tools standards: Usage (`/__dev/usage`)

The Usage page and everything behind it: the scan, the usage history and its push from a laptop to Railway's `develop`, the table, its filters and chart, and `bun run tokens`. How the `/__dev` tools are built and served, and what the dev server may spawn, is [dev-tools.md](dev-tools.md), which binds this page too.

- **Usage scans nothing until Scan is pressed, and nothing anywhere caches the answer — but since #417 the dev server keeps what each scan _read_, and since #419 one point per day for the trend.** The other pages fetch on load; a scan here reads every transcript the machine holds, and its claim is that the figures on screen were gathered at a named moment from a named directory. So `useUsageScan` is a `useMutation` rather than a `useQuery` (a query is something react-query is entitled to run for you — on mount, on focus, on reconnect), and the page holds the last result until the next one. **Since #432 the page opens on the stored reading instead of empty**: `GET /__devtools/usage` (`readStoredUsage` in `dev/usage.ts`, through `useStoredUsage`, a query with `gcTime: 0` so a return asks again) computes the same report from the history's rows, its trend and the listing the last scan kept in it (or `GH_ISSUES_FILE`, which a push rewrites), opening the file read only — no transcript, no `gh`, no write, ~32-45ms over 14,352 rows. Its `transcripts` is null, which is how the page words it as "Stored at … by the last scan or push" rather than "Gathered at" — the moment being the store's stamp of when rows last arrived; Scan replaces it. It is null — the empty state — with no history configured (`pushHistoryFile`), no file or no rows, and a failed `GET` is a warning beside that empty state, not a toast. Nothing derived is persisted for it (ADR-0023's #432 section). What the middleware keeps between presses is the **usage history** (`dev/usage-store.ts`, ADR-0023): one SQLite row per API response at `~/.claude-usage-history/<project-slug>.sqlite`, outside the repo and outside `~/.claude`, so an issue keeps its spend after Claude Code deletes the transcript after 30 days. **The slug is the main worktree's root, not the working directory's** (#423): `resolveHistoryFile` asks `git rev-parse --git-common-dir` (async, through `gitEnv`, falling back to the cwd's slug when git cannot answer), so every worktree of a clone shares one history while `resolveTranscriptDir` still reads each worktree's own transcripts; it is `async` for that reason, and both callers await it. It stores responses and never a row's answer — attribution and counting (`tallySpend` in `dev/transcripts.ts`) run over every stored row on every read, so a correction like #413's reaches rows whose transcript is gone — and it is opened per request and closed before the response, because a handle held between presses would stop a spec or a developer deleting the file on Windows. **On Bun, closing is not enough**: `bun:sqlite`'s `close` defers while any prepared statement is unfinalized, so the file stayed locked (EBUSY) after a scan until the garbage collector ran — the Bun opener finalizes what it prepared before it closes (#418), and the E2E, which runs Vite on Node, could never have seen it. **Since #418 a scan reads only what was appended**: the store also keeps a cursor per transcript (byte offset past the last newline, size, line count, and a hash of the first bytes), `readTranscripts` resumes from it, a file whose size has not changed is not opened, and a file that shrank or no longer starts the same way is re-read from the top, its overlap absorbed by the identity key. A trailing line with no newline is parsed but left in front of the cursor, so a half-written one counts once it is finished and a complete one counts once. Measured on 168 transcripts: a warm scan went from ~2.2s to ~60ms; a cold one still costs a full read (~2.2s before, ~2.3-2.4s after, the difference being the cursors' hashing and writes). The page names the history's earliest date (`historySince`) beside the reading. **Since #419 the history keeps one answer as well: a trend point per local calendar day, written by every scan that keeps a history (`bun run tokens` included)** (`trend_point`, the day's last scan replacing it) — the quartiles of output tokens, the accuracy tally and the band edges in force, because a past day's labels and bands cannot be asked again; never a row's verdict, so every verdict on the page is still judged against today's bands (ADR-0023's #419 section). The point is `trendPointFor` in `src/dev/usage-readings.ts`, built from the same `recordedSpend`/`percentiles`/`forecastAccuracy` calls the two panels make over the same rows, so today's point and the panels cannot disagree; the day is **local**, not `toISOString()`'s UTC date, and that boundary and the replace-not-append rule are vitest cases with a clock passed to `gatherUsage` (`dev/usage.test.ts`), since Playwright cannot move a day. The page draws it in `src/dev/UsageTrend.tsx` — two `ChartPanel`s and a `TableFrame` of points beneath them, which is the relief path and what `dev-usage-history.spec.ts` reads a day from. Their region names live in `USAGE_TREND_LABEL` and must not contain another region's name: Playwright matches names as case-insensitive substrings, so "Forecast accuracy over time" would put every `{ name: "Forecast accuracy" }` in `dev-usage.spec.ts` in strict-mode violation. Bun cannot resolve `node:sqlite` and Node cannot load `bun:sqlite`, and both run this code — the developer's dev server and `bun run tokens` on Bun, vitest and the E2E's `bunx vite` on Node — so the store speaks to a narrow `SqlDatabase` surface and `openUsageStore` imports whichever module the running process has, through a variable so neither resolver chokes on the other's; the `bun:sqlite` types are a minimal ambient declaration (`dev/bun-sqlite.d.ts`) rather than `@types/bun`. That is deliberately the opposite of the test runner ([dev-tools.md](dev-tools.md)): a run is a long-lived process worth surviving a reload, a scan is a few seconds of reading that is cheaper to repeat than to invalidate. The join itself lives in `apps/web/dev/usage.ts` and is shared with `bun run tokens`, so the page and the terminal cannot report different figures for the same issue.
- **Railway's `develop` history is fed by pushes, never by its own transcripts** (#428). It has none — they are on the developer's laptop — so `bun run tokens --push <url>` sends the local history's `response` rows and the issue listing to `DEVTOOLS_API.usagePush`, and that server's scans tally them like any other stored rows (the volume, the variables and the command are `DEPLOYMENT.md` §7). Four rules. **Rows, not transcripts**: the wire is `src/dev/usage-push.ts`, strict zod on both the rows (the six `TranscriptResponse` fields) and the issues, so a key nobody declared is a 400 rather than a stored column, and `buildPush` copies the six fields by name rather than spreading a row; `dev/usage-push.test.ts` asserts the payload's keys and that a transcript's text and paths are absent. The schema sits there rather than in `@ticket/core`, the one exception to [conventions.md](conventions.md)'s rule, and a forced one: `dev/` is loaded by Vite's native config loader, which resolves nothing extensionless (the `.ts` extensions bullet under [dev-tools.md](dev-tools.md)'s "How the tools are built and served"), and `@ticket/core`'s index re-exports extensionless — so it is defined once beside the other Usage contracts and parsed by both ends. **The listing rides along instead of `gh`**: the dev image has no `gh`, so the server writes the pushed listing to `GH_ISSUES_FILE` (temp file and rename) and the page reads it through the override that never falls back; a push carrying one with that variable unset is a 409 and stores nothing. **Re-pushing is free**: every row goes every time and the store's per-id `ON CONFLICT` is the dedupe (since #431 it raises a stored row's counts to a larger pushed one rather than doing nothing), so there is no second cursor to drift. **The develop server is marked, not inferred**: `Dockerfile.dev` sets `USAGE_HISTORY_PUSHED=1` (`PUSHED_HISTORY_ENV`), and only there does a missing (ENOENT) or empty transcript directory beside a history holding rows raise no warning (`gatherUsage`'s `pushedHistory`) and a push without `USAGE_HISTORY_FILE` get a 409, since the default file is inside the container. Inferring it from "the history holds rows" was the first cut and lost: since #423 the history is keyed on the main worktree and the transcripts on the cwd, so a laptop scan from the wrong directory would have dropped the very warning that says so. A directory that exists and cannot be read warns everywhere. The route is `/__devtools/usage-push`, a sibling of `usage` rather than a path under it, because connect mounts by prefix and the scan handler would answer it first.
- **`CLAUDE_TRANSCRIPT_DIR` and `GH_ISSUES_FILE` are the two seams that make any of it testable, and `USAGE_HISTORY_FILE` is the third** (#417) — `playwright.config.ts` points it at `tests/e2e/fixtures/usage-history.local.sqlite`, which `resetTranscriptWorkingCopy` removes with the working copy, and every unit test and the guardrail's `bun run tokens` spawn set it too: unset, a fixture scan writes fixture spend into the developer's real history. Neither source is something an assertion can name — the real transcript directory is derived from `cwd` + `homedir` and holds this machine's own spend, and what this repo's issues are titled changes every time somebody files one. So `resolveTranscriptDir` honours an override and `playwright.config.ts` points the E2E web server at a copy of `tests/e2e/fixtures/transcripts` (totals written down in that checked-in directory's `README.md`, restated as literals in `tests/e2e/dev-usage.spec.ts`). The copy is `tests/e2e/fixtures/transcripts.local`, gitignored and remade by each Usage spec before it scans (`resetTranscriptWorkingCopy`, #416), so a spec may delete or append to a transcript without touching the checked-in one. Likewise `fetchIssueMetadata` (`dev/issues.ts`) honours an override naming a file holding what `gh issue list --json …` would have printed. The page prints the directory it read, and the fixture titles carry the word “Fixture”, for the same reason: locally, `reuseExistingServer` will adopt a leftover Vite on 4001 that was started without either override, and the page then reports the developer's own transcripts against GitHub's real titles — which looks like a missing row rather than the wrong server.
  - **The listing override never falls back to `gh`**, and the E2E's listing fixture is written by the spec rather than checked in (`tests/e2e/fixtures/gh-issues.ts`, gitignored as `*.local.json`). Both follow from the same constraint: a web server's environment is fixed when it starts, so the only honest way to reach the no-`gh` state through the real middleware is for the file it names to be missing — and a fallback would have that case read live GitHub and pass or fail depending on whose machine it ran on.
  - **`gh` is available from a dev-server child, sanitiser and all** (#249, measured): its credential comes from the OS credential store, and no `.env*` file here declares a GitHub token, so `configuredKeys` has nothing to strip. Two things that are easy to break — the spawn's `cwd` must be the repo root (`gh` resolves the repository from the git remote of wherever it runs), and it must be **one** `gh issue list` call rather than a loop of `gh issue view`, which costs ~0.9s per issue against ~1.7s for all of them.
- **The Usage table opens on four columns, and one control appends the other three** (#271). `USAGE_SPINE` (`title`, `out`, `comparison`) is what a scan shows; `USAGE_DETAIL` (`turns`, `sessions`, `cacheRead`) comes back on a shadcn `Toggle` above the table, `variant="outline"` like the project map's pair, named by `aria-label` rather than by its chip. **The contract is two lists whose concatenation is the order, not one list with a `detail` flag**, and the reason is positional: detail columns _append_, so a spine cell sits at the same index in both states and the one `CELL` map each suite builds from `USAGE_COLUMNS` serves both. Two maps could disagree, and the suites that index a row by position would go on passing while asserting against a neighbouring cell. Bringing the three back is allowed to reintroduce horizontal scrolling — it is opt-in, and `TableFrame` already makes the scroller focusable and named. The E2E holds the width claim by comparing the scroller's `scrollWidth` to its `clientWidth` at 1280px rather than by counting columns — but **know what that assertion is worth before leaning on it.** Measured 2026-09-19 against a real scan (103 issues, 1280px window): the frame reads 1218/1218 with the detail columns _shown_, and 1248/1248 both ways on the E2E fixture. Seven columns already fit; the scroll the PRD complains about was **nine**, and #270's merged comparison cell is what removed it. The toggle buys less to read, not less to scroll, and the assertion is a regression guard — a `min-w` on the `<table>`, a column escaping `Title`'s `max-w-[26rem]` cap, a fifth column in the spine.
- **Every figure column and the issue number rank the table from their header, and a row with no recorded spend sinks to the bottom in _both_ directions whatever column is sorted** (#272). The comparator is `src/dev/usage-sort.ts` — pure, and unit-tested over made-up rows, because the sink is a property of the comparator rather than of the output-tokens column: `usage-sort.test.ts` asks it of every key in both directions. The header markup copies `ModuleTable` exactly (`aria-sort` on the `<th>`, a button inside it, an `aria-hidden` `ArrowUp`/`ArrowDown`, clicking the active column flips it); a column nothing ranks by carries **no** `aria-sort` rather than `"none"`, which would advertise a control that is not there. The sink _is_ the ticket, not a detail of it. `bucketFor(0)` is `S`, so an unstarted row read as zero arrives first in an ascending sort as the cheapest work in the repository, and its band would then score it as having come in under — the same lie the cells refuse to tell (`NotStarted`), told in the ordering instead. A row that really spent zero is a measurement and still ranks as the cheapest work there is; nothing substitutes one for the other. The sortable set is a **record keyed by `"issue" | keyof IssueSpend`** (`SORTABLE`, with `USAGE_SORT_KEYS` as its walkable half), so it is exhaustive by construction — a list could only be checked for membership, and a fifth figure on `IssueSpend` would have arrived with no way to rank by it. `title` and `comparison` cannot be named by that key type at all, which is where their exclusion stops being a comment: a name nobody ranks a spend table by and one that can be absent (a second sink rule, for a different reason), and three facts in one cell. Which column offers which key is said once too — `COLUMNS` is typed so a column whose name is a sort key **must** carry `sort`, and it must be its own name, because the two lists were otherwise free to drift: dropping `sort` from `turns` left the comparator's tests green while no header offered it, and a copy-pasted `sort: "turns"` on `cacheRead` compiled and ranked the wrong column. The default is output tokens descending because that **is** the order `joinIssues` returns, and one comparator is what holds the two level: while each side wrote its own, `dev-usage-guardrail.spec.ts` found that reversing either moved only one of the two surfaces: since #286 the node half imports `DEFAULT_USAGE_SORT` and `sortIssues` and sorts the wire rows with them, so the first render after a scan is the order the server sent rather than an order that reproduces it. The issue-number tie-break sits **outside** the direction flip, which is what makes the order total, and that is now load-bearing rather than tidy: a default whose tie-break reversed with the direction would be total in one direction only, and `joinIssues` would need a rule of its own again for the other.
  - **The chosen sort is `UsagePage`'s state, not `SpendTable`'s, and the reason is measured rather than stylistic.** `useUsageScan` is a `useMutation`, and a mutation clears its `data` the moment it is fired (`case "pending"` sets `data: undefined` in query-core), so `report` is null for the length of the read, the `report &&` gate closes and the table unmounts. Anything kept inside it is thrown away by the press of Scan that re-asks the same question — which is exactly what the acceptance criterion "the sort survives a re-scan" is about. **#271's detail toggle moved up with it**, and had to: `turns`, `sessions` and `cacheRead` only have a header while it is on, so a sort on one of them surviving a re-scan _without_ the columns would satisfy "the chosen sort survives" and break "the active column shows its direction" in the same render — a ranking with no arrow, no `aria-sort` and nothing on screen saying why. The two are one `UsageTableView` for that reason. The same hole is reachable by hand, so hiding the detail columns while the sort is on one of them **returns the sort to the default**: going back to the order the rows arrived in is the one outcome that can still be announced, and it happens in the gesture that caused it.
- **The Usage filter bar's reach is the table and nothing else, and that is the slice's decision rather than its implementation** (#273). A debounced `type="search"` box above the table narrows it on the issue number — matched as the row prints it, `#101`, so the hash out of a commit message is a term that matches — and on the title, through `matchesQuery` in `dev/module-match.ts` rather than an inline `includes`. What it must not touch is everything else on the page: the accuracy figure, the distribution's quartiles, the unattributed total and the gathered-at line all read `report.issues` on `UsagePage` and never see the filtered rows. The accuracy figure is the number somebody might quote, so a filter that moved it would turn a claim about this repository into a claim about a search box — the map's bar next door has two different reaches for its own controls, which is why a new filtering surface picks one deliberately instead of inheriting one. `dev-usage.spec.ts` holds it by comparing the three panels' `textContent` either side of a narrowing, not by re-reading a figure out of each. Four rules follow. The query lives in `UsageTableView` beside the sort and the detail toggle, for the measured reason #272 gives — the mutation clears its `data` while it reads, so anything kept inside `SpendTable` is thrown away by the press of Scan that re-asks the same question — and it is the **live** term there, debounced where it is spent (`useDebouncedValue`, 150 ms, the map's number) rather than lifted already settled, which would make every keystroke wait to appear in its own box. It is **not** in the URL, unlike the tickets list and the dashboard: a scan does not survive a reload, so a restored query would deserialize onto an empty page and describe rows that are not there. (Since #432 a reload opens on the stored reading rather than empty, which weakens that reason without retiring it — the page still opens empty with no history; putting the query in the URL has not been revisited.) The count is `countLabel(shown, total)` from the same module, in a **visible** line on the bar rather than in the frame's `aria-label` — `TableFrame`'s name is a landmark name, and rewriting it per keystroke would announce a new title as you type while still leaving a sighted developer counting rows. And a query that matches nothing renders its empty state _below_ the bar rather than instead of it, because the whole-block empty state above it (no issues at all) would take the box away with the rows and strand the query with nothing left to clear it from.
- **The Usage bar's three facet selects are the _vocabulary_, not an inventory of the rows on screen** (#274). Forecast band, verdict and started-versus-unstarted (`src/dev/UsageFilters.tsx`, predicates and — since #297 — the vocabulary beside them in `src/dev/usage-facets.ts`, as `USAGE_FACETS` / `USAGE_FACET_KEYS` / `UsageFacets`). Every band is offered including `XL` and every verdict including ones nothing currently lands in, which is what makes "narrow to a band and find the table empty" an answer a developer can ask for — derived from the rows instead, a facet could never produce the empty state at all and the question with the answer "none" would be the one question the bar cannot put. They are `&&`'d with `matchesQuery` in one pass, so "they compose" holds by construction and `countLabel(shown, total)` describes all four controls without any of them reporting itself. Four things follow. The `any` row needs a **non-empty** token (`ANY_FACET`): Radix reserves `""` for _cleared_ and throws on a `SelectItem` whose value is it, which `ProjectMapPage`'s workspace select learned first. A row carrying no value for a facet — no band, no verdict — is in **none** of that facet's results rather than in a default one, and `started` asks `spend !== null` rather than `out > 0`, because `bucketFor(0)` is `S` and a row that really spent zero is a measurement: the page's central distinction, told in a filter instead of in a cell. The state rides in `UsageTableView` with the sort, the detail toggle and the query, for the measured reason #272 gives. And `USAGE_NO_MATCH` was reworded to name _these filters_ rather than the search, because any of the four can empty the table on its own and sending a developer to clear a term that was never there is worse than saying nothing.
  - **The over-budget fixture row moves the chart figures.** `tests/e2e/fixtures/transcripts` held no over-budget row at all, so a verdict facet's only testable outcome was "matches nothing" — which a filter that did nothing would also produce. `#105` (90,000 output tokens against `forecast/S`) is what makes it testable, and adding a _third_ issue with recorded spend — a fourth row — moved `CHARTS.accuracy` from 1/1 to 1/2, p75 from 20,000 to 90,000 and the measured count from two to three, all of which are #252's assertions. An over-budget row **cannot** be small — `over` against the smallest band means at least 60,000 — so it also leads the default ranking and every positional row assertion in `dev-usage.spec.ts` moved with it; those that are not about the order now address a row by its issue number (`rowFor`). The arithmetic lives in that directory's `README.md`, and the fixture, the README and the constants are one commit so no intermediate commit is red.
- **The narrowing is a module, and `SpendTable` renders the rows it is handed** (#287). `src/dev/usage-view.ts` — pure — owns `UsageTableView`, `DEFAULT_USAGE_TABLE_VIEW`, `visibleRows(issues, view)` and `withDetail(view, next)`, absorbing the `matchesQuery`/`matchesFacets` `&&`, the `sortIssues` call over what they left, and the set of sort keys that only exist while the detail columns are shown. The three modules under it each answer about _one_ thing (`usage-sort.ts` an ordering, `usage-facets.ts` a predicate, `module-match.ts` a substring) and none of them can say whether the four controls narrow the **same** list in the order that keeps the ranking honest — which is exactly where a filter goes wrong: two passes instead of one `&&`, or a sort applied before the narrowing rather than after it. `usage-view.test.ts` asks that directly, importing no component. **The test split is the one to copy for the next table** (#288, which took `UsagePage.test.tsx` from 1,726 lines to 901): what a narrowing shows is `usage-view.test.ts`'s, over made-up rows; the four claims that need a render but not a page — the `aria-sort` vocabulary, the search debounce, the detail toggle calling `withDetail`, the selects' resting labels — are `SpendTable.test.tsx`, mounted with bare RTL `render` and a `useState` standing in for the page; and a control reaching a real reading of real transcripts stays `dev-usage.spec.ts`'s, untouched. Three things #287 deliberately did **not** change. The state still lives on `UsagePage`, which is #272's measured decision — these are pure functions _over_ a view, not a hook, and that is what lets the page hold it. `DETAIL_SORT_KEYS` is now `USAGE_DETAIL satisfies readonly UsageSortKey[]` rather than a map through `COLUMNS[name].sort`: the same compile-time claim that every detail column is rankable, said where a `.tsx` import is not available. And `SpendTable` keeps the debounce, because the settled term is substituted on its way into `visibleRows` — the memo rebuilds the three fields field by field rather than spreading `view`, or every keystroke re-filters and the 150 ms buys nothing. `visibleRows` takes `Pick<UsageTableView, "sort" | "query" | "facets">` and **not** the whole view, which is a claim rather than a tidy signature: the detail toggle changes which columns are drawn and never which rows, so naming it would put `detail` in that dependency list and re-filter every row on a press that changed nothing — the one case where the toggle does move the rows is the sort reset, and that arrives as a changed `sort`.
- **The Usage table is `src/dev/SpendTable.tsx`, and its column order is `USAGE_COLUMNS` in `src/dev/usage-copy.ts`, not the literal beside the definitions.** The same rule as `ROUTE` in [frontend.md](frontend.md) and for the same reason: `UsagePage.test.tsx` and `dev-usage.spec.ts` both index a row by position, neither can import a `.tsx` module, and a column inserted in the middle would leave every assertion silently checking its neighbour. `SpendColumns.tsx` keys its column definitions by those names and walks `USAGE_SPINE` or `USAGE_COLUMNS` depending on the toggle above it, so a name in either half without a definition — or a definition without a name — does not compile. The toggle's accessible name is in the contract too (`USAGE_DETAIL_LABEL`), for the reason the mark names are: neither suite can import a `.tsx` module, so a retyped label would leave both querying a control that no longer exists. `UsagePage.tsx` keeps what describes a _reading_ (`Gathered`, `Stored`, `Unattributed`, the scan mutation and `useStoredUsage`) and `SpendTable.tsx` holds everything that renders an issue, in four modules: `SpendCells.tsx` (the absence markers, the bands, the comparison cell), `SpendColumns.tsx` (the column record and its sortable header), `SpendTableBar.tsx` (the search box, the facets, the count and the toggle), and `SpendTable.tsx` itself (the debounce, `visibleRows`, the empty states and the markup).
  - **The forecast band, the band the spend landed in and the verdict are one cell** (`comparison`), reading `M 60-150k → S <60k` and then the word. `out` still stands alone — it is the figure the page exists for. The merge is what the two markers in the next bullet now have to survive: they sit an inch apart inside one cell, and `Comparison`'s half order (forecast, arrow, landed, verdict) is what says which absence a dash is. That order is held by two hover tests rather than by the compiler, unlike the columns around it — a reason to be careful about adding anything else to the cell.
- **Anything `gh` could not supply renders as an em dash meaning _unknown_, and a row with no `forecast/S|M|L` label gets no verdict.** Not "on target", not a default band: a verdict on work nobody estimated is a score the page invented, and it would move the accuracy figure the page exists to report. The one thing that crosses the divide is the band the spend _landed_ in — the right-hand half of the comparison cell, derived from the actual alone, so it survives a `gh` that does not while the forecast half beside it goes to a marker.
- **The row set is every issue with spend _plus_ every issue the listing calls open** (#251), so an issue nobody has started appears with its band, an empty actual and no verdict — and the forecast-coverage gap the PRD's second metric is about is a row you can see rather than an absence you have to know to look for. Open is the line: a _closed_ issue with no recorded spend was finished somewhere the scan cannot reach (another machine, or before these transcripts began), and a row for it would report the limits of the scan as a fact about the work. Two rules follow. `IssueSpend` is one nullable object on the wire rather than four nullable numbers, because the four figures are absent exactly together and a flat shape lets a row carry turns with no tokens; and nothing anywhere substitutes a zero for it — `bucketFor(0)` is `S`, so a forecast of `L` read against a zeroed row prints "under", and every unstarted issue in the backlog would sit in the table claiming to have beaten its estimate while dragging the percentiles and the accuracy figure with it. `bun run tokens` keeps those rows out of both. The page tells the two absences apart with `NotStarted` beside `Unknown` — the same em dash, different words on hover, because one means the question could not be asked and the other means the answer is _nothing yet_.
  - **That rule is one predicate, `hasRecordedSpend` in `src/dev/usage-readings.ts`, and everything the page renders reads it** (#285). It had been written out six times with nothing holding the copies in step. It is a **type guard** (`row is IssueUsage & { spend: IssueSpend }`), so a caller that asks the question and then reads a figure off the _same_ row does it without a `?.` or a `!` standing beside the check as a second, unverified copy of it. Read that narrowly: it is not a rule that every `?.` on `spend` is now a defect, and `figureOf` in `usage-sort.ts` keeps one on purpose (see the end of the next sub-bullet). It asks `spend !== null` and never `out > 0`: a row that really recorded zero is a measurement and ranks, bands and scores like any other figure.
    - **It is not the ranking's sink value, and collapsing the two changes the sort.** `hasRecordedSpend` answers "is there spend"; a _number_ an absent row sorts at is a different question with a different answer type, and ranking by the predicate itself would make every started row compare equal and lose the output-token order the page opens on. No sink value exists in the repo (#286): `sortIssues` asks the predicate of two rows directly, before it reads any figure, so a reintroduced sink value is a second ordering rather than a helper. The two derived fields in `joinIssues` (`bucket`, `verdict`) still branch on the local `spend` rather than the predicate, and that is not a copy of the rule — the row does not exist yet to ask about. `figure` in `scripts/issue-tokens.ts`, the terminal's em-dash cell, asks the predicate too (#290), so this is the _repo's_ one home for the rule — and the `?.` in `figureOf` (`usage-sort.ts`) is not a copy at all, but the live branch that orders the sunk block, which reverses with the header under the issue column and compares equal under a figure column.
- **Work on `main` is reported, as its own total and never as a row** (#253). Turns that ran on `main` or with no branch recorded belong to no issue and are a large share of everything a machine has done — 28% of all turns when the scan was written — so a page listing only issues reads as complete while omitting a quarter of the work. The scan used to count those turns and throw their output tokens away, which is why this was a change to what the scan accumulates (`apps/web/dev/usage.ts` then, `dev/transcripts.ts` since #297) and not only to what its two callers print; `UnattributedWork` on the wire carries **turns and output tokens, and deliberately not the other two** — `sessions` and `cacheRead` are questions about an issue, and a field on the wire is a promise that something reads it. A row is the obvious place for the total and the one place it cannot go: it has no issue number, nothing forecast it, and `bucketFor` would file its tokens in a band as though somebody had — which the distribution chart would then count and the accuracy figure would score. **A zero is rendered here where a row's figure would be an em dash**, and that does not contradict the "never substitute a zero" rule above — it is the other side of it. A row's figures are dashed because `bucketFor(0)` is `S`, so a zero there gets banded, scored and counted in the quartiles; nothing scores these two, so there is no score for a zero to invent, and a panel that vanished on one would read as the page not asking. (The plain counts elsewhere on the page — transcripts read, issues listed, issues with recorded spend — were never in that rule either.) A third case is neither attributed nor unattributed and must stay that way: a branch whose name carries no issue number is dropped, because `unattributed` means `main` or nothing at all.
- **A scan's warnings say which source failed, and the sources stack** (#289). `UsageReport.warnings` is `UsageWarning[]` — `{ source, message }` over `USAGE_WARNING_SOURCE` (`transcripts` | `listing`, and `history` since #420). The scan has two independent failure modes: the transcript directory can be unreadable while `gh` answers perfectly, and the reverse, so a machine with neither gets **two** warnings and does not have to discover the second after fixing the first. Neither throws — a missing directory is the ordinary state of a fresh clone and of CI, and an unavailable listing costs three columns, not the page. Branching on the prose instead would be a contract nobody declared, which every re-wording breaks, and would leave `bun run tokens`, which words its diagnostics its own way, nothing to branch on. **One value per source, not per way to fail**: "could not read the directory" and "the directory holds no transcripts" are one source failing in two ways and nothing on either surface treats them differently, so a value for each would be a distinction with no reader. The page renders `message` and branches on nothing (since #420 `source` reaches the DOM only as a `data-` attribute the E2E reads). The "no `.jsonl` transcripts" warning sits inside the same `try` as the read it is about, never behind `warnings.length === 0`, which says "the directory read cleanly" only while the transcripts are the first source to report.
  - **Since #420 there is a third value, `history`, and it is a third _source_ rather than a third way to fail** — the usage history is a different file from the transcripts, fails on its own, and carries its own advice. A history that cannot be opened or read costs that warning and nothing else: `gatherUsage` closes it, re-reads the transcripts whole with no store (the cursors that would have skipped bytes live in the file that failed), and reports those figures with `historySince` null and no trend. Only the store's own calls count — each goes through `fromHistory`, which marks what it throws as a `HistoryFailure` — so a bug in the tally or the trend arithmetic still throws rather than reading as a damaged history and sending the developer to delete it. **Nothing replaces the file** — a damaged history fails on its first statement, before any write, and may hold the spend of transcripts Claude Code already pruned — so the warning names the file and says to scan again and then move it aside or delete it. "Scan again" is there because a file another scan holds fails the same way; the store sets a five-second `busy_timeout` so the dev server and `bun run tokens` scanning at once wait rather than fail. `openUsageStore` closes the handle it opened when the schema's first statement fails, or the file would stay locked on Windows and the developer could not do what the warning says. A _deleted_ history is not a warning at all: the next scan creates a fresh one from what is on disk and the start date moves with it. The E2E tells the history's warning from the other two by `data-usage-warning`, the one place the page puts `source` in the DOM.
  - The project map's `warnings` next door is still `string[]` (`map-protocol.ts`), and that is not an oversight to tidy: its scan has a dozen failure modes rather than two, every one of them a line of source it could not parse, and nothing branches on which. A source tag there would be a field on the wire that nothing reads.
- **`bun run tokens` and the Usage page call the same function, and the terminal still sounds like a terminal** (#290). `gatherUsage(dir, meta, historyFile)` is the one entry point both have (a fourth argument, `now`, is the clock tests pass since #419, and a fifth, `{ pushedHistory }`, is the plugin's alone since #428): the script formats the report it returns — rows, unattributed total, warnings — and takes only `gatherUsage` from `apps/web/dev/usage.ts`, plus `resolveTranscriptDir` and `TRANSCRIPT_DIR_ENV` (for the diagnostic below) from `dev/transcripts.ts`, and `resolveHistoryFile` from `dev/usage-store.ts`, so it tallies over the same history the page does. Since #428 `--push` adds `buildPush` and `pushRequest` from `dev/usage-push.ts` and `UsagePushResult` from the push's wire, and its `fetch` is the one network call the script makes itself. It imports the contract modules directly, as every browser-side reader does, and `dev/usage.ts` exports three functions (`gatherUsage`, `verdictFor`, `readStoredUsage`); `joinIssues` and `emptyRead` stay private. The unattributed total is on the wire and each warning carries a `source` (#253, #289), so the terminal words its own sentence for a source without matching the prose of the one it was handed. It does that for `transcripts`; since #420 it passes `history`'s message through with a sentence of its own naming `USAGE_HISTORY_FILE` appended, since the message already names the file, the cause and the remedy; and it passes `listing`'s message through, since that sentence is `fetchIssueMetadata`'s own account of what it could not read and already says what it costs. **The terminal has one transcript sentence, and it branches on the variable, not the failure**: unreadable and empty take the same advice. What does change the advice is whether `CLAUDE_TRANSCRIPT_DIR` is set, because with it set the working directory is never consulted and "run this from the repo root" would send the developer to fix something the run did not read; so the sentence names the variable instead. The directory in it comes off `report.transcriptDir` rather than off the local `dir`, which is what keeps the sentence describing the reading it was handed.
  - **The transcripts' diagnostic is covered by nothing, and that is a gap rather than a decision.** The guardrail captures **stdout only**, and both its runs use healthy fixtures, so both branches of the sentence above are verified by hand and by nothing else. The history's sentence is the exception since #420: `dev-usage-history.spec.ts` reads `bun run tokens`' stderr over a damaged history and asserts it names the file and the variable — the set-variable branch only, since the E2E always sets it. There is no home for a unit test: `scripts/` has no runner pointed at it — Vitest is scoped to `apps/web` and `bun test` to `apps/api`, `packages/shared` and `tools/repo-scan`, none of which reaches `scripts/` — which is also why `bun run tokens` had no test of any kind before #283. Giving `scripts/` a runner is a bigger decision than this slice; until then, change either sentence by hand and check it by hand.
  - **The issue's `state` stays off the wire, and `--open` keeps its lookup.** `state` earns no place on `IssueUsage`. #253's rule is that a field on the wire is a promise something reads it, and the only reader would be that one filter — the page has no column for it and never will, since the row set already implies it (an issue with no spend earns a row _only_ because the listing called it open). The lookup is not the re-join it looks like: the script holds the listing because it **passes** it to `gatherUsage`, so filtering is one `Map.get` against a map already in hand. That is also why the script fetches the metadata itself rather than letting `gatherUsage` default it — same single `gh` call, one caller holding the result.
