# Checks

What runs before code lands — Prettier, the two git hooks, lint, and what CI re-runs — and what each one costs. The code rules those checks enforce are in [conventions.md](conventions.md) and the area files; the standards guards and `doc-citations` that run inside the hooks are described here.

## Formatting and git hooks

**Prettier owns formatting; nobody hand-formats and nobody argues about it.** `bun run format` writes, `bun run format:check` reports. The config is `.prettierrc` and it is one line, because the defaults are what this codebase already was — measured, not assumed: at Prettier's default 80 columns a whole-repo run rewrote 176 source files, at 100 it rewrote 245, and only 2,497 of 68,204 lines exceeded 80 to begin with.

- **The one override is `endOfLine: "auto"`, and it is load-bearing on Windows.** This repo is developed with `core.autocrlf=true`, so the working tree is CRLF while the object store is LF. Prettier's default `"lf"` compares against the file on disk, so every file would report as unformatted forever on a fresh Windows checkout — and CI, which checks out LF, would disagree with the developer's machine about a repo neither had touched. `"auto"` takes each file's existing endings, which is LF on CI and CRLF here, and both are right.
- **`.husky/*` is pinned to LF in `.gitattributes`, and that is the exception to the above.** Hooks are executed by `sh`; checked out with CRLF, `sh` reads the stray `\r` as part of the last argument on every line. Nothing else in the tree is pinned — a repo-wide `eol=lf` would rewrite every working copy on the next checkout for no gain.
- **Every tracked text file is UTF-8 with no byte-order mark, and `apps/api/src/standards-guard.test.ts` fails one that is not**, naming the file and line. Windows PowerShell 5.1 damages files three ways: `Out-File` and `Set-Content` write a byte-order mark; `Get-Content` without `-Encoding utf8` reads a file that has none as Windows-1252, so writing it back turns each `—` into three characters beginning `â`; and bytes that were never UTF-8 decode as the replacement character. Prettier passes all three. Review caught one of them six times before this rule (`29c3b98`, `d20153e`, `e2da7b1`, `037ff02`, `198e831`, `b85bc6a`) and missed two: `apps/api/src/jobs/auto-reply-ticket.ts` reached `develop` with 41 mangled dashes from one review-fix commit (`4927a82`), and `apps/web/src/pages/UsersTable.tsx` with a mark. Write files with the Write and Edit tools, or with `[IO.File]::WriteAllText` and a `UTF8Encoding($false)`, never `Out-File` or `Set-Content`. The rule reads every tracked text file, comments included, and runs on pre-push.
- **`.claude/` and `.agents/` are in `.prettierignore`.** Most of those skills are vendored from upstream repos and pinned by content hash in `skills-lock.json`; reformatting one changes its hash and puts this repo permanently out of sync with its source. The repo-authored skills sit in the same trees, so both are excluded whole rather than by a per-skill list that would rot. **One vendored skill is patched on purpose:** `.claude/skills/migrate-radix-to-base/SKILL.md` carries `disable-model-invocation: true` and a one-line description (#306), so its long description stays out of every session while the app is on `radix-ui`. The pinned copy in `.agents/skills/` is untouched, so the hash still matches; re-apply the patch after any skills update overwrites the `.claude/` copy.

**Two hooks, split by what they cost.** Husky installs them from `.husky/`; `bun install` runs the `prepare` script that wires `core.hooksPath`, so a fresh clone needs no extra step. (Husky exits 0 when there is no `.git` — which is what the Dockerfiles' `bun install --frozen-lockfile` hits, since `.dockerignore` excludes `.git`.)

- **`pre-commit` — `lint-staged` then `bun run typecheck`, ~20s.** lint-staged runs Prettier over the _staged_ files and re-stages what it rewrites, so what lands is already formatted. The pattern in `.lintstagedrc` is a bare `*` with `--ignore-unknown`, so `.sql` migrations, `schema.prisma` and the `.png` fixtures pass through instead of erroring for want of a parser. **Since #553 `typecheck` also runs `tsc -p tsconfig.json` over the root project**, `playwright.config.ts` and `tests/**`, which no workspace config reads: until then an error only that project reports reached `develop` unreported, a TS5097 on `apps/web/src/dev/usage-readings.ts`, which the specs reach transitively and so check under the root's options. It adds ~1.6s to the workspaces' ~16.6s, measured 2026-10-20 on a Windows dev machine, warm.
- **`pre-push` — `bun run typecheck` then the `@ticket/api` suite, under a minute warm.** The API suite plus a typecheck the commit hook may never have run (a `--no-verify`, another tool's commit, a rebase); measured 2026-09-24 on a Windows dev machine, warm, at typecheck ~16s and `@ticket/api` ~33s. **The suite includes `apps/api/src/doc-citations.test.ts` since #439**, so a rename that leaves a backticked path in `docs/standards/` naming no tracked file fails the push, with the document, the line and the path; a citation that is deliberately not a file is exempted in that test's table with a reason, never by marking the prose. Its cost, measured 2026-10-08 on the same machine, warm, as the mean of four alternating runs each: the API suite took 38.1s without it and 40.3s with it, so it adds ~2.2s, about 4.5% of the hook's ~49s. The rise from 2026-09-24's ~33s to 38.1s is the suite's own growth, not this check. **Since #440 it reads `docs/adr/` too, and checks code symbols**: a backticked camelCase, PascalCase-compound or underscored name that no tracked source, test or config file says outside a comment fails the same way, so a rename that leaves the old name behind in a comment is still caught. A symbol exemption is history or a library or tool name, and says which; `doc-citations.ts` records the measurement the rule was chosen on. Building its symbol index over 564 files adds ~0.45s, measured the same day and machine, warm. **Since #441 it also reads every `CLAUDE.md` and every markdown file under `.claude/skills/` and `.claude/agents/`**, so a skill or agent that names a script, path or symbol that has moved fails the push too. A skill is read unless `EXCLUDED_SKILLS` in `doc-citations.ts` names it: three library skills are, because they describe a library's API rather than this repo, and a name there that is no longer a skill directory fails the check. `.agents/` is never read, since a fix there would break `skills-lock.json`'s hash. Widening the walk from 33 documents to 59 cost nothing measurable: the test file took ~3.1s before and after, the mean of four warm alternating runs each, measured 2026-10-08 on the same machine. **Since #442 it reads every PRD under `docs/prd/` whose header does not say `Status: Shipped`**, so an open PRD fails on a stale citation like a standard does, while a shipped one is history and is not read. The `implement` skill writes `Shipped` in the PR that closes a PRD's last ticket, and drops that PRD's exemptions with it. Plans under `docs/plans/` are never read: they name the `new:` modules they propose, so every plan would fail the day it was written. Reading the 13 PRDs' headers and checking the 2 open ones cost nothing measurable: the test file took ~3.0s before and after, the mean of four warm alternating runs each, measured 2026-10-08 on the same machine. **Since #443 a failure names the rename** when git history shows one, as `OLD → New (<sha>)` after the line, so the fix is a one-line edit. The lookup in `doc-citations.ts` asks history only about a citation that has already failed, so a green push reads none of it, and a failing one pays ~0.7s once for its paths and ~2s for each stale symbol. CI's API job checks out shallow, so there the hint is absent and the failure fires as before; nothing deepens the checkout for a hint. The cases that prove it build their own temporary git repository, a rename and a shallow clone of it, which took the test file from ~3.1s to ~5.4s, each the mean of four warm runs, measured 2026-10-08 on the same machine; #442's ~3.0s and this ~3.1s are the same file, apart by run-to-run noise. The cost is the git processes those cases start, each ~60ms or more on Windows: 25 when measured, 22 since #614 made three git mv calls plain renames. Under memory pressure they ran past bun's 5s default and blocked a push, so since #614 the setup hook and each case that starts git carry a 30s timeout of their own. **Since #531 every git call the check makes runs without the variables that name a repository**: git sets `GIT_DIR` for a hook, and pushed from a linked worktree it pointed every call at the worktree, so those cases built their scratch repositories inside it, committing to the branch and setting `core.bare = true` in the shared config. The case that proves it starts one more `git init` and a child `bun` that runs one `git ls-files`; the test file took ~5.6s before and ~5.9s after, the mean of four warm runs each, measured 2026-10-15 on the same machine. **Since #545 the suite's `apps/api/src/standards-guard.test.ts` also reads the raw text of both apps** for a typed product name ([copy.md](copy.md)): walking and reading 533 files took that test file from ~2.2s to ~2.7s, the mean of eight warm alternating runs each, measured 2026-10-15 on the same machine. Since #568 it reads `packages/` (all but `packages/shared`) and `scripts/` too, 583 tracked files, a measurement not retaken. **Since #566 the suite's `apps/api/src/git-spawn-env.test.ts` fails any `git` or `gh` spawn under `apps/` or `scripts/` whose environment does not come from `repositoryFreeEnv`** ([dev-tools.md](dev-tools.md) has why), reading the files git tracks there with their comments blanked: the file takes ~2.7s on its own, the mean of four warm runs, measured 2026-10-21 on the same machine. **Since #444 `bun run graph <file>` asks the reverse question before an edit**: which documents and lines cite the file, by path or by a name it exports, plus its importers and imports from the project map's scan; given a document, what it cites and whether each resolves. It reads plans too, which the check does not, and reports rather than fails. **The web suite is in neither hook.** It is jsdom-bound and cost ~4m54s of every push on Windows; CI runs it on every PR, and CLAUDE.md makes a green PR the finish line, so CI owns it. Run `bun run test` by hand when a change is mostly web and you want the answer before CI does. E2E is in neither hook either: it needs Postgres, a migrated `ticket_manager_test` and two servers on alt ports (`SCRIPTS.md`), and CI's `e2e` job owns it.
- **CI re-runs `format:check` anyway** (`.github/workflows/ci.yml`), for the same reason it re-runs typecheck: lint-staged only ever sees staged files, so a `--no-verify` or a merge would otherwise carry unformatted code to `main` unnoticed. A hook is a fast local loop, not a gate.

The whole-repo reformat is one commit, listed in `.git-blame-ignore-revs`. GitHub's blame view reads that file automatically; locally it is `git config blame.ignoreRevsFile .git-blame-ignore-revs`, once per clone.

## Lint

**`bun run lint` is type-aware ESLint over both apps and both packages, and it runs two rules in all four: `@typescript-eslint/no-floating-promises` and `@typescript-eslint/no-misused-promises`, both errors** (#534). It reads `apps/api` (the seed scripts and `prisma.config.ts` included, under the API's own compiler options), `packages/core`, `packages/shared` and, since #535, `apps/web`, which also gets the two React hooks rules ([frontend.md](frontend.md) has those and how the web app satisfies the promise rules); never the generated Prisma client or the web app's build output. A missing `await` on a Prisma call, an outbox write or a pg-boss `send` compiles cleanly, drops its error or lets a transaction close before the write lands, and most tests pass anyway; typecheck cannot see it and this can. No other rule set is switched on: a new rule is its own ticket, with its own sweep of the violations it finds.

- **CI only, in the `check` job after typecheck, and in neither hook.** Pre-commit is the fast gate and pre-push already costs under a minute; this is the slow kind, because every file is checked against a full type program. Measured 2026-10-15 over the backend alone, warm, each the mean of three runs: ~39s on a Windows dev machine, and ~14s for the step on CI's `ubuntu-latest` (12s, 14s and 15s, runs 38752817177, 38754676601 and 38752602677 of #534's PR; two of them were the scratch commit's red runs, which type the same program). **Re-measured 2026-10-21 with `apps/web` included** (#535), warm, the mean of three alternating runs each on a Windows dev machine: ~31.6s over the backend alone and ~67.0s over all four, so the web app roughly doubles it. On CI's `ubuntu-latest` the step took 27s and 29s, runs 39509338167 and 39509698558 of #535's PR (the first the scratch commit's red run, which types the same program), against ~14s over the backend alone. Run it by hand before pushing a change you want the answer to early.
- **The project service finds a file only through a tsconfig that names it**, so a file reached solely by import is a parsing error: `apps/web/csp.ts`, which `vite.config.ts` imports, is in `tsconfig.node.json`'s `include` for that reason (#535).
- **The config is `tools/lint/eslint.config.js`, in a workspace of its own, because typescript-eslint cannot run on TypeScript 7.** It drives the classic compiler API, which 7 no longer ships, and its peer range stops below 6.1. `tools/lint` pins `typescript@6.0.3` beside `eslint` and `typescript-eslint`, and Bun's isolated linker resolves the peer against that package alone, so every other workspace still compiles with 7. Its `lint` script moves to the repository root before starting ESLint, since ESLint ignores any file outside the directory it runs from. Being a workspace, its `package.json` is one more manifest each Dockerfile copies before `bun install --frozen-lockfile` ([deployment.md](deployment.md)).
- **What made the gate pass on day one: 22 `mock.module(...)` calls left floating, all in API tests and their shared stubs.** Bun types it `void | Promise<void>`, the promise being what an async factory returns when the module is already loaded. Each one now reads `await mock.module(...)`: correct if a factory ever goes async, and a no-op for the synchronous ones in use today. The suite stayed green in both file orders.
- **Exempt one line at a time, with the reason in the comment**: `// eslint-disable-next-line @typescript-eslint/no-floating-promises -- <why this promise may float>`. Never a file-level `eslint-disable`, never a rule turned off in the config. A deliberate fire-and-forget usually needs no exemption: the rule accepts `promise.catch(handler)`, and `void promise` where a rejection genuinely cannot matter. An exemption that no longer suppresses anything fails the run (`reportUnusedDisableDirectives`), so a fixed line cannot keep a stale comment.
