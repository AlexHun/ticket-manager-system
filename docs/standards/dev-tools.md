# Dev tools standards (`/__dev`)

The dev-only tools at `/__dev` are never in a production build. Railway's `develop` environment runs the dev server itself, behind HTTP Basic Auth (the #314 bullet below). The Usage page's own standards are [dev-tools-usage.md](dev-tools-usage.md). Four pages: `/__dev/map` is a project map — module graph, imports, layers, client routes, API endpoints with their guards, the Prisma models, and which client module calls which endpoint; `/__dev/tests` runs the repo's suites from the browser with streamed output; `/__dev/usage` reports what each GitHub issue was forecast to cost and what it actually cost in output tokens, read off this machine's Claude Code transcripts and one `gh issue list` call; `/__dev/sessions` (#590) draws this machine's sessions of this repository from the same transcripts, each with every subagent it started nested under it. All four are also linked from the sidebar's "Dev" group.

## Sessions (`/__dev/sessions`)

- **The Sessions tree hangs on one link: the `toolUseId` in a subagent's `agent-<id>.meta.json`, the id of the `tool_use` call that started it** (`dev/sessions.ts`). A subagent goes under whichever card's transcript made that call, at any depth; the meta file's `spawnDepth` and `parentAgentId` are not read. Measured 2026-10-21 over this machine's 206 sessions: 732 cards, three deep, and every `toolUseId` found its call. One meta file had no `toolUseId` at all, a skill forked into a subagent, and it is drawn under its session. The layout is undocumented, so a file the reading cannot use is a warning naming it and never an empty page: an unparseable meta file costs its own card, and a call no transcript made puts the subagent under its session. Its own reader rather than `readTranscripts`, which keeps no file on a response and whose six fields are the history's stored row (ADR-0023); the count is the same rule, each response once at its largest count. The words on the page are the PRD's R12 (_session_, _subagent_, _state_, _step_, never the desk's _agent_, _run_, _status_, _stage_ or _handoff_), and `dev-sessions.spec.ts` checks the rendered text for the banned five. A reading of those 206 sessions (605 MB, 732 transcripts) took 5.6-10.4s warm and ~24s with a cold disk cache, against ~5.6s warm for `readTranscripts` over the same directory, which is why #591 gave the reader cursors (the next bullet).
- **The page follows the transcripts live, by polling, and only while a page is open** (#591). `DEVTOOLS_API.sessions` is a server-sent-event stream in the test runner's shape, and `dev/sessions-stream.ts` reads every `SESSIONS_POLL_MS` (2s) while at least one page listens, sends a reading only when it differs from the last (its clock aside), and stops and forgets the last reading when the last page leaves, so a page opened later is never handed a stale one. It polls one `createSessionsReader` the plugin holds for the dev server's life, which keeps a cursor per transcript the way the Usage scan's do (#418): a file whose size and modification time are unchanged is not opened, a grown one is read from past its last newline, and one that no longer holds the 64 bytes the cursor sits behind is read from the top. Measured 2026-10-21 on Windows over the same 206 sessions, which had grown to 735 transcripts since #590's reading earlier that day: 15-20s for the first reading, then 457-972ms each, so a change reaches the page in about 3s, inside R4's 5. A file watcher was not needed and could not have replaced the clock: Stopped is a session going _quiet_, which no file event announces. **Stopped** is a card that is not Done whose files have gone unwritten for `SESSION_IDLE_MS` (15 minutes, in `src/dev/sessions-protocol.ts` with the measurement it came from) and that has nothing Running under it; a quiet parent waiting on a Running subagent stays Running. Its age is the files' modification time, never the records' timestamps, so `tests/e2e/fixtures/transcript-fixture.ts` stamps the working copy with the current time after copying it — on Windows `cpSync` keeps the source's, and every card would otherwise read Stopped — and `dev-sessions.spec.ts` reaches Stopped by setting a file's time back past the idle time rather than by waiting it out.
- **Waiting for you comes from a hook, not the transcripts, which never record a wait** (#592). `.claude/hooks/record-waiting.mjs`, registered in the committed `.claude/settings.json`, writes `<session>.json` or `<session>.<agent>.json` holding `{ sessionId, agentId }` when a wait starts and removes it when the wait ends. A permission prompt whose notification names no subagent is `<session>@prompt.json` instead, and, like any wait that names no subagent, it ends only on the session's own `PostToolUse`, `PostToolUseFailure`, `UserPromptSubmit`, `Stop` or `SessionEnd`. **A subagent's event never ends the session's wait**: in a `/chain` a background worker's next call would otherwise clear the conductor's prompt. A `SubagentStop` that names no subagent ends nothing. If such a prompt was in fact a foreground subagent's, its session's card reads Waiting for you until that subagent ends and the call that ran it returns; a background subagent cannot ask. `dev/waiting.ts` reads them on every reading, and the card a record names reads Waiting for you. A record that names no subagent, or one the session has no card for, marks its session. **The start events are a `permission_prompt` notification and an `AskUserQuestion` call, never the PermissionRequest event.** That one also fires in a background subagent that cannot ask anyone and is denied at once, so it would mark a wait that never happened. A wait ends on the card's next `PostToolUse` or `PostToolUseFailure`, the session's `UserPromptSubmit` or `Stop`, the subagent's `SubagentStop`, or `SessionEnd`, which clears the whole session; each ends only the wait of the card it names. The hooks reference names no event for a dialog the developer denies, so a denial clears on whichever of those comes next. The spike is the comment on #592, and `apps/api/src/record-waiting-hook.test.ts` runs the hook on the reference's own example payloads: the auto-mode classifier refused recording live ones. Waiting for you outranks Stopped, since a prompt can be held for an hour, and like Running it keeps the cards above it from reading Stopped or Done. A Done card stays Done whatever a leftover record says. The hook fires on every tool call in every clone, so it prints nothing (some events' output becomes the session's context), exits 0 whatever happens, renames each record into place, and refuses an id that is not a plain name. **`CLAUDE_WAITING_DIR` is the fourth seam**, beside the three [dev-tools-usage.md](dev-tools-usage.md) names (`CLAUDE_TRANSCRIPT_DIR`, `GH_ISSUES_FILE` and `USAGE_HISTORY_FILE`): unset, the records go to `~/.claude-sessions-waiting`, and `playwright.config.ts` points the E2E at `WAITING_WORKING_DIR`, a gitignored directory beside the fixtures that `resetTranscriptWorkingCopy` removes with the transcripts' working copy.
- **The Sessions page's figures are the Usage page's, grouped by the branch each response ran on, not by session** (#593). Measured 2026-10-21 over this machine's 206 sessions: 162 ran on more than one branch, and one `/chain` conductor's own records covered seven issue branches and `develop`, so a session filed under one branch would carry the others' spend into the wrong issue. Each card keeps the responses its own transcript holds, keyed by the Usage scan's `identityOf` and folded at the largest count, and `groupSessions` (`dev/session-groups.ts`) credits each once and groups them: one group per issue, one for `BASE_BRANCHES` (`develop`, where a conductor runs, and `main`), counted toward no issue, and one for a branch naming no issue or none. An issue group's total is `tallySpend` over those same responses, the one join the Usage page and `bun run tokens` use (R7), and `dev-sessions.spec.ts` reads `#101` off both pages in one run and compares them. **Which card a response is in is which card's list holds it, never a seventh field on `TranscriptResponse`**, whose six are the stored row and the push's wire (ADR-0023). A session is in every group its responses ran on, with its share of each, and in the group of its latest record's branch even before it has spent anything there; a group carries `SessionSlice`s naming cards by id, so a card's facts and state are sent once and a Waiting for you is counted once however many groups show it. A response in two files would be credited to the first card read; over 744 transcripts the same day, none was. A subagent transcript with no usable meta file draws no card, but the Usage scan counts every `.jsonl` under `subagents/`, so its responses are its session's. Two limits are by construction. **The figures agree while the transcripts are on disk**: the Usage page totals the usage history, which keeps a response after Claude Code deletes its transcript at 30 days, and this page reads only the files, so an older issue reads lower here. And the `develop` and `main` group is its own figure, matching nothing on the Usage page, whose unattributed total is `main` and branchless work and which drops `develop`.
- **A running `/chain` lists its issues in the order it works them, read from the conductor's transcript and one `gh issue list`** (#594, R8). A session whose prompt ran `/chain` (Claude Code records it as `<command-name>/chain</command-name>` with its `<command-args>`, not always as the first prompt: a conductor can open on a `/clear`; read by `commandOf`, so only off a prompt that opens on those tags, #682) and that reads Running or Waiting for you gets a chain view above the groups (`src/dev/SessionChains.tsx`). Its workers are the conductor's `Agent` calls whose prompt opens as `chain` step 2 writes it ("You are Ember, on the team. Invoke the `implement` skill for issue #…"), each linked to its card by the call's id as the tree is. Its issues are `listChainIssues` in `dev/issues.ts`: `chain` step 1's call with `--state all` (a merged issue is a closed one), the plan's whole path quoted (`"docs/plans/<slug>.md" in:body`, as `implement` searches a PRD's) and `blockedBy`, through `gitEnv`. `chainView` in `dev/chains.ts` orders them as step 1 does, blockers in the chain first and ties by number, and marks each Merged (closed), In progress (open with a worker, the latest one named), Blocked (a blocker outside the chain still open), Next (the first other open issue whose blockers are all closed) or Waiting. **A finished or stopped chain gets no view**, so `gh` is never asked about every chain this machine has run (16 sessions' transcripts held a `/chain` on 2026-10-21), and **one listing per plan is kept for `CHAIN_LISTING_TTL_MS` (a minute)**, a failed one included, because the stream reads every 2 seconds and `gh` takes about 2 to answer. A chain given issue numbers rather than a plan (17 of the 20 `/chain` commands in this machine's transcripts on 2026-10-21) names nothing to search for, so it reads "the chain's order is unknown" with its workers listed, as does one whose listing failed. **`GH_CHAIN_ISSUES_FILE` is the fifth seam**: it holds what the call prints, is read on every reading rather than kept, and never falls back to `gh`, for `GH_ISSUES_FILE`'s reason; `dev-sessions.spec.ts` writes it and a conductor into the working copy for the chain tests alone (`tests/e2e/fixtures/gh-issues.ts`), so no other test's figures move.
- **A card running `implement` shows the step it has reached, and every card the tools it called** (#595, R9 and R10). The step is inferred from the card's own tool calls, so its rules are one pure module, `dev/implement-step.ts`, each step matched by the call `.claude/skills/implement/SKILL.md` tells the worker to make (`gh issue view`, `git switch`, the `coding-standards` skill, the `tdd` skill or an edit, the `Progress: built` comment, the `code-review` skill, `gh pr create`, `wait-checks.mjs` or `gh pr checks`), with a unit test per step over made-up calls. **An edit to that skill which changes a call is an edit to this module and its test**, or the page drifts; the test reads the skill's `Progress:` comments off the skill itself, so a reworded one fails there rather than on the page (#626). A step the skill gains has no step on the page unless R9 gives it one: step 7, looking at the page at real volume (#626), leaves a `Progress: looked` comment no rule matches, so a worker there reads Commit, the step before it. Commit is the comment, not a `git commit`, because step 4 commits every slice too. The card is on the furthest step it has made a call of since it last invoked `implement` (a `Skill` call, or a prompt that opens on `/implement`'s tags, read by `commandOf`, #682), and **a sequence with a gap reads Unknown, never the nearest guess** (the PRD's third risk) — a resumed worker that starts mid-way reads Unknown for that reason. A card that never invoked `implement` shows no step at all. `marksOf` turns each call into marks as the transcript is read, so the reader keeps the marks and a tally per tool name (`ToolTally`, in the order each was first called), never the calls' inputs, which can be whole files.
- **Each session's `Card` in a group's list is `content-visibility: auto`, and a fold is only cheap because of it** (#611). Without it, a fold of one card's subagents laid out and pre-painted every card on the page to move the ones below it. With this machine's 256 sessions (about 44k elements) each press blocked the main thread for 1.3s, and a run of presses held the page long enough to measure an INP of 70,784 ms. It was not React (5–10 ms of JS), the animations or the `:has()` rules. In a trace of a generated 26k-element page, both layouts of one fold covered 38,930 objects to change 14–17. With the property they cover ~1,600, layout went from 141 ms to 3 ms, and pre-paint from 238 ms to 10 ms. `contain-intrinsic-size: auto 15rem` is the placeholder height of a card not yet drawn; the `auto` keeps its real height once it has been. `dev-sessions.spec.ts` holds it by the objects each layout of a fold covers, read from a Chromium trace, a count rather than a time, so it does not pass or fail on the machine's speed. It sits on the `Card` and not on the `<li>` around it: the property's paint containment clips whatever its element's descendants draw outside it, and the card's border is a `ring-1`, a box-shadow just outside the card, which the `<li>` it fills exactly would cut off. The card is `overflow-hidden` already, so on the card it clips nothing new.
- **The page draws a reading a batch at a time, and the cost it cut was the browser's, not the reading's** (#618). Measured 2026-10-30 on this machine's 206 groups (1,230 cards, about 52k elements): a return visit's stream sent its first reading 0.7-0.95s after it opened, since the plugin's reader already keeps its cursors for the dev server's life, and the first card then came 14.7s later, 7.9s of it React and 6.3s style recalculation, both growing with the elements one commit draws. So keeping the last reading across visits would have saved under a second and is not done: the stream still forgets it when the last page leaves. `drawnGroups` in `src/dev/sessions-batches.ts`, unit-tested over made-up readings, cuts the groups to a budget of cards in the page's order, each session whole with its subagents, and a cut group keeps its total; `useDrawBudget` in `SessionsPage.tsx` starts it at `FIRST_BATCH_CARDS` (20) and adds `BATCH_CARDS` (100) a frame, with a `Skeleton` below the cards drawn so far until it covers them, `aria-busy` itself rather than the list above it, which would keep a screen reader from the cards already there. The first card then came 0.53-0.8s after the reading. Two rules hold it up. **`Group` and `CardBody` are memoised, and `drawnGroups` returns the same object for what it does not cut**, so a batch renders only its own cards: unmemoised, 50 a frame took 75s to draw the page, against one commit's 15s; memoised, 100 a frame took 20s. **A batch is not a transition**: a running session sends a reading every 2 seconds, a new reading restarts a transition, and a batch slower than that was never drawn, which `dev-sessions.spec.ts`'s fold test found by waiting on a page that never finished drawing. That test now waits for the skeleton (`data-sessions-drawing`) to go before it counts the page, since a batch laid out during its trace is not the fold's. From navigation, a return visit's first card came at 5.4-8.2s over three loads, of which 2.5-3.9s is the app the dev server serves before any page draws, the Tests page's included. A cold visit, the dev server's modules already transformed, drew its first card at 31.5s, 25.2s of it the first reading, which this does not change. A new reading still renders every drawn card, since each reading's objects are new.
- **A card ranks its facts in three rows, the page filters by state, and what is read once starts folded** (#613). The first row is state, elapsed time and the token totals, in the foreground colour. The second, muted, is type, model and step. The third is the tools, under a visible label, wrapping inside the card. `dev-sessions.spec.ts` finds a card's own facts as `:scope > div`, so the rows stay inside that one wrapper. The state filter is `filterGroups` in `src/dev/sessions-filter.ts`, unit-tested over made-up readings. It keeps a session when its **card's** tree holds the state, not its group's slice's: a slice carries only the subagents that worked on that group's branches, so a session whose waiting subagent ran on `#101` would have vanished from its `develop` group. A group's total is left as it is whatever is shown, so it still matches the Usage page. A chain whose issues are all merged starts folded to "n of n merged". Its conductor still runs, so R8 keeps it on the page. A top-level session whose step is Unknown shows no step, since R9 gives a step to a worker; a session that typed `/implement` once and went on to other work would otherwise read "Step unknown" for the rest of its life. A subagent still says it. **A session's heading is its first prompt, a typed command read as the command and its arguments** (#616): `commandOf` in `dev/command-prompt.ts` takes a prompt for a command only when it opens on a `<command-name>` or `<command-message>` tag, since Claude Code writes them in either order and a prompt can quote the markup further in. The chain view's `/chain` and the `implement` step's `/implement` are read through it too (#682), so a prompt that only quotes their markup starts neither. A bare `/clear` gives way to the next prompt. Measured 2026-10-25, 211 of this machine's 220 sessions were titled with the raw markup before this. A prompt that opens on `<bash-input>`, a `!` shell command, reads `! ` and the command, and one that opens on `<bash-stdout>` or `<bash-stderr>`, its output, is no task, so it never titles a session (#679); measured later that day, none of this machine's 221 sessions was titled with markup after it.

## Reading the transcripts

Both pages read this machine's Claude Code transcripts through `dev/transcripts.ts`, so these rules bind Sessions and [Usage](dev-tools-usage.md) alike.

- **A scan reads two transcript locations, not one** (#431): the top-level `~/.claude/projects/<slug>/*.jsonl`, and each session's `~/.claude/projects/<slug>/<session>/subagents/*.jsonl`, where Claude Code writes every subagent's transcript (`listTranscripts` in `dev/transcripts.ts`). Reading only the first, #428 read 257 output tokens against ~56k, and the machine left 1.21M output tokens on issue branches unread (2026-10-06). Subagent records carry `gitBranch` and join issues the same way, a response id seen in both places counts once, and cursors stay keyed on the full path, so an unchanged subagent file is not opened. **A read keeps each response's largest count.** Measured 2026-10-07, 1,705 of 2,855 multi-record subagent responses carried a partial `output_tokens` on their first record and the final count on their last (177k against 1.41M summed); top-level records never differ, which is why #413's first-record rule had held. So a read takes the largest count per id, and the store's `ON CONFLICT` raises a stored row to a larger count instead of doing nothing, since a scan can store a running subagent's first block before its last is written. Only `.jsonl` directly under `subagents/` is read — not the `agent-<id>.meta.json` beside it, not another session directory (`tool-results/`), not anything nested deeper. A record with no id is keyed on its path below the directory (`line:<session>/subagents/agent-<id>.jsonl:<n>`), so it cannot collide with a top-level file of the same base name, and top-level keys are unchanged so an existing history picks the new rows up on its next scan without re-adding the old ones. `transcripts` on the report counts both kinds.
- **A turn is one API response, not one transcript record** (#413). Claude Code writes a response as one record per content block — text, each `tool_use` — every one carrying the same `message.id` and a copy of the same `usage`, so summing records counted a response once per block: 2.32x the true output overall, 1.00x-3.89x per issue, and not a constant factor, since it scales with how many tool calls the work made. `readTranscripts` in `dev/transcripts.ts` keeps one row per id, under its first record's session and branch, before any branch is read, so issue rows and the unattributed total collapse alike. Since #431 that row takes the **largest** `output_tokens` and cache-read among its records rather than the first's, because subagent transcripts write a partial count on a response's first record (see the #431 bullet above). (Since #417 that id is also the key the usage history stores a response under.) A record with **no** id falls back to its `uuid`, then to its file and line, and so still counts once per record, so a format change that drops the id over-counts rather than reading as zero spend. Every turn count and per-turn rate measured before it was measured on records. #627 re-measured the output per turn on responses (~745 became ~500) and the per-issue distribution the `forecast/S|M|L` edges in `docs/agents/issue-tracker.md` came from, and kept the edges; the 28% share above still wants re-measuring.

## How the tools are built and served

- Browser half in `apps/web/src/dev/`, node half in `apps/web/dev/` (a Vite plugin, `apply: "serve"`), wire types shared in `apps/web/src/dev/`. **One contract module per page, since #284** — `map-protocol.ts`, `test-run-protocol.ts` and `usage-protocol.ts` (and `sessions-protocol.ts` since #590), plus `devtools-paths.ts` for the route table they all spend. The split follows the importers, who cluster by page (of thirty, sixteen Usage, eleven map and five test runner, when one 42 KB module held them all and sat in fifteen of the Usage page's twenty-four commits), so a module that renders one tool reads no other tool's contract. **Only three name more than one, and all three are wiring rather than a page**: `dev/plugin.ts` (the middleware registers every tool's handler), `dev/plugin.test.ts` and `src/dev/dev-api.ts` (the browser client calls every tool). `dev-api.ts` is why criterion one holds at the import level and not transitively — `ProjectMapPage` reaches the Usage contract one hop out through it — and splitting that client is a later ticket, not a defect here. `DEVTOOLS_API` is the one name that did not cluster at all, so it is a module of its own rather than a copy per tool: each copy is one more chance for a client and its handler to be renamed apart, with nothing failing until the request 404s. All of them stay **import-free**, for the reason `routes.ts` is: the node half reaches them by relative path under Vite's native config loader, with the `.ts` extension that loader requires. **The Usage contract is itself four modules, split by reader rather than by size** (#297): `usage-protocol.ts` is the wire — the row, the report, the warnings, and the `BUCKETS`/`VERDICT` words a row's fields are typed in; `usage-readings.ts` is the arithmetic over it plus `hasRecordedSpend`; `usage-copy.ts` is the column order and the strings both suites reach for; and the facet vocabulary sits with its predicates in `usage-facets.ts`, so a fourth facet is one file's edit. The first two are what the node half and `bun run tokens` import, the last two they never do. `BUCKETS` stays on the wire rather than with `bucketFor` because the arithmetic imports the wire, and the reverse would be a cycle. The wire and `usage-copy.ts` are import-free; `usage-readings.ts` imports the wire and nothing else. A fifth, `usage-push.ts` (#428), is the push's wire, read only by the node half and `bun run tokens`, and the one that imports a package, `zod` and nothing else, which the config loader resolves like any bare specifier. `tests/e2e/dev-usage.spec.ts` reaches `usage-facets.ts` as well, which is **not** import-free — the one E2E import that is not, and it holds because everything that module pulls in is a relative import of the other two with no `@/…` alias and no React, so Playwright's loader resolves the chain the way it resolves `routes.ts`. A facet module that grows a component import breaks the E2E at load, not at an assertion. Every module a Usage slice reads is under 15 KB, the deepening PRD's R10; the figures are in `docs/plans/usage-page-module-seams.md` (slice 9). `tsconfig.node.json` includes `dev` so both ends are checked.
- **Relative imports in `dev/` and in `vite.config.ts` carry their `.ts` extension, and use `import.meta.dirname` rather than `__dirname`.** Both are required by Vite's `configLoader: 'native'`, which is announced to become the default in a later major; until then Vite 8 prints a warning naming every offending line on each dev start. `allowImportingTsExtensions` is already on in `tsconfig.node.json`, so the extension costs nothing. Keep new files in this directory to the same rule — the warning is per-import, so one extensionless addition brings the whole block back.
  - **And the rule follows the import graph out of `dev/`, which is the trap.** The loader resolves nothing extensionless in anything it pulls in either, so a `src/dev/` module the node half reaches has to spell its _own_ relative imports the same way. The contract modules never noticed, being import-free; `usage-sort.ts` is the first module that is not one and is imported from `dev/` anyway (#286, `joinIssues` sorting with `DEFAULT_USAGE_SORT`), so its imports carry the extension while every other file in `src/dev/` writes them bare. `usage-readings.ts` is the second (#297): `joinIssues` bands its rows with `bucketFor`, and `usage-sort.ts` asks `hasRecordedSpend`, so it is reached from `dev/` twice over and its one import is `./usage-protocol.ts`. `allowImportingTsExtensions` is on in `tsconfig.app.json` too, so the browser build and the component suites are indifferent — but a module in `src/dev/` is not automatically loadable from `dev/`, and finding out costs a dev server that will not start.
- Kept out of production by `import.meta.env.DEV` in `App.tsx` and `nav-items.ts` — Vite folds it to `false`, so Rollup drops the `import()` and emits no chunk. If you add an entry point to this code, check `.vite/stats.html` after a build.
- **Railway's `develop` environment serves them, from `vite dev` behind HTTP Basic Auth over every request** (#314). Its `web` service builds `apps/web/Dockerfile.dev` (selected by `apps/web/railway.dev.json`) rather than the static build, so `import.meta.env.DEV` is true there and the plugin exists; production still builds `apps/web/Dockerfile` and has neither. The gate is `apps/web/dev/basic-auth.ts`, a `configureServer` pre-middleware that is the **first** plugin in `vite.config.ts`, so it covers the dev tools and the `/api` proxy along with the app — the proxy runs after plugin middlewares. The public repo means serving source is not the concern; strangers starting test runs on a metered machine is. Four rules: `/health` is the one exemption, for Railway's healthcheck, and its host `healthcheck.railway.app` must also be in `__VITE_ADDITIONAL_SERVER_ALLOWED_HOSTS` because Vite's host check runs _before_ any plugin middleware; the comparison hashes both sides and uses `timingSafeEqual`, as the inbound-email webhook's does; the credential is deleted from the request once it passes, so the API behind the proxy never sees or logs it; and it **fails closed** — `Dockerfile.dev` sets `DEV_BASIC_AUTH_REQUIRED=1`, and with that on (or with one credential set without the other) `readCredentials` throws and the server never listens. With nothing set, or both set empty, it is a no-op. A developer who pushes usage (DEPLOYMENT.md §7) carries both credentials, so `playwright.config.ts` blanks them for the E2E web server (#619). The root `.dockerignore` still applies to that image, so `tests/`, `scripts/`, `*.md` and `playwright.config.ts` are absent: the map does not show them, and the test runner shows the E2E suite as unavailable there (the test-runner section below).

## The project map (`/__dev/map`)

- The scan is regex-over-source with comments stripped first (`dev/scan.ts`), not a TS AST. The stripper is `stripComments` from the `tools/repo-scan` workspace (#565), the one copy both standards guards, `validation-copy.test.ts` and the API's doc citations read too, imported by its bare name `@ticket/repo-scan/strip-comments`: the config loader takes a workspace package whose files are `.ts`, under `--configLoader native` on Bun as well as under the default, so the node half needs no relative path into `tools/`. It keeps template contents, which the endpoint matcher reads. It handles the import styles this repo uses; anything it cannot parse lands in the map's `warnings` rather than being dropped silently. Routes are read off `ROUTE` (`readRouteRecord`), so a new way of writing a route path needs teaching there ([frontend.md](frontend.md)'s `ROUTE` bullet).
- The map's filter bar has **two different reaches, and a new view has to pick one deliberately.** The workspace `Select` and the two toggles stop at the Graph and Modules tabs — Overview and Wiring report whole-project totals, and a project that shrank because you hid the tests would be worse than useless. The **search reaches all four**, and every match goes through `matchesQuery` in `dev/module-match.ts` rather than an inline `id.includes(...)`: the inline version is exactly how the box came to do nothing on Overview and Wiring, which are the tabs written last and the first one the page opens on. Wire a new view in by naming the fields it searches. Two rules that follow from it — an empty query matches _everything_, so callers filter unconditionally instead of branching; and a card heading whose list can narrow shows `countLabel(shown, total)`, because a heading still reading `12` over three rows is the same lie the frozen module counter used to tell. Scan `warnings` are deliberately exempt: a warning says the map you are reading is incomplete, so it outranks whatever you typed.

## The test runner, and what the dev server spawns

- Test runs belong to the **dev server**, not the tab: reloading reconnects and replays, only Cancel stops one (it kills the process tree). Editing anything under `apps/web/dev/` restarts the dev server — it is a `vite.config.ts` dependency — which cancels any run in flight.
- Anything spawned from the dev server must sanitise its environment first (`childEnv` in `dev/child-env.ts`, shared by the test runner and, through `gitEnv` beside it, by the Usage page's `git` and `gh` calls). The dev script is `bunx --bun vite`, and `--bun` puts a fake `node` on PATH plus `NODE=…/bun-node-*/node.exe`; a child that inherits it sees Bun where it expects Node, and Vitest's `node --require …/suppress-warnings.cjs` worker launch turns into Bun trying to _install_ that path as a package. It also strips every key the repo's `.env*` files declare, because `dotenv-cli` won't override an inherited value — otherwise `.env.test` loses to the dev `PORT`/`DATABASE_URL` and the E2E database reset points at the dev database.
  - **And it is asynchronous.** `execFileSync` in a dev-server middleware is wrong twice over: it blocks the thread Vite answers every other request on for as long as the child runs, and its `timeout` option **does not work in that process**. Measured 2026-09-17 while wiring the Usage page's `gh` call: a Scan returned in 2.4s with `spawnSync gh ETIMEDOUT`, `signal=SIGTERM` and empty stderr — the child killed at once rather than after the 20 seconds it was given — so the page reported “no `gh`” on every press, while `bun run tokens` ran the identical call from a plain Bun process and succeeded. The dev server is `bunx --bun vite`, so the middleware runs on Bun's runtime; only the _synchronous_ spawn misbehaves. Use `promisify(execFile)` and let the handler be `async` — `only()` in `dev/plugin.ts` awaits a promise-returning handler and turns a rejection into a 500. `execFileSync`, `spawnSync` or `execSync` anywhere under `dev/` fails the standards guard (`apps/web/dev/standards-guard.test.ts`); `vite.config.ts` reads `git` synchronously at config time, outside any request, and is not in its scope.
  - **A `git` or `gh` child takes `gitEnv`, not bare `childEnv`** (#566): `gitEnv` is `childEnv` with `repositoryFreeEnv` from `@ticket/repo-scan/git-env` on top, which removes the 15 variables `git rev-parse --local-env-vars` lists. Inherited from a git hook, `GIT_DIR` or `GIT_INDEX_FILE` makes git answer for the hook's repository whatever its `cwd` says (#531), and `gh` finds its repository through git. The `gitEnv` it replaced removed 3 of them, and `usage-store.test.ts` holds the difference with a second repository's `GIT_DIR` and `GIT_INDEX_FILE`. `vite.config.ts`' git calls take `repositoryFreeEnv` alone. A `git` or `gh` spawn anywhere under `apps/` or `scripts/` whose environment does not come from it fails `apps/api/src/git-spawn-env.test.ts`.
- **On Railway's `develop` server the page runs three suites and shows the fourth as unavailable, and that is a property of the image, measured** (#585). `Dockerfile.dev` copies only the workspaces and root manifests, so the image has no `.git`, `.claude/`, `.mcp.json`, Markdown, `tests/` or `playwright.config.ts`, and no `git`; before the fix, all four suites failed there. Each gap is closed where it lives. **E2E** names the paths it `needs` in `SUITES`, and `describeSuites` reads them per request: one that is missing makes the suite `unavailable` with the reason, the page leaves it out of "Run all tests" and the counts and disables its Run button with the reason as a tooltip, and `/__devtools/start` refuses it with a 409. **The web suite** needs a real Node: the Bun image's only `node` is `/usr/local/bun-node-fallback-bin/node`, a link to `bun` that the `bun-node-*` rule above does not match, so Vitest ran on Bun and 31 of 86 files failed to load ("Vitest mocker was not initialized", `evaluating 'runner.config'`). The image copies Node 22 into `/usr/local/bin`, ahead of the fallback on PATH. **Tests that read the repository's own files or start `git`** skip under `PARTIAL_CHECKOUT=1` (`@ticket/repo-scan/checkout`), which only `Dockerfile.dev` sets, and each runner prints `PARTIAL_CHECKOUT_NOTE` once (the API preload, and `vite.config.ts` under Vitest). The skip is keyed on that marker and never on a file being absent, so a file missing from a clone or from CI still fails. A new test that reads `.claude/`, a doc, `tests/` or the tracked file list, or starts `git`, takes `skipIf(partialCheckout)`, and a list it builds at load time is empty under it. The TypeScript suite runs `bun --filter '*' typecheck` there, since the root script's second half checks only the absent E2E files and fails TS5058 on their missing `tsconfig.json`. Measured in a local build of the image: the API suite 1205 passed and 139 skipped, 1344 tests against 1346 passed on a clone, the totals differing because some `test.each` tables are built from files the image lacks (`hook-input.test.ts`'s is five tests on a clone and one skipped there); the web suite 1171 passed and 69 skipped over 86 files.
