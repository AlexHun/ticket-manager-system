# Dev tools standards: reading the transcripts

How the `/__dev` tools read this machine's Claude Code transcripts: the transcript reader (`dev/transcript-reader.ts`), the attributing and counting `dev/transcripts.ts` keeps, the cursors a read resumes from, a response's identity, and the subagent transcripts. Split out of [dev-tools.md](dev-tools.md) (#757), which holds the pages, the plugin and what the dev server spawns, so a change to the reader alone reads this file.

These rules bind Sessions and [Usage](dev-tools-usage.md) alike. **One incremental reader, `dev/transcript-reader.ts`, owns them since #748**: listing the files, resuming a read, splitting and numbering lines, a response's identity and folding its copies. The Usage scan reads through its `readTranscripts`, and resumes by the rule #748 took from the Sessions reader: a file whose size and modification time are its cursor's is not opened, and one that no longer holds the 64 bytes its cursor sits behind is read from the top. The Sessions reader follows each transcript through its `followTranscript` since #749: the same rule, read asynchronously, with a per-record hook for what only that page shows. A response's identity, counts and folding are private to the module; `foldResponses` is how the Sessions groups count the cards' responses once. Attributing and counting stay in `dev/transcripts.ts` (`tallySpend`).

- **A scan reads two transcript locations, not one** (#431): the top-level `~/.claude/projects/<slug>/*.jsonl`, and each session's `~/.claude/projects/<slug>/<session>/subagents/*.jsonl`, where Claude Code writes every subagent's transcript (`listTranscripts` in `dev/transcript-reader.ts`). Reading only the first, #428 read 257 output tokens against ~56k, and the machine left 1.21M output tokens on issue branches unread (2026-10-06). Subagent records carry `gitBranch` and join issues the same way, a response id seen in both places counts once, and cursors stay keyed on the full path, so an unchanged subagent file is not opened. **A read keeps each response's largest count.** Measured 2026-10-07, 1,705 of 2,855 multi-record subagent responses carried a partial `output_tokens` on their first record and the final count on their last (177k against 1.41M summed); top-level records never differ, which is why #413's first-record rule had held. So a read takes the largest count per id, and the store's `ON CONFLICT` raises a stored row to a larger count instead of doing nothing, since a scan can store a running subagent's first block before its last is written. Only `.jsonl` directly under `subagents/` is read — not the `agent-<id>.meta.json` beside it, not another session directory (`tool-results/`), not anything nested deeper. A record with no id is keyed on its path below the directory (`line:<session>/subagents/agent-<id>.jsonl:<n>`), so it cannot collide with a top-level file of the same base name, and top-level keys are unchanged so an existing history picks the new rows up on its next scan without re-adding the old ones. `transcripts` on the report counts both kinds.
- **A turn is one API response, not one transcript record** (#413). Claude Code writes a response as one record per content block — text, each `tool_use` — every one carrying the same `message.id` and a copy of the same `usage`, so summing records counted a response once per block: 2.32x the true output overall, 1.00x-3.89x per issue, and not a constant factor, since it scales with how many tool calls the work made. `readTranscripts` in `dev/transcript-reader.ts` keeps one row per id, under its first record's session and branch, before any branch is read, so issue rows and the unattributed total collapse alike. Since #431 that row takes the **largest** `output_tokens` and cache-read among its records rather than the first's, because subagent transcripts write a partial count on a response's first record (the #431 bullet). (Since #417 that id is also the key the usage history stores a response under.) A record with **no** id falls back to its `uuid`, then to its file and line, and so still counts once per record, so a format change that drops the id over-counts rather than reading as zero spend. Every turn count and per-turn rate measured before it was measured on records. #627 re-measured the output per turn on responses (~745 became ~500) and the per-issue distribution the `forecast/S|M|L` edges in `docs/agents/issue-tracker.md` came from, and kept the edges; the 28% share of turns on `main` in [dev-tools-usage.md](dev-tools-usage.md)'s #253 bullet still wants re-measuring.
