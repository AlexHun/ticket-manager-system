# Backend standards (`apps/api`)

Server-side conventions: database, HTTP, auth, background jobs, ingestion, outbound mail. Testing lives in [testing.md](testing.md); the reasoning behind the security invariants lives in [security.md](security.md).

## Database, HTTP, jobs, ingestion

- DB: Postgres (Neon/Supabase) via **Prisma 7** with the `@prisma/adapter-pg` driver adapter. Schema at `apps/api/prisma/schema.prisma`; CLI config at `apps/api/prisma.config.ts` (this is where `DATABASE_URL` is wired in — Prisma 7 no longer accepts `url` inside `datasource`). Generated client lives at `apps/api/src/generated/prisma` (gitignored, recreate with `bun run db:generate`). Import the singleton from `./db`, not the generated path directly.
- CORS: cross-origin in dev → API uses `cors` middleware in `apps/api/src/index.ts` with `origin: trustedOrigins` (exported from `auth.ts`) and `credentials: true`. Mounted before the Better Auth handler. Frontend uses `credentials: "include"`.
- Background jobs: **pg-boss**, in `src/jobs/`. `boss.ts` owns the lifecycle plus the two registrars — `registerWorker` and `registerSweep` — and knows no queue by name; `index.ts` wires registrations (one line per consumer); one file per consumer beside them, with `ai-retry.ts` holding the one `Record<AiFailure, boolean>` they share.
  - **There are two kinds of queue and two registrars, and nothing outside `boss.ts` calls pg-boss's own `createQueue`, `updateQueue`, `work` or `schedule`** (#158). A consumer declares a spec and hands it over; `boss.test.ts` reads the directory and fails on any job module whose text contains one of those four **as a call** (`.work(`), or one of `retryLimit` / `retryDelay` / `notifyPollingIntervalSeconds` / `policy` / `deadLetter` **as an object key** (`retryLimit:`). Both checks match a form rather than a word, deliberately: files here explain themselves at length, and a sweep must stay free to write a comment about why it has no retry ladder without failing the build. `ensureQueue` — the create-then-update pair that makes #144's reconcile-on-boot work — is no longer exported: while it was, "make a queue" and "make *this app's* kind of queue" were two things a caller chose between, and all four scheduled queues chose the first. `send` is deliberately not on the banned list; enqueueing is what a consumer is for.
  - **A worker is registered by handing `registerWorker` a spec, never by wiring queues itself** (#154). The spec is a name, a `handle`, an `onExhausted`, a concurrency and an expiry; `boss.ts` owns everything that makes those a *queue in this app* — the live queue and its `-dead` twin (both through `ensureQueue`, so #144's reconcile-on-boot holds for both), the retry ladder, `notify: true` with the 5s poll, `batchSize: 1` with `localConcurrency`, and the single log line plus Sentry alert that fire when the ladder runs out and nowhere earlier. Those were re-typed in all three worker files before this, which is how a queue invariant ends up living in the consumers. A consumer that needs a different ladder should argue it in `boss.ts`, and `boss.test.ts` enforces that by reading the directory. (`retryLimit: 0` on a cron sweep used to be the one exception to that rule; since #158 `registerSweep` sets it, so there is no exception left and no consumer may write it.) **The spec is exported** (`CLASSIFY_WORKER`, `AUTO_REPLY_WORKER`, `SEND_EMAIL_WORKER`), which is what makes both halves callable in a test with no queue running — including the terminal path, which otherwise never runs on a good day. Payload types are declared with `type`, not `interface`, so they satisfy the spec's `Record` constraint (the alert attaches the payload to the Sentry scope verbatim). Started before `app.listen` and stopped in the SIGINT/SIGTERM handler *before* `prisma.$disconnect()` — a job finishing gracefully still needs the database. A failure to start takes the boot down on purpose: an API that is up but silently running no background work is the hardest kind of broken to notice. **To enqueue from inside a request, pass `fromPrisma(tx)`** so the job and the row it refers to commit together (see `routes/webhooks/inbound-email.ts`). Handlers must be idempotent — delivery is at-least-once — and must throw only for failures worth retrying; returning normally means "done, do not retry".
  - **A scheduled sweep is registered by handing `registerSweep` a `SweepSpec`** — a name, a cron, an expiry and a `run` that takes no payload. `boss.ts` owns what makes those a *scheduled queue in this app*: `policy: "singleton"` (a tick arriving while the last one runs must not start a second — every sweep reads a batch and writes to the rows it read), `retryLimit: 0` (not a shorter ladder, the absence of one: the next tick sees the same rows, so a retry buys a duplicate rather than a recovery), the `ensureQueue` pass that keeps #144's reconcile-on-boot, and the `boss.schedule` re-asserted on every boot so an edited cron takes effect on deploy. No dead-letter twin — there is no ladder to run out of. **The spec is exported** (`CLASSIFY_RECONCILE_SWEEP`, `AUTO_REPLY_RECOVER_SWEEP`, `PRUNE_OUTBOX_SWEEP`, `PRUNE_ACTIVITY_TRAILS_SWEEP`), which is what makes `run` a function call in `sweeps.test.ts` instead of something only a running cron could reach — and these are the four paths that most need it: what they do is invisible in production until a ticket is stuck, an email is missing, or an article's last revision has been swept away. `expireInSeconds` stays per-sweep (the two that re-enqueue tickets borrow their worker's; the two that delete in batches take five minutes).
  - **`Processing` is a claim, not a phase.** `auto-reply-ticket.ts` takes a ticket by moving it `New → Processing` in a single conditional `updateMany`, and `GET /api/tickets` refuses to return that status — so for the seconds a worker holds a ticket, no agent can open it and write a second reply to the same customer. Every write after the claim is conditional on still holding it, so a duplicate delivery or a released ticket costs nothing. Release on **every** exit path: `New` when a retry is coming (so the retry has something to claim), `Open` when it is over. A claim that leaks is a ticket nobody can see.
  - That is also why `recoverStuck` exists. pg-boss re-offers an expired *job*, but the re-delivery cannot claim a ticket that is already `Processing`, so the two would wait for each other forever after a hard kill. The cron sweep reads staleness off `updatedAt` (the claim moves it) and puts the ticket back to `New`. Any future status-as-claim needs the same pairing — the claim and the thing that undoes it are one design, not two.
- Ingestion: **`src/ingest.ts` is the only path into the ticket table.** `ingestInboundEmail` is called by the Postmark webhook and by the `/pipeline` simulator, and each caller keeps only what is genuinely its own (the webhook: Basic Auth, a 45mb body limit, the Postmark adapter; the simulator: `requireAdmin`, a pinned sender domain, a rate cap). `findParentTicketId` is exported alongside it because the simulator has to ask the same threading question *before* ingesting, in order to refuse an `inReplyTo` that lands on a real customer's thread — asking twice is two indexed lookups and no duplicated rules.
- Express 5 auto-forwards rejected promises from `async` route handlers to the error pipeline — don't wrap `await` calls in `try/catch` just to translate the error into a response. Let it throw. Only catch when you actually need to branch on the error (e.g. map a specific error type to a custom response, or recover and continue) — never to re-throw or to manually call `next(err)`.

## Auth

- Auth: **Better Auth** (`better-auth`) with the Prisma adapter. Server config at `apps/api/src/auth.ts` (email/password enabled, `disableSignUp: true`, `role` additional field `admin|agent`, `TRUSTED_ORIGINS` required, `BETTER_AUTH_SECRET` validated ≥32 chars, `rateLimit` enabled only in production). Server-side RBAC middleware at `apps/api/src/middleware/auth.ts` exports `requireAuth` and `requireAdmin` — apply to every protected route (frontend `AdminRoute` is UX, not security). Client at `apps/web/src/lib/auth-client.ts` exports `signIn` / `signOut` / `useSession` and reads `VITE_API_URL` for cross-origin baseURL. Cookie-based sessions — **not JWT**.
  - **Nobody types somebody else's password** (`docs/adr/0011`). `POST /api/users` calls `createUser` with **no password**, then triggers the reset flow; the colleague picks their own from a link. Recovery (`/forgot-password`) and resend (`POST /api/users/:id/invite`) are the *same* mechanism — Better Auth's own guidance for a credential-less user — told apart inside `sendResetPassword` by whether a `credential` account row exists. So there is no password field on either user form and `setUserPassword` is unreachable from the API. `resetPasswordTokenExpiresIn` is **24h**, a compromise: one setting serves both flows, and an hour-old invitation is a dead link on somebody's first morning.
  - **No email verification** (`docs/adr/0010`). `emailVerified` is forced true at creation and read by nothing. It used to default false with no way to ever set it true, so the roster drew a permanent "Unverified" badge on every real colleague and a clean tick on the assistant. Don't enable `requireEmailVerification` without backfilling first — it would lock out every pre-existing account.
  - **Every email goes through the outbox, never straight to a provider** (`docs/adr/0009`). `enqueueEmail` in `jobs/send-email.ts` writes an `OutboundEmail` row inside the caller's transaction and a worker makes the network call afterwards; `mail/transport.ts` is the *only* module that will ever speak to Postmark. This is forced, not stylistic: `sendReply` runs inside `prisma.$transaction`, and an HTTP call there would hold a transaction open across a third-party round trip that a rollback cannot undo. With no provider, rows land `undeliverable` and `/outbox` (admin-only) **is** the delivery mechanism — which is what makes removing admin-typed passwords survivable. Those rows hold live single-use links; keep the route admin-only. **`undeliverable` and `failed` are terminal on purpose** — nothing reopens them on a schedule, because an outbox that retries forever turns a provider outage into a duplicate-mail incident. The way out is a person: `POST /api/outbox/:id/retry` flips the row back to `queued` and re-enqueues, both inside one transaction. It refuses when no provider is configured (the retry would only land back where it started) and it can never touch a `sent` row — `RETRYABLE_STATUS` is in the `updateMany`'s `where`, so two admins clicking at once means the second one matches nothing and enqueues nothing. Read-then-write here would send twice. This route is the reason binding Postmark is not the end of the job: every email written before that moment is sitting `undeliverable` and needs pushing.
    - **The table does not grow forever: `jobs/prune-outbox.ts` sweeps it hourly**, and the retention is per *kind* because the rows are two different things. A `reply` row duplicates `Message.textBody` — the copy an agent actually reads, never pruned — so what expires at 90 days is the delivery record, not the correspondence. An `invitation` or `passwordReset` row **is** a working single-use credential and nothing else, so it is kept for exactly `RESET_TOKEN_TTL_SECONDS` and no longer: `AUTH_MAIL_RETENTION_MS` imports that constant from **`auth-tokens.ts`** rather than restating it, so lengthening a link's life lengthens how long it stays readable, automatically. It lives in that leaf, and not in `auth.ts` beside the Better Auth setting it also feeds, for a reason worth keeping: `auth.ts` throws at import without `TRUSTED_ORIGINS` and `BETTER_AUTH_SECRET`, so no unit test can load it, so `routes/users.test.ts` replaces the whole module — and `mock.module`'s registry is process-wide. Anything reaching this constant through `auth.ts` is one file-ordering away from linking against that fake (#158; green locally, `SyntaxError: Export named 'RESET_TOKEN_TTL_SECONDS' not found` on CI). A leaf with no imports is not worth mocking, so nothing mocks it — keep it dependency-free. Nothing is lost by that — an expired invitation is a dead link, and the fix is the same as it always was, `POST /api/users/:id/invite`. Two properties to keep: `queued` is absent from `PRUNABLE_STATUS`, because a queued row has a job coming for it and deleting one silently drops a promised email; and this **deletes rather than redacts**, because `POST /:id/retry` sends whatever is in `textBody` and a blanked row is one click from emailing somebody a placeholder. `RETENTION_MS` is a `Record<OutboundEmailKind, number>`, so a fourth kind of mail is a compile error until somebody says how long it is kept.
  - **`better-auth` is pinned to an exact `1.6.13`, in both apps, and the pin is load-bearing.** Do not widen it to `^` or `~` without reading this. In `1.6.22` Better Auth replaced how it resolves a client IP from `X-Forwarded-For`: the old code took the leftmost entry (`value.split(",")[0].trim()` in `dist/utils/get-request-ip.mjs`), the new code **refuses a multi-value header outright** unless `advanced.ipAddress.trustedProxies` names every hop to the right of the client, and returns `null` when it cannot decide. `null` is not inert — the rate limiter keys on `NO_TRUSTED_IP_KEY` instead, so *every visitor shares one bucket*, and the 5-per-minute rule on `/sign-in/email` becomes a global sign-in outage that any one person can cause with five bad passwords. Measured against the header this deployment actually receives (`82.135.202.248, 152.233.43.33, ::1`): `getIP` returns `null` on 1.6.30 and 1.7.1, and the true client on 1.6.13. This is the same failure the `X-Forwarded-For` note in `apps/web/Caddyfile` exists to prevent, arriving by a different route — read that note before touching either.
  - The pin is **not** a decision to stay behind. `1.6.13` was chosen because it is the newest release that still has the old resolver *and* clears every advisory that can reach this app: everything in the `bun audit` list for `better-auth` is fixed by `<1.6.11` or `<1.6.13`, and the one that needs `1.6.22` (pre-account hijacking on magic-link / email-OTP sign-in) is unreachable here because neither plugin is loaded. The critical and high entries that remain listed against this version are all in `oidcProvider`, `mcp`, `@better-auth/oauth-provider`, the organization plugin, social auto-linking and device authorization — **none of which this app configures**; it loads `admin` and `emailAndPassword` only, with `disableSignUp: true`. The one genuinely applicable advisory is the *low* "stale sessions persist after user deletion", already mitigated by `DELETE /api/users/:id` deleting the sessions itself (see the `cookieCache` note in `auth.ts` for the 60s window that survives it).
  - Moving past `1.6.13` is a real upgrade, not a bump: it needs `trustedProxies` set to Railway's edge hops — **measured against the live deployment, not guessed** — or a single-value client-IP header arranged at the proxy and named in `ipAddressHeaders`. Note that Railway's inner hop is a *public* address, so "trust the private ranges" is not enough; that is the exact mistake the Caddyfile note records.
