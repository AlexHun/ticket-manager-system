# AI feature standards

Four features, one provider, one key. The shared machinery, the failure taxonomy, the retry policy, and the measured traps. Prompt-injection defences for these features live in [security.md](security.md); the `AiShine` waiting state lives in [frontend.md](frontend.md).

- AI: **four features ship today, all on OpenAI `gpt-5-nano`** through the Vercel AI SDK (`ai` + `@ai-sdk/openai`): reply polishing (`apps/api/src/ai/polish.ts`, `POST /api/ai/polish-reply`), ticket summarising (`apps/api/src/ai/summarize.ts`, `POST /api/ai/summarize-ticket`), automatic ticket classification (`apps/api/src/ai/classify.ts` + `jobs/classify-ticket.ts`, no endpoint — it runs off the inbound-email webhook) and knowledge-base auto-reply (`apps/api/src/ai/auto-reply.ts` + `knowledge-base.ts` + `jobs/auto-reply-ticket.ts`, no endpoint — it runs off classification). Shared machinery — the key, the provider handle, `AI_FAILURE`/`classify`, `fenced`, `unbackedCommitments`, `withoutDashes`, `usdFor` — lives in `apps/api/src/ai/provider.ts`; prompts, models and output validation deliberately do **not**. One `OPENAI_API_KEY` gates all four; unset means the two endpoints answer 503, new tickets stay uncategorised in `New`, and nothing else in the app changes. `AUTO_REPLY_ENABLED=false` stops the fourth alone. `tech-stack.md` names the Anthropic SDK (with prompt caching for the KB block) and lists classification under it; both landing on OpenAI settles that fork **deliberately** — they reuse the machinery, the account and the failure taxonomy the first two already have, and one provider is worth more than matching a plan written before any of it existed. Prompt caching still applies: the auto-reply puts the static corpus in the _system_ prompt precisely so the prefix is identical across requests. Nothing Anthropic-shaped is left outstanding; adding a second AI stack now needs its own argument.
  - Summaries are **never cached**, client or server: `TicketSummaryPanel` uses `useMutation` and the panel is keyed on the ticket id, so every click is a fresh generation. That is the feature, not an oversight — a cached summary is a confident paragraph about a conversation that has moved on. The response carries `messageCount` so the panel can say when the thread has outrun the summary.
  - **Classification is the only AI feature with no human at the moment it runs**, so it is the only one whose safety story is structural rather than procedural. Its entire influence over the system is one of four `TicketCategory` values on one nullable column, enforced by a `z.enum` in a strict schema — a message that talks its way past the prompt has mis-filed a ticket and done nothing else. It also **never overwrites a human**: the handler re-reads the ticket, bails if `category` or `classifiedAt` is no longer null, and writes through `updateMany({ where: { id, category: null } })` so an agent who files it during the call wins. Keep both properties if this is rewritten; without them it is a different feature. They are also what makes pg-boss's at-least-once delivery safe — **the ticket row is the source of truth, the job is only a nudge**, so a job delivered twice or replayed after a crash costs nothing. Never replace those guards with a check on job state. Since the eval harness's fourth slice the classifier is also the one AI feature with a **measured** accuracy: `/evals` scores it against the category each case in `AUTO_REPLY_CASES` declares, five repeats apiece, and reports which category is being mistaken for which (PRD R15). Two things about how that is wired are load-bearing rather than incidental. The eval runner asks the classifier and then hands `gateDecline` the case's **declared** category anyway, so a classifier flake cannot move decline accuracy and a red board still says which of the two models drifted; and it asks on the gated cases too — `refund` misfiled as `General` is the category gate failing, which is the only control between a refund request and an unattended reply, so it is the sharpest place to measure rather than one to skip. Two cases are deliberately outside the metric (`unclassified` expects classification to have failed, `no-inbound-message` has nothing to read); `apps/api/src/evals/classify-case.ts` is where that argument lives, and it is a module of its own partly so `evals/runner.test.ts` gets a mock seam that `jobs/activity-before-publish.test.ts` does not already own.
  - The classifier is **non-blocking by construction**, and since it moved onto pg-boss it is durable too. The inbound-email webhook enqueues `classify-ticket` _inside_ the transaction that creates the ticket (`enqueueClassification(id, fromPrisma(tx))`), so the two facts share a fate; a worker picks it up afterwards. What must never be awaited before responding is the **model call** — a mail provider times that webhook, a slow one is retried, and a retried webhook is duplicate ingestion. A local INSERT is not that. Measured: the webhook answers in 8-185ms and categories land 4-17s later; after a `taskkill` mid-flight, six queued jobs survived and completed on the next boot.
  - **Retry policy comes free from the failure taxonomy.** `AiFailure` already splits transient from terminal, so the handler _throws_ on `provider`/`busy`/`empty` (pg-boss retries: 30s, then ~60/120/240 with jitter, then dead-letter) and _returns_ on `quota`/`auth`/`config`, which will fail identically forever. `RETRYABLE_AI_FAILURE` in `jobs/ai-retry.ts` is a `Record<AiFailure, boolean>` so a new failure mode is a compile error until someone classifies it. The classifier's `onExhausted` stamps `classifiedAt` — that is what stops the 15-minute reconciliation sweep re-offering a ticket that has already exhausted its retries. The ladder itself is not the classifier's: it belongs to `registerWorker` in `jobs/boss.ts`, shared with the auto-reply and the sender because all three wait for the same kind of thing (see [backend.md](backend.md)).
  - Two pg-boss traps, both found by measurement and both commented at the site — now in `jobs/boss.ts`, once, rather than per consumer. **`createQueue` does not update an existing queue**, so editing `RETRY_LIMIT` and restarting silently changes nothing on any deployment past the first — `ensureQueue` calls `updateQueue` after it, which is what keeps the constants in the file authoritative. And **NOTIFY fires on insert, not when a retry becomes due**, so with `notify: true` a retry waits for the backstop poll: on the 30s default a 1s retry delay took 58s. `notifyPollingIntervalSeconds: 5` is the fix.
  - **Every model call logs one line, from `logUsage` in `provider.ts`.** `[ai] feature=… model=… input=… cached=… output=… reasoning=… total=… usd~…` — greppable by eye, parseable by a shipper, and never carrying prompt or completion text, because these calls hold customer email and a log is the one place it would sit in plaintext outside the database. The `usd` figure prices tokens against `USD_PER_MTOK`, a copy of the published `gpt-5-nano` rates that **will go stale**; nothing bills off it. The field to watch is `cached`: prompt caching is the difference between the auto-reply costing what it does and ten times that, it engages silently, and it stops just as silently if anything perturbs the front of the prompt — reordering the corpus, interpolating a timestamp, letting article text vary per request. A run of `cached=0` on a feature that should be hitting it is that regression, and until the eval harness landed nothing on any screen would show it — `/evals` now reports, per run, how many of each case's repeats 2..5 came back cached, which is the only place in this codebase where an identical prompt prefix is sent more than once on purpose. `usdFor` is the same arithmetic split out so a run can _record_ the figure rather than only print it (PRD R10); the log line itself is unchanged, deliberately. `usage` is optional as a whole — a provider that reports nothing logs `usage=unreported` rather than failing a call that already succeeded — but **every field inside `AiUsage` is required-and-nullable (`number | undefined`), not optional (`?:`), and that is a fix rather than a style choice.** The first thing the eval harness ever found was `cached=0` across two full runs and 350 calls, and the cause was not the cache: `AiUsage` had been hand-written against the AI SDK's _v5_ flat usage shape while the installed `ai` v7 reports the cached and reasoning counts nested under `inputTokenDetails.cacheReadTokens` and `outputTokenDetails.reasoningTokens`. The SDK's usage object was assigned straight into `AiUsage`, which typechecked precisely _because_ the fields were optional — an absent optional field is a legal value — so both counts read `undefined`, and `cached=0 reasoning=0` had been printed for every AI call this app had ever made. The alarm the paragraph above calls "the field to watch" was a stuck needle for as long as it existed. Two things now stop that recurring, and neither may be relaxed: **`toAiUsage` in `provider.ts` is the only place `LanguageModelUsage` is named**, so an SDK release that moves a field again fails to compile there instead of quietly zeroing a number; and the required fields mean a mapper cannot silently omit one. Nothing else may read the SDK's usage object directly — the four features all log through `toAiUsage(usage)`. `ai/provider.test.ts` holds the whole account.
  - **`reasoningEffort` stays `"low"`, and `"minimal"` is a trap, not a saving.** Measured on `gpt-5-nano` against `polishDraft`: `"minimal"` is accepted — HTTP 200, ~1.6s, 54 output tokens — and returns the draft back **byte-for-byte unedited**, every time. A rewrite endpoint that no-ops has no failing status code to notice. All four features carry the same setting for the same reason; re-measure before trimming this again.
  - **An empty email body and an absent one are the same thing to a prompt, and the prompt builder is what enforces that** — not its callers. `userPrompt` in `auto-reply.ts`, `classify.ts` and `polish.ts` each begins `context.<field>?.trim() ?? ""` and branches on the length, so `null`, `""`, `"   "` and `"\n\t  \n"` build the byte-identical prompt (measured; asserted in `auto-reply.test.ts` and `polish.test.ts`). That is what makes the eval harness structurally unable to drift from the pipeline on it: both hand their context to the same builder. The six sites that assemble one still write the rule out for themselves — `?.trim() || null` at five of them, a message dropped from the array at the summariser — and should keep doing so, but they are belt, not brace, and `docs/adr/0017` is why turning them into a shared assembly module was rejected on the deletion test. `polish.ts` was the one builder branching on the untrimmed string until #210; a whitespace-only message reached the model as an empty fence wearing the "quoted as data" preamble, in place of the branch that tells it not to invent what the customer said. **Never take the normalisation out of a builder and rely on the caller for it.**
  - Structured output goes through `generateText` + `Output.object`, **not** `generateObject`: the latter omits `timeout` from its options. Schemas for it must use `.nullable()` (never `.optional()`/`.nullish()`) and carry no `.min()`/`.max()` — strict mode rejects those, and an unsupported keyword surfaces as a `content-filter` refusal that looks like moderation and isn't.
  - A summary carries `highlights`: short phrases the model picks out of its own summary text, which the panel marks with `<mark>`. Every one is guaranteed to occur verbatim in `overview`/`keyPoints`/`nextStep` because `usableHighlights` drops the rest, so the client matches literally. Two things had to be enforced in code rather than prose: a word cap (asked for terms, the model returns whole quoted sentences out of the customer's email) and the verbatim check (it paraphrases). Ordering in the system prompt matters too — the highlights rule lives **last**, after STYLE; earlier in the prompt its "copy character for character" wording bled into KEY POINTS and turned them into raw email quotes.
