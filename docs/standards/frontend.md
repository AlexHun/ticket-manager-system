# Frontend standards (`apps/web`)

Client-side conventions: forms, styling, UI controls, data fetching, notifications, dev tooling. Component testing lives in [testing.md](testing.md).

- Forms: **react-hook-form** + **zod** via `@hookform/resolvers/zod`. Define the schema, infer the values type with `z.infer`, disable inputs on `isSubmitting`, surface server errors in local state.
- Icons: **lucide-react**. Use `Loader2` with `animate-spin` for pending/loading states.
- Tailwind v4 (CSS-first, no `tailwind.config`). Theme tokens are CSS variables in `apps/web/src/index.css` under `:root` / `.dark`; reference them as `var(--background)` etc. shadcn/ui components live in `apps/web/src/components/ui/`. `:root` / `.dark` also set `color-scheme`, which is what themes the remaining browser-drawn UI (scrollbars, the `type="search"` clear button) — don't remove it.
- **UI controls: shadcn/ui only.** Selects, checkboxes, radios, switches, tabs, tooltips, popovers, dropdown menus, comboboxes — all of it comes from shadcn. Add what's missing with `bunx --bun shadcn@latest add <component>` (the repo is already configured: `apps/web/components.json`, style `radix-nova`, `radix-ui` installed). **Never** reach for a native control instead: a native `<select>`'s popup is drawn by the OS, so it ignores `--popover`/`--radius`/font tokens and looks foreign next to the shadcn controls beside it. This is not a matter of taste — a native `<select>` in the filter bar shipped white-on-white options in dark mode. If shadcn genuinely has no component for the need, **ask** rather than inventing one.
  - Radix primitives that open a floating layer (Select, DropdownMenu, Popover, Combobox) need jsdom shims for the Pointer Capture API, `scrollIntoView` and `ResizeObserver`. They're already installed in `apps/web/src/test/setup.ts` — no per-test setup needed.
  - Radix rejects `value=""` on a `SelectItem` (it reserves the empty string for "cleared"), so an "any"/"all" row needs its own non-empty token mapped at the component boundary.
  - `SelectLabel` reads its id from `SelectGroup`'s context and **throws** without one. Nothing above the pages is an error boundary, so a stray `<SelectLabel>` inside a `SelectContent` blanks the whole app the moment the dropdown opens — always wrap it in `<SelectGroup>`.
  - Testing them: they are **not** native selects, so `selectOptions` (RTL) and `selectOption` (Playwright) do not work. Click the trigger, then click `getByRole("option", { name })`. Assert the current value from the trigger's text, not `toHaveValue`.
- Data fetching: **axios** + **@tanstack/react-query**. Don't use `fetch` directly. Use the shared axios instance from `@/lib/api` (preconfigured with `baseURL: VITE_API_URL` and `withCredentials: true` for cookie-based sessions). Wrap every server call in `useQuery` / `useMutation` — pass the `signal` from the query function into axios for automatic cancellation. The `QueryClientProvider` is wired in `apps/web/src/main.tsx`.
- Notifications: **sonner** via the wrapper at `apps/web/src/components/ui/sonner.tsx` (re-exports `toast`, themes the `<Toaster />` from `useTheme`). The `<Toaster />` is mounted once in `apps/web/src/main.tsx`. Fire `toast.success(...)` on successful mutations and `toast.error(...)` on failure (in addition to surfacing the error inline in the form). Use `extractErrorMessage(err, fallback)` from `@/lib/errors` to pull the API error message out of axios errors consistently. In component tests, `sonner` is globally mocked in `apps/web/src/test/setup.ts` — `toast.*` are `vi.fn()` no-ops and `<Toaster />` renders `null`, so don't assert on toast DOM output.
- **A scrollable table goes in `<TableFrame label="…">`** (`apps/web/src/lib/table-frame.tsx`) — the shared border, rounding and `overflow-auto`, plus the three attributes that make the scroller operable: `tabIndex={0}`, `role="region"` and the required `label` as its `aria-label`. They are one decision, not three (issue #111): an `overflow-auto` div is not focusable, so a keyboard-only user cannot reach the columns that overflow right or the rows below the fold — sharpest on `UsersTable`, where scrolling horizontally at narrow widths _is_ the fix (#83) — but `tabIndex` alone buys an anonymous tab stop, and a `region` with no accessible name is not exposed as a landmark at all. `label` is required for exactly that reason; there is no class-string export to reach for instead. It is focusable whether or not it currently overflows: toggling on measured overflow makes a control appear and vanish as the window resizes, and jsdom reports every scroll dimension as `0`, so no test could hold it. Locked in by `tests/e2e/tickets.spec.ts` — focus the region, press PageDown, and the rows scroll while the sticky `<thead>` holds its place and the window stays put.
  - **The five desk tables use it; `ChartCard` does not, and that is a known gap, not the convention.** The dashboard's chart-to-table toggle (`apps/web/src/components/dashboard/ChartCard.tsx`) still renders its table into a bare `cn(CHART_HEIGHT_CLASS, "overflow-auto")` with no `tabIndex`, role or name — the same defect #111 fixed elsewhere, on a container that never shared `TABLE_FRAME` and so was outside that issue's scope. It bites harder there than it did here, because that table _is_ the chart's accessibility-relief path. Tracked as #123; don't read this bullet as saying the codebase is already uniform.
- **TanStack column sizing stays _uncontrolled_, and the reason is a race, not a preference** (issue #263). `TicketsTable` is the repo's only `useReactTable` call site and the only resizable table; it passes `state: { sorting }` and nothing else, and `columnSizing` must not be lifted back into a `useState` beside it. TanStack's resize handler fills a closure object with the new column sizes from **inside** the `setColumnSizingInfo` updater and reads that same object back from **inside** the `setColumnSizing` updater, so the two updates are a producer and a consumer that React only orders correctly when they share one update queue. Controlled, they did not share one: `columnSizing` was a hook declared above `useReactTable`, so React reached it first on every render where it could not eagerly evaluate the dispatches — which is any render with an update already pending on that fiber — and the consumer spread an **empty** object. The drag then applied nothing whatsoever and the column came back at the _exact_ width it started at, which is what made this read as a test flake rather than a bug: `data-resizing` still went true, the keyboard path (`nudge`, one plain `setColumnSizing`) was never affected, and it only fired under CI load. Uncontrolled, both updates land in the single `useState` inside `useReactTable` and are applied in dispatch order. Locked in by `apps/web/src/pages/TicketsTable.test.tsx`, whose three cases differ only in where React is allowed to flush: one event at a time (the control, which passed even before the fix), the whole drag batched into one `act`, and the whole drag batched behind an update already queued — Playwright cannot hold this, because in a browser the pending update is whatever the runner happened to be doing.
- **A route's path is declared once, in `ROUTE`** (`apps/web/src/lib/routes.ts`), together with the timing key it produces `performance` entries under. Nothing retypes a path: the router's `path`, `NavItem.to`, `<Link to>`, `navigate(...)`, a `pathname ===` comparison and the timing module's patterns all read `ROUTE.<name>.path`, and a ticket link goes through `ticketDetailPath(id)` rather than interpolating `/tickets/${id}`. `NavItem["to"]` is typed as `RoutePath` — the union of the record's paths — so a literal that no longer names a route stops compiling. Issue #151 is what this is for: the user-timing module used to keep its own copy of the three instrumented patterns, and a rename anywhere else made the match miss, the render mark no-op and the measure **stop existing** — no build error, no failing test, nothing in the log. The E2E could not catch it either, because it restated the key strings too; it imports `navigateMarkName`/`renderedMarkName`/`timeToDataMeasureName` now. Two constraints follow. `routes.ts` is **import-free** — no `@/…` alias, no React, no router — which is what lets `tests/e2e/route-timing.spec.ts` reach into it the way `dashboard-layout.spec.ts` reaches into `dashboard-panels.ts`; and `timingKey` is present only on instrumented routes, so `as const satisfies` makes `ROUTE.users.timingKey` a type error rather than an `undefined` that flows on into a mark name. The `/__dev/map` scanner resolves `path: ROUTE.<name>.path` against the record (`readRouteRecord` in `dev/scan.ts`) — a new way of writing a route path needs teaching there, or that route silently drops out of the map.
  - The timing module is split for the same reason: `route-timing.ts` is the pure half (entry names, the pathname→key lookup, the awaiting-render set) and is unit-tested without a renderer in `route-timing.test.ts`; `route-timing-layout.tsx` holds `RouteTimingLayout` and the `useRouteRenderedMark` hook. A page calls the hook with `ROUTE.<name>.timingKey`.
- **A route that prefetches does it through `prefetchLoader`** (`apps/web/src/lib/route-prefetch.ts`), and supplies only which queries its URL implies: `export const ticketsLoader = prefetchLoader(({ request }) => [prefetchQuery(...)])`. The module owns the four decisions every prefetching route shares — await the queries (so the page mounts with its cache primed instead of rendering a skeleton), tolerate a rejection (the page owns its own error screen; throwing would hand the navigation to the router's error boundary, which has no way back), start several at once via `allSettled` (the pages fire theirs concurrently, so a serialized loader would be _earlier and slower_), and return `null` (react-query stays the cache layer). Issue #157 is what this is for: those four rules had been prose repeated once per route above four lines of code, and each route reached the module-level `queryClient` directly, so nothing could substitute it and none of the three had a test. Each query goes through `prefetchQuery(queryOptions(...))` — a closure, not the options object, because a query's key tuple and response type appear in contravariant positions in react-query's option types, so a heterogeneous list of them has no supertype short of `any`. The client is swappable (`setPrefetchQueryClient`), which is what makes a loader testable at all — see [testing.md](testing.md). Both the loader and the page must read the URL through the same parser (`parseTicketListParams`, `parseDashboardParams`), or a hand-edited `?sort=nonsense` primes one entry and the page reads a neighbouring one.
- **Dev-only tooling at `/__dev`** (never shipped). Three pages: `/__dev/map` is a project map — module graph, imports, layers, client routes, API endpoints with their guards, the Prisma models, and which client module calls which endpoint; `/__dev/tests` runs the repo's suites from the browser with streamed output; `/__dev/usage` reports what each GitHub issue was forecast to cost and what it actually cost in output tokens, read off this machine's Claude Code transcripts and one `gh issue list` call. All three are also linked from the sidebar's "Dev" group.
  - **Usage gathers nothing until Scan is pressed, and nothing anywhere caches the answer.** The other two pages fetch on load; this one reads every transcript the machine holds, and its claim is that the figures on screen were gathered at a named moment from a named directory. So `useUsageScan` is a `useMutation` rather than a `useQuery` (a query is something react-query is entitled to run for you — on mount, on focus, on reconnect), the middleware holds no copy between presses, and the page holds the last result until the next one. That is deliberately the opposite of the test runner beside it: a run is a long-lived process worth surviving a reload, a scan is a few seconds of reading that is cheaper to repeat than to invalidate. The join itself lives in `apps/web/dev/usage.ts` and is shared with `bun run tokens`, so the page and the terminal cannot report different figures for the same issue.
  - **`CLAUDE_TRANSCRIPT_DIR` and `GH_ISSUES_FILE` are the two seams that make any of it testable.** Neither source is something an assertion can name — the real transcript directory is derived from `cwd` + `homedir` and holds this machine's own spend, and what this repo's issues are titled changes every time somebody files one. So `resolveTranscriptDir` honours an override and `playwright.config.ts` points the E2E web server at `tests/e2e/fixtures/transcripts` (totals written down in that directory's `README.md`, restated as literals in `tests/e2e/dev-usage.spec.ts`), and `fetchIssueMetadata` (`dev/issues.ts`) honours one naming a file holding what `gh issue list --json …` would have printed. The page prints the directory it read, and the fixture titles carry the word “Fixture”, for the same reason: locally, `reuseExistingServer` will adopt a leftover Vite on 4001 that was started without either override, and the page then reports the developer's own transcripts against GitHub's real titles — which looks like a missing row rather than the wrong server.
    - **The listing override never falls back to `gh`**, and the E2E's listing fixture is written by the spec rather than checked in (`tests/e2e/fixtures/gh-issues.ts`, gitignored as `*.local.json`). Both follow from the same constraint: a web server's environment is fixed when it starts, so the only honest way to reach the no-`gh` state through the real middleware is for the file it names to be missing — and a fallback would have that case read live GitHub and pass or fail depending on whose machine it ran on.
    - **`gh` is available from a dev-server child, sanitiser and all** (#249, measured): its credential comes from the OS credential store, and no `.env*` file here declares a GitHub token, so `configuredKeys` has nothing to strip. Two things that are easy to break — the spawn's `cwd` must be the repo root (`gh` resolves the repository from the git remote of wherever it runs), and it must be **one** `gh issue list` call rather than a loop of `gh issue view`, which costs ~0.9s per issue against ~1.7s for all of them.
  - **The Usage table's column order is `USAGE_COLUMNS` in `src/dev/protocol.ts`, not the literal in `UsagePage.tsx`.** The same rule as `ROUTE` above and for the same reason: `UsagePage.test.tsx` and `dev-usage.spec.ts` both index a row by position, neither can import a `.tsx` page, and a column inserted in the middle would leave every assertion silently checking its neighbour. The page keys its column definitions by those names and renders `USAGE_COLUMNS.map(...)`, so a name without a definition — or a definition without a name — does not compile.
  - **Anything `gh` could not supply renders as an em dash meaning _unknown_, and a row with no `forecast/S|M|L` label gets no verdict.** Not "on target", not a default band: a verdict on work nobody estimated is a score the page invented, and it would move the accuracy figure the page exists to report. The one column that crosses the divide is the bucket, derived from the actual alone, so it survives a `gh` that does not.
  - **The row set is every issue with spend _plus_ every issue the listing calls open** (#251), so an issue nobody has started appears with its band, an empty actual and no verdict — and the forecast-coverage gap the PRD's second metric is about is a row you can see rather than an absence you have to know to look for. Open is the line: a _closed_ issue with no recorded spend was finished somewhere the scan cannot reach (another machine, or before these transcripts began), and a row for it would report the limits of the scan as a fact about the work. Two rules follow. `IssueSpend` is one nullable object on the wire rather than four nullable numbers, because the four figures are absent exactly together and a flat shape lets a row carry turns with no tokens; and nothing anywhere substitutes a zero for it — `bucketFor(0)` is `S`, so a forecast of `L` read against a zeroed row prints "under", and every unstarted issue in the backlog would sit in the table claiming to have beaten its estimate while dragging the percentiles and the accuracy figure with it. `bun run tokens` keeps those rows out of both. The page tells the two absences apart with `NotStarted` beside `Unknown` — the same em dash, different words on hover, because one means the question could not be asked and the other means the answer is _nothing yet_.
  - **Work on `main` is reported, as its own total and never as a row** (#253). Turns that ran on `main` or with no branch recorded belong to no issue and are a large share of everything a machine has done — 28% of all turns when the scan was written — so a page listing only issues reads as complete while omitting a quarter of the work. The scan used to count those turns and throw their output tokens away, which is why this was a change to what `apps/web/dev/usage.ts` accumulates and not only to what its two callers print; `UnattributedWork` on the wire carries **turns and output tokens, and deliberately not the other two** — `sessions` and `cacheRead` are questions about an issue, and a field on the wire is a promise that something reads it. A row is the obvious place for the total and the one place it cannot go: it has no issue number, nothing forecast it, and `bucketFor` would file its tokens in a band as though somebody had — which the distribution chart would then count and the accuracy figure would score. **A zero is rendered here where a row's figure would be an em dash**, and that does not contradict the "never substitute a zero" rule above — it is the other side of it. A row's figures are dashed because `bucketFor(0)` is `S`, so a zero there gets banded, scored and counted in the quartiles; nothing scores these two, so there is no score for a zero to invent, and a panel that vanished on one would read as the page not asking. (The plain counts elsewhere on the page — transcripts read, issues listed, issues with recorded spend — were never in that rule either.) A third case is neither attributed nor unattributed and must stay that way: a branch whose name carries no issue number is dropped, because `unattributed` means `main` or nothing at all.
  - Browser half in `apps/web/src/dev/`, node half in `apps/web/dev/` (a Vite plugin, `apply: "serve"`), wire types shared in `apps/web/src/dev/protocol.ts`. `tsconfig.node.json` includes `dev` so both ends are checked.
  - **Relative imports in `dev/` and in `vite.config.ts` carry their `.ts` extension, and use `import.meta.dirname` rather than `__dirname`.** Both are required by Vite's `configLoader: 'native'`, which is announced to become the default in a later major; until then Vite 8 prints a warning naming every offending line on each dev start. `allowImportingTsExtensions` is already on in `tsconfig.node.json`, so the extension costs nothing. Keep new files in this directory to the same rule — the warning is per-import, so one extensionless addition brings the whole block back.
  - Kept out of production by `import.meta.env.DEV` in `App.tsx` and `nav-items.ts` — Vite folds it to `false`, so Rollup drops the `import()` and emits no chunk. If you add an entry point to this code, check `.vite/stats.html` after a build.
  - The scan is regex-over-source with comments stripped first (`dev/scan.ts`), not a TS AST. It handles the import styles this repo uses; anything it cannot parse lands in the map's `warnings` rather than being dropped silently.
  - The map's filter bar has **two different reaches, and a new view has to pick one deliberately.** The workspace `Select` and the two toggles stop at the Graph and Modules tabs — Overview and Wiring report whole-project totals, and a project that shrank because you hid the tests would be worse than useless. The **search reaches all four**, and every match goes through `matchesQuery` in `dev/module-match.ts` rather than an inline `id.includes(...)`: the inline version is exactly how the box came to do nothing on Overview and Wiring, which are the tabs written last and the first one the page opens on. Wire a new view in by naming the fields it searches. Two rules that follow from it — an empty query matches _everything_, so callers filter unconditionally instead of branching; and a card heading whose list can narrow shows `countLabel(shown, total)`, because a heading still reading `12` over three rows is the same lie the frozen module counter used to tell. Scan `warnings` are deliberately exempt: a warning says the map you are reading is incomplete, so it outranks whatever you typed.
  - Test runs belong to the **dev server**, not the tab: reloading reconnects and replays, only Cancel stops one (it kills the process tree). Editing anything under `apps/web/dev/` restarts the dev server — it is a `vite.config.ts` dependency — which cancels any run in flight.
  - Anything spawned from the dev server must sanitise its environment first (`childEnv` in `dev/child-env.ts`, shared by the test runner and the Usage page's `gh` call). The dev script is `bunx --bun vite`, and `--bun` puts a fake `node` on PATH plus `NODE=…/bun-node-*/node.exe`; a child that inherits it sees Bun where it expects Node, and Vitest's `node --require …/suppress-warnings.cjs` worker launch turns into Bun trying to _install_ that path as a package. It also strips every key the repo's `.env*` files declare, because `dotenv-cli` won't override an inherited value — otherwise `.env.test` loses to the dev `PORT`/`DATABASE_URL` and the E2E database reset points at the dev database.
    - **And it is asynchronous.** `execFileSync` in a dev-server middleware is wrong twice over: it blocks the thread Vite answers every other request on for as long as the child runs, and its `timeout` option **does not work in that process**. Measured 2026-09-17 while wiring the Usage page's `gh` call: a Scan returned in 2.4s with `spawnSync gh ETIMEDOUT`, `signal=SIGTERM` and empty stderr — the child killed at once rather than after the 20 seconds it was given — so the page reported “no `gh`” on every press, while `bun run tokens` ran the identical call from a plain Bun process and succeeded. The dev server is `bunx --bun vite`, so the middleware runs on Bun's runtime; only the _synchronous_ spawn misbehaves. Use `promisify(execFile)` and let the handler be `async` — `only()` in `dev/plugin.ts` awaits a promise-returning handler and turns a rejection into a 500.
- **The per-page tutorial**: `<Tutorial pageKey={TUTORIAL_PAGE_KEY.x} />` (`apps/web/src/components/Tutorial.tsx`) is mounted once near the top of each of the eight main pages. It fetches `GET /api/tutorials/:pageKey`, pops up unprompted when the API says `shouldShow`, and posts `/api/tutorials/:pageKey/seen` on dismiss/finish so it does not show again. **If a change to one of these pages' UI or logic would make its existing tutorial steps misleading, bump that page's entry in `TUTORIAL_PAGE_VERSIONS`** (`packages/shared/src/index.ts`) — that is what re-shows it to users who already dismissed it. Editing the tutorial's own wording (via the admin editor at `/tutorials`) never needs this; only a page change that makes the _current_ steps wrong does.
- **The "new" nav badge** (issue #45): a small "New" text badge (`SidebarMenuBadge`, the same slot the unread-assignments count uses) on a `NavItem` (`apps/web/src/components/layout/nav-items.ts`), rendered by `AppSidebar` while `NEW_FEATURE_VERSIONS[key]` (`packages/shared/src/index.ts`) is ahead of what the signed-in user has seen, and dismissed permanently the first time they follow that link. To flag something new: add a key to `NEW_FEATURE_KEY`, give it a starting version in `NEW_FEATURE_VERSIONS`, and set `newFeatureKey` on the relevant `NavItem`. To re-flag something later (a page changed enough to be worth calling out again), bump its entry in `NEW_FEATURE_VERSIONS` — same trick as `TUTORIAL_PAGE_VERSIONS`, but there's no admin-editable content half here, only the code-level registry. Unlike `TutorialPageKey`, `NewFeatureKey` isn't a Postgres enum — the key set churns as things age out of "new", so it's a plain `String` column validated in code, and removing a key later needs no migration.
- **The "what's new" changelog** (issue #94): `ChangelogPopover` (`apps/web/src/components/layout/ChangelogPopover.tsx`), mounted once in `AppTopBar`. Unlike the tutorial and the "new" badge, its content is generated, not hand-authored or hand-versioned: `CHANGELOG_ENTRIES` (`packages/shared/src/changelog-entries.json`, re-exported from `packages/shared/src/index.ts`) is appended to by CI's `bump-version` job (`.github/workflows/ci.yml`, via `scripts/ci/record-changelog-entry.mjs`) on every push to `main`, one entry per `feat`/`fix` commit **on the merged branch** — a `chore`/`refactor`/etc. still bumps the version but adds no entry, because not every deploy is user-facing. The job checks out with `fetch-depth: 0` and reads `git log HEAD^2 --not HEAD^1`; both halves are load-bearing and were measured (issue #113). Under checkout's default shallow clone `HEAD^2` does not resolve at all, so the fallback read the merge commit's own "Merge pull request #N" subject and _no merge ever recorded an entry_; and reading only the branch tip drops the entry whenever a branch ends on a review fix-up over its `feat`, which is the ordinary shape of a branch here. A branch carrying two user-facing commits therefore yields two entries at the same version, and the popover lists both — `sort` there is stable, so they stay in the order CI recorded them. The popover reads entries straight out of `@ticket/shared` (no round trip for content); only the per-user "seen" flag is server state, `GET`/`POST /api/changelog/status` and `/seen`, mirroring the "new" badge's `NewFeatureSeen` shape but with one row per user rather than per key, since there is exactly one changelog stream. Versions compare numerically (`compareVersions`), not lexically — `"0.5.9"` sorts _after_ `"0.5.10"` as plain strings, which is backwards. **`CHANGELOG_LATEST_VERSION` is a sparse subsequence of deployed versions, not a second counter**: every entry's version is a genuine past value of `VITE_SENTRY_RELEASE` (see `releaseName()` in `apps/web/vite.config.ts`), so it can trail whatever's actually running in production after a `chore`-only deploy — that gap is intentional (nothing shipped worth telling a user about) and is not fixed by reading `VITE_SENTRY_RELEASE` into the seen-state comparison, which would light up the badge on deploys with no new content. See the doc comment on `ChangelogEntry` in `packages/shared/src/index.ts`.
- **Respect `prefers-reduced-motion`** for any animation that isn't already covered by a library default (Recharts honours it itself via `isAnimationActive: 'auto'`). Use the `useReducedMotion` hook (`apps/web/src/lib/use-reduced-motion.ts`) rather than a fresh `matchMedia` query — it already handles the jsdom-has-no-`matchMedia` case (defaults to reduced) and the mount-vs-effect race. See the stat tiles' count-up for the pattern.
- **Waiting states use `AiShine`** (`apps/web/src/components/AiShine.tsx`) — a light tracing the element's border, worn by the summary card and by both AI buttons so "a model is working" looks identical everywhere. Parent needs `relative`; the ring inherits the radius. The `ai-shine-ring` utility in `index.css` confines it to the border with a two-layer `mask` + `mask-composite: exclude`, and `ai-shine-beam` paints the gradient that travels inside it. Keep animations to `transform`/`opacity` per the note in that file: animating `background-position`, or spinning a conic gradient behind an `@property` angle, looks the same and repaints every frame. The beam uses its own `--ai-shine` / `--ai-shine-core` tokens rather than `--primary` — deliberately, and don't "fix" it back: `--primary` is oklch(0.432 …), a deep low-chroma green that reads as a faint olive line against the card, and these buttons are `disabled:opacity-50` for the entire time the shine is visible, so every colour is halved where it matters.
