# Frontend standards (`apps/web`)

Client-side conventions: forms, styling, UI controls, data fetching, notifications, dev tooling. Component testing lives in [testing.md](testing.md).

- Forms: **react-hook-form** + **zod** via `@hookform/resolvers/zod`. Define the schema, infer the values type with `z.infer`, disable inputs on `isSubmitting`, surface server errors in local state.
- Icons: **lucide-react**. Use `Loader2` with `animate-spin` for pending/loading states.
- Tailwind v4 (CSS-first, no `tailwind.config`). Theme tokens are CSS variables in `apps/web/src/index.css` under `:root` / `.dark`; reference them as `var(--background)` etc. shadcn/ui components live in `apps/web/src/components/ui/`. `:root` / `.dark` also set `color-scheme`, which is what themes the remaining browser-drawn UI (scrollbars, the `type="search"` clear button) — don't remove it.
- **UI controls: shadcn/ui only.** Selects, checkboxes, radios, switches, tabs, tooltips, popovers, dropdown menus, comboboxes — all of it comes from shadcn. Add what's missing with `bunx --bun shadcn@latest add <component>` (the repo is already configured: `apps/web/components.json`, style `radix-nova`, `radix-ui` installed). **Never** reach for a native control instead: a native `<select>`'s popup is drawn by the OS, so it ignores `--popover`/`--radius`/font tokens and looks foreign next to the shadcn controls beside it. This is not a matter of taste — a native `<select>` in the filter bar shipped white-on-white options in dark mode. If shadcn genuinely has no component for the need, **ask** rather than inventing one.
  - Radix primitives that open a floating layer (Select, DropdownMenu, Popover, Combobox) need jsdom shims for the Pointer Capture API, `scrollIntoView` and `ResizeObserver`. They're already installed in `apps/web/src/test/setup.ts` — no per-test setup needed.
  - Radix rejects `value=""` on a `SelectItem` (it reserves the empty string for "cleared"), so an "any"/"all" row needs its own non-empty token mapped at the component boundary.
  - `SelectLabel` reads its id from `SelectGroup`'s context and **throws** without one. Nothing above the pages is an error boundary, so a stray `<SelectLabel>` inside a `SelectContent` blanks the whole app the moment the dropdown opens — always wrap it in `<SelectGroup>`.
  - Testing them: they are **not** native selects, so `selectOptions` (RTL) and `selectOption` (Playwright) do not work. Click the trigger, then click `getByRole("option", { name })`. Assert the current value from the trigger's text, not `toHaveValue`.
- Data fetching: **axios** + **@tanstack/react-query**. Don't use `fetch` directly. Use the shared axios instance from `@/lib/api` (preconfigured with `baseURL: VITE_API_URL` and `withCredentials: true` for cookie-based sessions). Wrap every server call in `useQuery` / `useMutation` — pass the `signal` from the query function into axios for automatic cancellation. The `QueryClientProvider` is wired in `apps/web/src/main.tsx`.
- Notifications: **sonner** via the wrapper at `apps/web/src/components/ui/sonner.tsx` (re-exports `toast`, themes the `<Toaster />` from `useTheme`). The `<Toaster />` is mounted once in `apps/web/src/main.tsx`. Fire `toast.success(...)` on successful mutations and `toast.error(...)` on failure (in addition to surfacing the error inline in the form). Use `extractErrorMessage(err, fallback)` from `@/lib/errors` to pull the API error message out of axios errors consistently. In component tests, `sonner` is globally mocked in `apps/web/src/test/setup.ts` — `toast.*` are `vi.fn()` no-ops and `<Toaster />` renders `null`, so don't assert on toast DOM output.
- **A scrollable table goes in `<TableFrame label="…">`** (`apps/web/src/lib/table-frame.tsx`) — the shared border, rounding and `overflow-auto`, plus the three attributes that make the scroller operable: `tabIndex={0}`, `role="region"` and the required `label` as its `aria-label`. They are one decision, not three (issue #111): an `overflow-auto` div is not focusable, so a keyboard-only user cannot reach the columns that overflow right or the rows below the fold — sharpest on `UsersTable`, where scrolling horizontally at narrow widths _is_ the fix (#83) — but `tabIndex` alone buys an anonymous tab stop, and a `region` with no accessible name is not exposed as a landmark at all. `label` is required for exactly that reason; there is no class-string export to reach for instead. It is focusable whether or not it currently overflows: toggling on measured overflow makes a control appear and vanish as the window resizes, and jsdom reports every scroll dimension as `0`, so no test could hold it. Locked in by `tests/e2e/tickets.spec.ts` — focus the region, press PageDown, and the rows scroll while the sticky `<thead>` holds its place and the window stays put.
  - **The five desk tables use it; `ChartCard` does not, and that is a known gap, not the convention.** The dashboard's chart-to-table toggle (`apps/web/src/components/dashboard/ChartCard.tsx`) still renders its table into a bare `cn(CHART_HEIGHT_CLASS, "overflow-auto")` with no `tabIndex`, role or name — the same defect #111 fixed elsewhere, on a container that never shared `TABLE_FRAME` and so was outside that issue's scope. It bites harder there than it did here, because that table _is_ the chart's accessibility-relief path. Tracked as #123; don't read this bullet as saying the codebase is already uniform.
- **TanStack column sizing stays _uncontrolled_, and the reason is a race, not a preference** (issue #263). `TicketsTable` is the repo's only `useReactTable` call site and the only resizable table; it passes `state: { sorting }` and nothing else, and `columnSizing` must not be lifted back into a `useState` beside it. TanStack's resize handler fills a closure object with the new column sizes from **inside** the `setColumnSizingInfo` updater and reads that same object back from **inside** the `setColumnSizing` updater, so the two updates are a producer and a consumer that React only orders correctly when they share one update queue. Controlled, they did not share one: `columnSizing` was a hook declared above `useReactTable`, so React reached it first on every render where it could not eagerly evaluate the dispatches — which is any render with an update already pending on that fiber — and the consumer spread an **empty** object. The drag then applied nothing whatsoever and the column came back at the _exact_ width it started at, which is what made this read as a test flake rather than a bug: `data-resizing` still went true, the keyboard path (`nudge`, one plain `setColumnSizing`) was never affected, and it only fired under CI load. Uncontrolled, both updates land in the single `useState` inside `useReactTable` and are applied in dispatch order. Locked in by `apps/web/src/pages/TicketsTable.test.tsx`, whose three cases differ only in where React is allowed to flush: one event at a time (the control, which passed even before the fix), the whole drag batched into one `act`, and the whole drag batched behind an update already queued — Playwright cannot hold this, because in a browser the pending update is whatever the runner happened to be doing.
- **A route's path is declared once, in `ROUTE`** (`apps/web/src/lib/routes.ts`), together with the timing key it produces `performance` entries under. Nothing retypes a path: the router's `path`, `NavItem.to`, `<Link to>`, `navigate(...)`, a `pathname ===` comparison and the timing module's patterns all read `ROUTE.<name>.path`, and a ticket link goes through `ticketDetailPath(id)` rather than interpolating `/tickets/${id}`. `NavItem["to"]` is typed as `RoutePath` — the union of the record's paths — so a literal that no longer names a route stops compiling. Issue #151 is what this is for: the user-timing module used to keep its own copy of the three instrumented patterns, and a rename anywhere else made the match miss, the render mark no-op and the measure **stop existing** — no build error, no failing test, nothing in the log. The E2E could not catch it either, because it restated the key strings too; it imports `navigateMarkName`/`renderedMarkName`/`timeToDataMeasureName` now. Two constraints follow. `routes.ts` is **import-free** — no `@/…` alias, no React, no router — which is what lets `tests/e2e/route-timing.spec.ts` reach into it the way `dashboard-layout.spec.ts` reaches into `dashboard-panels.ts`; and `timingKey` is present only on instrumented routes, so `as const satisfies` makes `ROUTE.users.timingKey` a type error rather than an `undefined` that flows on into a mark name. The `/__dev/map` scanner resolves `path: ROUTE.<name>.path` against the record (`readRouteRecord` in `dev/scan.ts`) — a new way of writing a route path needs teaching there, or that route silently drops out of the map.
  - The timing module is split for the same reason: `route-timing.ts` is the pure half (entry names, the pathname→key lookup, the awaiting-render set) and is unit-tested without a renderer in `route-timing.test.ts`; `route-timing-layout.tsx` holds `RouteTimingLayout` and the `useRouteRenderedMark` hook. A page calls the hook with `ROUTE.<name>.timingKey`.
- **A route that prefetches does it through `prefetchLoader`** (`apps/web/src/lib/route-prefetch.ts`), and supplies only which queries its URL implies: `export const ticketsLoader = prefetchLoader(({ request }) => [prefetchQuery(...)])`. The module owns the four decisions every prefetching route shares — await the queries (so the page mounts with its cache primed instead of rendering a skeleton), tolerate a rejection (the page owns its own error screen; throwing would hand the navigation to the router's error boundary, which has no way back), start several at once via `allSettled` (the pages fire theirs concurrently, so a serialized loader would be _earlier and slower_), and return `null` (react-query stays the cache layer). Issue #157 is what this is for: those four rules had been prose repeated once per route above four lines of code, and each route reached the module-level `queryClient` directly, so nothing could substitute it and none of the three had a test. Each query goes through `prefetchQuery(queryOptions(...))` — a closure, not the options object, because a query's key tuple and response type appear in contravariant positions in react-query's option types, so a heterogeneous list of them has no supertype short of `any`. The client is swappable (`setPrefetchQueryClient`), which is what makes a loader testable at all — see [testing.md](testing.md). Both the loader and the page must read the URL through the same parser (`parseTicketListParams`, `parseDashboardParams`), or a hand-edited `?sort=nonsense` primes one entry and the page reads a neighbouring one.
- **Dev-only tooling at `/__dev`** (never in a production build — Railway's `develop` environment runs the dev server itself, behind HTTP Basic Auth; see the #314 sub-bullet below). Three pages: `/__dev/map` is a project map — module graph, imports, layers, client routes, API endpoints with their guards, the Prisma models, and which client module calls which endpoint; `/__dev/tests` runs the repo's suites from the browser with streamed output; `/__dev/usage` reports what each GitHub issue was forecast to cost and what it actually cost in output tokens, read off this machine's Claude Code transcripts and one `gh issue list` call. All three are also linked from the sidebar's "Dev" group.
  - **Usage gathers nothing until Scan is pressed, and nothing anywhere caches the answer.** The other two pages fetch on load; this one reads every transcript the machine holds, and its claim is that the figures on screen were gathered at a named moment from a named directory. So `useUsageScan` is a `useMutation` rather than a `useQuery` (a query is something react-query is entitled to run for you — on mount, on focus, on reconnect), the middleware holds no copy between presses, and the page holds the last result until the next one. That is deliberately the opposite of the test runner beside it: a run is a long-lived process worth surviving a reload, a scan is a few seconds of reading that is cheaper to repeat than to invalidate. The join itself lives in `apps/web/dev/usage.ts` and is shared with `bun run tokens`, so the page and the terminal cannot report different figures for the same issue.
  - **`CLAUDE_TRANSCRIPT_DIR` and `GH_ISSUES_FILE` are the two seams that make any of it testable.** Neither source is something an assertion can name — the real transcript directory is derived from `cwd` + `homedir` and holds this machine's own spend, and what this repo's issues are titled changes every time somebody files one. So `resolveTranscriptDir` honours an override and `playwright.config.ts` points the E2E web server at `tests/e2e/fixtures/transcripts` (totals written down in that directory's `README.md`, restated as literals in `tests/e2e/dev-usage.spec.ts`), and `fetchIssueMetadata` (`dev/issues.ts`) honours one naming a file holding what `gh issue list --json …` would have printed. The page prints the directory it read, and the fixture titles carry the word “Fixture”, for the same reason: locally, `reuseExistingServer` will adopt a leftover Vite on 4001 that was started without either override, and the page then reports the developer's own transcripts against GitHub's real titles — which looks like a missing row rather than the wrong server.
    - **The listing override never falls back to `gh`**, and the E2E's listing fixture is written by the spec rather than checked in (`tests/e2e/fixtures/gh-issues.ts`, gitignored as `*.local.json`). Both follow from the same constraint: a web server's environment is fixed when it starts, so the only honest way to reach the no-`gh` state through the real middleware is for the file it names to be missing — and a fallback would have that case read live GitHub and pass or fail depending on whose machine it ran on.
    - **`gh` is available from a dev-server child, sanitiser and all** (#249, measured): its credential comes from the OS credential store, and no `.env*` file here declares a GitHub token, so `configuredKeys` has nothing to strip. Two things that are easy to break — the spawn's `cwd` must be the repo root (`gh` resolves the repository from the git remote of wherever it runs), and it must be **one** `gh issue list` call rather than a loop of `gh issue view`, which costs ~0.9s per issue against ~1.7s for all of them.
  - **The Usage table opens on four columns, and one control appends the other three** (#271). `USAGE_SPINE` (`title`, `out`, `comparison`) is what a scan shows; `USAGE_DETAIL` (`turns`, `sessions`, `cacheRead`) comes back on a shadcn `Toggle` above the table, `variant="outline"` like the project map's pair, named by `aria-label` rather than by its chip. **The contract is two lists whose concatenation is the order, not one list with a `detail` flag**, and the reason is positional: detail columns _append_, so a spine cell sits at the same index in both states and the one `CELL` map each suite builds from `USAGE_COLUMNS` serves both. Two maps could disagree, and the suites that index a row by position would go on passing while asserting against a neighbouring cell. Bringing the three back is allowed to reintroduce horizontal scrolling — it is opt-in, and `TableFrame` already makes the scroller focusable and named. The E2E holds the width claim by comparing the scroller's `scrollWidth` to its `clientWidth` at 1280px rather than by counting columns — but **know what that assertion is worth before leaning on it.** Measured 2026-09-19 against a real scan (103 issues, 1280px window): the frame reads 1218/1218 with the detail columns _shown_, and 1248/1248 both ways on the E2E fixture. Seven columns already fit; the scroll the PRD complains about was **nine**, and #270's merged comparison cell is what removed it. The toggle buys less to read, not less to scroll, and the assertion is a regression guard — a `min-w` on the `<table>`, a column escaping `Title`'s `max-w-[26rem]` cap, a fifth column in the spine.
  - **Every figure column and the issue number rank the table from their header, and a row with no recorded spend sinks to the bottom in _both_ directions whatever column is sorted** (#272). The comparator is `src/dev/usage-sort.ts` — pure, and unit-tested over made-up rows, because the sink is a property of the comparator rather than of the output-tokens column: `usage-sort.test.ts` asks it of every key in both directions. The header markup copies `ModuleTable` exactly (`aria-sort` on the `<th>`, a button inside it, an `aria-hidden` `ArrowUp`/`ArrowDown`, clicking the active column flips it); a column nothing ranks by carries **no** `aria-sort` rather than `"none"`, which would advertise a control that is not there. The sink _is_ the ticket, not a detail of it. `bucketFor(0)` is `S`, so an unstarted row read as zero arrives first in an ascending sort as the cheapest work in the repository, and its band would then score it as having come in under — the same lie the cells refuse to tell (`NotStarted`), told in the ordering instead. A row that really spent zero is a measurement and still ranks as the cheapest work there is; nothing substitutes one for the other. The sortable set is a **record keyed by `"issue" | keyof IssueSpend`** (`SORTABLE`, with `USAGE_SORT_KEYS` as its walkable half), so it is exhaustive by construction — a list could only be checked for membership, and a fifth figure on `IssueSpend` would have arrived with no way to rank by it. `title` and `comparison` cannot be named by that key type at all, which is where their exclusion stops being a comment: a name nobody ranks a spend table by and one that can be absent (a second sink rule, for a different reason), and three facts in one cell. Which column offers which key is said once too — `COLUMNS` is typed so a column whose name is a sort key **must** carry `sort`, and it must be its own name, because the two lists were otherwise free to drift: dropping `sort` from `turns` left the comparator's tests green while no header offered it, and a copy-pasted `sort: "turns"` on `cacheRead` compiled and ranked the wrong column. The default is output tokens descending because that **is** the order `joinIssues` returns: since #286 the node half imports `DEFAULT_USAGE_SORT` and `sortIssues` and sorts the wire rows with them, so the first render after a scan is the order the server sent rather than an order that reproduces it. It had been `rank(b) - rank(a) || a.issue - b.issue` over there against the sink plus this key here — one claim written twice, and `dev-usage-guardrail.spec.ts` measured the cost: reversing either expression moved exactly one of the two surfaces, so nothing but inspection held them level. The issue-number tie-break sits **outside** the direction flip, which is what makes the order total, and that is now load-bearing rather than tidy: a default whose tie-break reversed with the direction would be total in one direction only, and `joinIssues` would need a rule of its own again for the other.
    - **The chosen sort is `UsagePage`'s state, not `SpendTable`'s, and the reason is measured rather than stylistic.** `useUsageScan` is a `useMutation`, and a mutation clears its `data` the moment it is fired (`case "pending"` sets `data: undefined` in query-core), so `report` is null for the length of the read, the `report &&` gate closes and the table unmounts. Anything kept inside it is thrown away by the press of Scan that re-asks the same question — which is exactly what the acceptance criterion "the sort survives a re-scan" is about. **#271's detail toggle moved up with it**, and had to: `turns`, `sessions` and `cacheRead` only have a header while it is on, so a sort on one of them surviving a re-scan _without_ the columns would satisfy "the chosen sort survives" and break "the active column shows its direction" in the same render — a ranking with no arrow, no `aria-sort` and nothing on screen saying why. The two are one `UsageTableView` for that reason. The same hole is reachable by hand, so hiding the detail columns while the sort is on one of them **returns the sort to the default**: going back to the order the rows arrived in is the one outcome that can still be announced, and it happens in the gesture that caused it.
  - **The Usage filter bar's reach is the table and nothing else, and that is the slice's decision rather than its implementation** (#273). A debounced `type="search"` box above the table narrows it on the issue number — matched as the row prints it, `#101`, so the hash out of a commit message is a term that matches — and on the title, through `matchesQuery` in `dev/module-match.ts` rather than an inline `includes`. What it must not touch is everything else on the page: the accuracy figure, the distribution's quartiles, the unattributed total and the gathered-at line all read `report.issues` on `UsagePage` and never see the filtered rows. The accuracy figure is the number somebody might quote, so a filter that moved it would turn a claim about this repository into a claim about a search box — the map's bar next door has two different reaches for its own controls, which is why a new filtering surface picks one deliberately instead of inheriting one. `dev-usage.spec.ts` holds it by comparing the three panels' `textContent` either side of a narrowing, not by re-reading a figure out of each. Four rules follow. The query lives in `UsageTableView` beside the sort and the detail toggle, for the measured reason #272 gives — the mutation clears its `data` while it reads, so anything kept inside `SpendTable` is thrown away by the press of Scan that re-asks the same question — and it is the **live** term there, debounced where it is spent (`useDebouncedValue`, 150 ms, the map's number) rather than lifted already settled, which would make every keystroke wait to appear in its own box. It is **not** in the URL, unlike the tickets list and the dashboard: a scan does not survive a reload, so a restored query would deserialize onto an empty page and describe rows that are not there. The count is `countLabel(shown, total)` from the same module, in a **visible** line on the bar rather than in the frame's `aria-label` where the plan first put it — `TableFrame`'s name is a landmark name, and rewriting it per keystroke would announce a new title as you type while still leaving a sighted developer counting rows. And a query that matches nothing renders its empty state _below_ the bar rather than instead of it, because the whole-block empty state above it (no issues at all) would take the box away with the rows and strand the query with nothing left to clear it from.
  - **The Usage bar's three facet selects are the _vocabulary_, not an inventory of the rows on screen** (#274). Forecast band, verdict and started-versus-unstarted (`src/dev/UsageFilters.tsx`, predicates and — since #297 — the vocabulary beside them in `src/dev/usage-facets.ts`, as `USAGE_FACETS` / `USAGE_FACET_KEYS` / `UsageFacets`). Every band is offered including `XL` and every verdict including ones nothing currently lands in, which is what makes "narrow to a band and find the table empty" an answer a developer can ask for — derived from the rows instead, a facet could never produce the empty state at all and the question with the answer "none" would be the one question the bar cannot put. They are `&&`'d with `matchesQuery` in one pass, so "they compose" holds by construction and `countLabel(shown, total)` describes all four controls without any of them reporting itself. Four things follow. The `any` row needs a **non-empty** token (`ANY_FACET`): Radix reserves `""` for _cleared_ and throws on a `SelectItem` whose value is it, which `ProjectMapPage`'s workspace select learned first. A row carrying no value for a facet — no band, no verdict — is in **none** of that facet's results rather than in a default one, and `started` asks `spend !== null` rather than `out > 0`, because `bucketFor(0)` is `S` and a row that really spent zero is a measurement: the page's central distinction, told in a filter instead of in a cell. The state rides in `UsageTableView` with the sort, the detail toggle and the query, for the measured reason #272 gives. And `USAGE_NO_MATCH` was reworded to name _these filters_ rather than the search, because any of the four can empty the table on its own and sending a developer to clear a term that was never there is worse than saying nothing.
    - **It is also the slice that moved the chart fixtures, and that cost was named in the ticket rather than discovered.** `tests/e2e/fixtures/transcripts` held no over-budget row at all, so a verdict facet's only testable outcome was "matches nothing" — which a filter that did nothing would also produce. `#105` (90,000 output tokens against `forecast/S`) is what makes it testable, and adding a _third_ issue with recorded spend — a fourth row — moved `CHARTS.accuracy` from 1/1 to 1/2, p75 from 20,000 to 90,000 and the measured count from two to three, all of which are #252's assertions. An over-budget row **cannot** be small — `over` against the smallest band means at least 60,000 — so it also leads the default ranking and every positional row assertion in `dev-usage.spec.ts` moved with it; those that are not about the order now address a row by its issue number (`rowFor`). The arithmetic lives in that directory's `README.md`, and the fixture, the README and the constants are one commit so no intermediate commit is red.
  - **The narrowing is a module, and `SpendTable` renders the rows it is handed** (#287). `src/dev/usage-view.ts` — pure — owns `UsageTableView`, `DEFAULT_USAGE_TABLE_VIEW`, `visibleRows(issues, view)` and `withDetail(view, next)`, absorbing the `matchesQuery`/`matchesFacets` `&&`, the `sortIssues` call over what they left, and the set of sort keys that only exist while the detail columns are shown. It was all real logic inside a `.tsx` module, so the only way to ask “what does this filter show” was to mount a page, stub axios, press Scan and read the rows back out of the DOM — which is how `UsagePage.test.tsx` reached 1,726 lines. #287 made that question reachable rather than answering it twice, and #288 spent it — see the end of this bullet. The three modules under it each answer about _one_ thing (`usage-sort.ts` an ordering, `usage-facets.ts` a predicate, `module-match.ts` a substring) and none of them can say whether the four controls narrow the **same** list in the order that keeps the ranking honest — which is exactly where a filter goes wrong: two passes instead of one `&&`, or a sort applied before the narrowing rather than after it. `usage-view.test.ts` asks that directly, importing no component. **#288 then retired those page-level cases**, and the split it left is the one to copy for the next table: what a narrowing shows is `usage-view.test.ts`'s, over made-up rows; the four claims that need a render but not a page — the `aria-sort` vocabulary, the search debounce, the detail toggle calling `withDetail`, the selects' resting labels — are `SpendTable.test.tsx`, mounted with bare RTL `render` and a `useState` standing in for the page; and a control reaching a real reading of real transcripts stays `dev-usage.spec.ts`'s, untouched. `UsagePage.test.tsx` went from 1,726 lines to 901. Three things the move deliberately did **not** change. The state still lives on `UsagePage`, which is #272's measured decision — these are pure functions _over_ a view, not a hook, and that is what lets the page hold it. `DETAIL_SORT_KEYS` is now `USAGE_DETAIL satisfies readonly UsageSortKey[]` rather than a map through `COLUMNS[name].sort`: the same compile-time claim that every detail column is rankable, said where a `.tsx` import is not available. And `SpendTable` keeps the debounce, because the settled term is substituted on its way into `visibleRows` — the memo rebuilds the three fields field by field rather than spreading `view`, or every keystroke re-filters and the 150 ms buys nothing. `visibleRows` takes `Pick<UsageTableView, "sort" | "query" | "facets">` and **not** the whole view, which is a claim rather than a tidy signature: the detail toggle changes which columns are drawn and never which rows, so naming it would put `detail` in that dependency list and re-filter every row on a press that changed nothing — the one case where the toggle does move the rows is the sort reset, and that arrives as a changed `sort`.
  - **The Usage table is `src/dev/SpendTable.tsx`, and its column order is `USAGE_COLUMNS` in `src/dev/usage-copy.ts`, not the literal beside the definitions.** The same rule as `ROUTE` above and for the same reason: `UsagePage.test.tsx` and `dev-usage.spec.ts` both index a row by position, neither can import a `.tsx` module, and a column inserted in the middle would leave every assertion silently checking its neighbour. `SpendColumns.tsx` keys its column definitions by those names and walks `USAGE_SPINE` or `USAGE_COLUMNS` depending on the toggle above it, so a name in either half without a definition — or a definition without a name — does not compile. The toggle's accessible name is in the contract too (`USAGE_DETAIL_LABEL`), for the reason the mark names are: neither suite can import a `.tsx` module, so a retyped label would leave both querying a control that no longer exists. The table left `UsagePage.tsx` in #270, which is also where four columns became three: `UsagePage.tsx` keeps what describes a _reading_ (`Gathered`, `Unattributed`, the scan mutation) and `SpendTable.tsx` holds everything that renders an issue — four modules since #297: `SpendCells.tsx` (the absence markers, the bands, the comparison cell), `SpendColumns.tsx` (the column record and its sortable header), `SpendTableBar.tsx` (the search box, the facets, the count and the toggle), and `SpendTable.tsx` itself (the debounce, `visibleRows`, the empty states and the markup).
    - **The forecast band, the band the spend landed in and the verdict are one cell** (`comparison`), reading `M 60-150k → S <60k` and then the word. They were four columns with `out` between them, which spelled the comparison out across the width of the table and is why nine columns would not fit at 1280px. `out` still stands alone — it is the figure the page exists for. The merge is what the two markers in the next bullet now have to survive: they sit an inch apart inside one cell, and `Comparison`'s half order (forecast, arrow, landed, verdict) is what says which absence a dash is. That order is held by two hover tests rather than by the compiler, unlike the columns around it — a reason to be careful about adding anything else to the cell.
  - **Anything `gh` could not supply renders as an em dash meaning _unknown_, and a row with no `forecast/S|M|L` label gets no verdict.** Not "on target", not a default band: a verdict on work nobody estimated is a score the page invented, and it would move the accuracy figure the page exists to report.
