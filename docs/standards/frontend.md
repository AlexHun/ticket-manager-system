# Frontend standards (`apps/web`)

Client-side conventions: forms, styling, UI controls, data fetching, notifications. Component testing lives in [testing.md](testing.md); how a screen looks and behaves lives in [design.md](design.md) and [design-states.md](design-states.md).

- Forms: **react-hook-form** + **zod** via `@hookform/resolvers/zod`. Define the schema, infer the values type with `z.infer`, disable inputs on `isSubmitting`, surface server errors in local state.
- Icons: **lucide-react**. Use `Loader2` with `animate-spin` for pending/loading states.
- Tailwind v4 (CSS-first, no `tailwind.config`). Theme tokens are CSS variables in `apps/web/src/index.css` under `:root` / `.dark`; reference them as `var(--background)` etc. shadcn/ui components live in `apps/web/src/components/ui/`. `:root` / `.dark` also set `color-scheme`, which is what themes the remaining browser-drawn UI (scrollbars, the `type="search"` clear button) — don't remove it.
- **UI controls: shadcn/ui only.** Selects, checkboxes, radios, switches, tabs, tooltips, popovers, dropdown menus, comboboxes — all of it comes from shadcn. Add what's missing with `bunx --bun shadcn@latest add <component>` (the repo is already configured: `apps/web/components.json`, style `radix-nova`, `radix-ui` installed). **Never** reach for a native control instead: a native `<select>`'s popup is drawn by the OS, so it ignores `--popover`/`--radius`/font tokens and looks foreign next to the shadcn controls beside it. This is not a matter of taste — a native `<select>` in the filter bar shipped white-on-white options in dark mode. If shadcn genuinely has no component for the need, **ask** rather than inventing one. A native `<select>`, checkbox or radio outside `src/components/ui/` fails `apps/web/dev/standards-guard.test.ts` (#390).
  - Radix primitives that open a floating layer (Select, DropdownMenu, Popover, Combobox) need jsdom shims for the Pointer Capture API, `scrollIntoView` and `ResizeObserver`. They're already installed in `apps/web/src/test/setup.ts` — no per-test setup needed.
  - Radix rejects `value=""` on a `SelectItem` (it reserves the empty string for "cleared"), so an "any"/"all" row needs its own non-empty token mapped at the component boundary.
  - `SelectLabel` reads its id from `SelectGroup`'s context and **throws** without one. Nothing above the pages is an error boundary, so a stray `<SelectLabel>` inside a `SelectContent` blanks the whole app the moment the dropdown opens — always wrap it in `<SelectGroup>`.
  - Testing them: they are **not** native selects, so `selectOptions` (RTL) and `selectOption` (Playwright) do not work. Click the trigger, then click `getByRole("option", { name })`. Assert the current value from the trigger's text, not `toHaveValue`.
- Data fetching: **axios** + **@tanstack/react-query**. Don't use `fetch` directly. Use the shared axios instance from `@/lib/api` (preconfigured with `baseURL: VITE_API_URL` and `withCredentials: true` for cookie-based sessions). Wrap every server call in `useQuery` / `useMutation` — pass the `signal` from the query function into axios for automatic cancellation. The `QueryClientProvider` is wired in `apps/web/src/main.tsx`. A direct `fetch(` anywhere under `src/` or `dev/` fails the standards guard (`apps/web/dev/standards-guard.test.ts`).
- **`bun run lint` holds the web app to four rules, all errors** (#535): the backend's `@typescript-eslint/no-floating-promises` and `@typescript-eslint/no-misused-promises` ([conventions.md](conventions.md) has the gate, its cost and how to exempt one line), plus `react-hooks/rules-of-hooks` and `react-hooks/exhaustive-deps`. CI's `check` job runs it; no hook does. The first sweep found 20 violations and fixed every one in code, with no exemption.
  - **A promise handed to something that expects `void` is `void`ed where it is handed over**: `onClick={() => void handleSignOut()}` (`AppTopBar`), and `void navigate(…)`, since react-router's data-router `navigate` returns a promise. `void` swallows nothing — a rejection still reaches the browser as an unhandled rejection, as it did before — it writes down that the promise floats on purpose. Where a failure should be handled, handle it inside the handler, as `PipelineSimulator`'s submit does with a `.catch`.
  - **`no-misused-promises` stays on for JSX attributes, react-hook-form included**, so a form reads `onSubmit={(event) => void handleSubmit(onSubmit)(event)}`. `checksVoidReturn: { attributes: false }` would quiet `handleSubmit` by also quieting every `onClick={async …}` in the app, which is the case the rule is here for. And `handleSubmit` is not a false positive: its promise rejects with whatever `onSubmit` throws (react-hook-form 7.85 catches it, updates `formState`, then rethrows), so an `onSubmit` that does not catch its own failure does leave a rejection floating.
  - **An `exhaustive-deps` miss is fixed by what the effect means, never by dropping the dependency or a disable.** A value an effect reads but must not re-run on goes through `useEffectEvent`: `TicketsPage` writes the settled search through one, since `update` is a new function every render, and `ArchitectureView` reads `selectedId` through one, since only a change of level moves focus. A helper an effect calls becomes a `useCallback` over what it reads (`GraphCanvas`'s `moveView`, over `reducedMotion`, which that effect already watched). A dependency written as a property path is lifted into a local first (`TicketDetailPage`'s `ticketId`), so the effect watches exactly what it reads. None of the four changed when its effect runs.
- Notifications: **sonner** via the wrapper at `apps/web/src/components/ui/sonner.tsx` (re-exports `toast`, and pins the `<Toaster />` to `theme="dark"`: the app has one theme, and sonner's own default, `"system"`, would follow the OS and put light toasts on the dark shell). The `<Toaster />` is mounted once in `apps/web/src/main.tsx`. Fire `toast.success(...)` on successful mutations and `toast.error(...)` on failure (in addition to surfacing the error inline in the form). Use `extractErrorMessage(err, fallback)` from `@/lib/errors` to pull the API error message out of axios errors consistently. **One mutation toasts nothing, on purpose:** `useFollowWelcomeStep` (`@/lib/demo-queries`, #464) is a tally fired as a welcome step's link navigates, so by the time it could fail the visitor is already where they asked to go, and a lost figure is the owner's, not something the visitor can act on. In component tests, `sonner` is globally mocked in `apps/web/src/test/setup.ts` — `toast.*` are `vi.fn()` no-ops and `<Toaster />` renders `null`, so don't assert on toast DOM output.
- **A scrollable table goes in `<TableFrame label="…">`** (`apps/web/src/lib/table-frame.tsx`) — the shared border, rounding and `overflow-auto`, plus the three attributes that make the scroller operable: `tabIndex={0}`, `role="region"` and the required `label` as its `aria-label`. They are one decision, not three (issue #111): an `overflow-auto` div is not focusable, so a keyboard-only user cannot reach the columns that overflow right or the rows below the fold — sharpest on `UsersTable`, where scrolling horizontally at narrow widths _is_ the fix (#83) — but `tabIndex` alone buys an anonymous tab stop, and a `region` with no accessible name is not exposed as a landmark at all. `label` is required for exactly that reason; there is no class-string export to reach for instead. It is focusable whether or not it currently overflows: toggling on measured overflow makes a control appear and vanish as the window resizes, and jsdom reports every scroll dimension as `0`, so no test could hold it. Locked in by `tests/e2e/tickets.spec.ts` — focus the region, press PageDown, and the rows scroll while the sticky `<thead>` holds its place and the window stays put.
  - **`ChartCard` uses it too, since #123 (closed).** The dashboard's chart-to-table toggle (`apps/web/src/components/dashboard/ChartCard.tsx`) renders its table into `<TableFrame label={title}>` at `CHART_HEIGHT_CLASS`, so the card's title names the region. That table is the chart's accessibility-relief path, which made it the sharper case of the defect #111 fixed on the desk tables: a relief path the keyboard cannot scroll is no relief. It had sat outside #111's scope only because it never shared the class string the desk tables shared before `TableFrame` replaced it.
- **TanStack column sizing stays _uncontrolled_, and the reason is a race, not a preference** (issue #263). `TicketsTable` is the repo's only `useReactTable` call site and the only resizable table; it passes `state: { sorting }` and nothing else, and `columnSizing` must not be lifted back into a `useState` beside it. TanStack's resize handler fills a closure object with the new column sizes from **inside** the `setColumnSizingInfo` updater and reads that same object back from **inside** the `setColumnSizing` updater, so the two updates are a producer and a consumer that React only orders correctly when they share one update queue. Controlled, they did not share one: `columnSizing` was a hook declared above `useReactTable`, so React reached it first on every render where it could not eagerly evaluate the dispatches — which is any render with an update already pending on that fiber — and the consumer spread an **empty** object. The drag then applied nothing whatsoever and the column came back at the _exact_ width it started at, which is what made this read as a test flake rather than a bug: `data-resizing` still went true, the keyboard path (`nudge`, one plain `setColumnSizing`) was never affected, and it only fired under CI load. Uncontrolled, both updates land in the single `useState` inside `useReactTable` and are applied in dispatch order. Locked in by `apps/web/src/pages/TicketsTable.test.tsx`, whose three drag-race cases differ only in where React is allowed to flush: one event at a time (the control, which passed even before the fix), the whole drag batched into one `act`, and the whole drag batched behind an update already queued — Playwright cannot hold this, because in a browser the pending update is whatever the runner happened to be doing.
  - **The same symptom came back with the state right, and that is a different bug** (#313). Twice on CI after the fix (runs 35584773994 and 36008583266), a drag again read the default 227.36px. The second run kept traces, and their DOM snapshots held the dragged `<col>` widths while `getBoundingClientRect` still reported an older layout — the default in the failing attempt, and only the first half of the drag in a retry that passed because half was already "wider". It never reproduced locally: not under CPU throttling, and not in a static copy of the table on Windows or in the Linux Playwright image. So two defences went in without a red loop. Each `<th>` carries its column's width as well as the `<col>` (`HeaderCell`'s `width`, held by `TicketsTable.test.tsx`), so a resize restyles the measured cell too — nothing changes on screen, since fixed layout already reads the `<col>`, and whether it closes the lag is unproven. And the drag tests read `settledSubjectWidth` rather than one width straight after `mouse.up()`: it polls until Subject has moved in the expected direction _and_ its rendered width matches what the `<col>`s imply (`col × table ÷ Σcols`, fixed layout's proportional share). The second condition is the one that matters — a width that had merely moved and held steady would have passed on the first half of a drag, which one of the traces read. If it fires again, check a trace's DOM snapshots before the component: a `<col>` that moved means this bullet, and one that did not means #263's.
- **A route's path is declared once, in `ROUTE`** (`apps/web/src/lib/routes.ts`), together with the timing key it produces `performance` entries under. Nothing retypes a path: the router's `path`, `NavItem.to`, `<Link to>`, `navigate(...)`, a `pathname ===` comparison, a full-page navigation (`window.location.href = …`, `window.location = …`, `location.assign(…)`, `location.replace(…)`) and the timing module's patterns all read `ROUTE.<name>.path`, and a ticket link goes through `ticketDetailPath(id)` rather than interpolating `/tickets/${id}`. `NavItem["to"]` is typed as `RoutePath` — the union of the record's paths — so a literal that no longer names a route stops compiling. `navigate()`, `<Navigate to>`, `<Link to>`, a `pathname ===` comparison, an assignment to `location.href` or `window.location` and a call to `location.assign()` or `location.replace()` (with or without `window.`) get no such compile error, so a path literal in any of them under `src/` fails the standards guard instead (`apps/web/dev/standards-guard.test.ts`, #390), as one in a spec's `page.goto` under `tests/e2e` does ([conventions.md](conventions.md)'s one-owner rule) — five sites had retyped the dashboard's `"/"` before it existed, and #521's `window.location.href = "/"` reached `develop` before the guard read the two `location` forms (#544). Issue #151 is what this is for: the user-timing module used to keep its own copy of the three instrumented patterns, and a rename anywhere else made the match miss, the render mark no-op and the measure **stop existing** — no build error, no failing test, nothing in the log. The E2E could not catch it either, because it restated the key strings too; it imports `navigateMarkName`/`renderedMarkName`/`timeToDataMeasureName` now. Two constraints follow. `routes.ts` is **import-free** — no `@/…` alias, no React, no router — which is what lets `tests/e2e/route-timing.spec.ts` reach into it the way `dashboard-layout.spec.ts` reaches into `dashboard-panels.ts`; and `timingKey` is present only on instrumented routes, so `as const satisfies` makes `ROUTE.users.timingKey` a type error rather than an `undefined` that flows on into a mark name. The `/__dev/map` scanner resolves `path: ROUTE.<name>.path` against the record (`readRouteRecord` in `dev/scan.ts`) — a new way of writing a route path needs teaching there, or that route silently drops out of the map.
  - The timing module is split for the same reason: `route-timing.ts` is the pure half (entry names, the pathname→key lookup, the awaiting-render set) and is unit-tested without a renderer in `route-timing.test.ts`; `route-timing-layout.tsx` holds `RouteTimingLayout` and the `useRouteRenderedMark` hook. A page calls the hook with `ROUTE.<name>.timingKey`.
- **A route that prefetches does it through `prefetchLoader`** (`apps/web/src/lib/route-prefetch.ts`), and supplies only which queries its URL implies: `export const ticketsLoader = prefetchLoader(({ request }) => [prefetchQuery(...)])`. The module owns the four decisions every prefetching route shares — await the queries (so the page mounts with its cache primed instead of rendering a skeleton), tolerate a rejection (the page owns its own error screen; throwing would hand the navigation to the router's error boundary, which has no way back), start several at once via `allSettled` (the pages fire theirs concurrently, so a serialized loader would be _earlier and slower_), and return `null` (react-query stays the cache layer). Issue #157 is what this is for: those four rules had been prose repeated once per route above four lines of code, and each route reached the module-level `queryClient` directly, so nothing could substitute it and none of the three had a test. Each query goes through `prefetchQuery(queryOptions(...))` — a closure, not the options object, because a query's key tuple and response type appear in contravariant positions in react-query's option types, so a heterogeneous list of them has no supertype short of `any`. The client is swappable (`setPrefetchQueryClient`), which is what makes a loader testable at all — see [testing.md](testing.md). Both the loader and the page must read the URL through the same parser (`parseTicketListParams`, `parseDashboardParams`), or a hand-edited `?sort=nonsense` primes one entry and the page reads a neighbouring one.
- **Dev-only tooling at `/__dev`** — the project map, the test runner, Usage and Sessions, and the Vite plugin behind them — has its own standards: [dev-tools.md](dev-tools.md).
- **The per-page tutorial**: `<Tutorial pageKey={TUTORIAL_PAGE_KEY.x} />` (`apps/web/src/components/Tutorial.tsx`) is mounted once near the top of each of the nine main pages. It fetches `GET /api/tutorials/:pageKey`, pops up unprompted when the API says `shouldShow`, and posts `/api/tutorials/:pageKey/seen` on dismiss/finish so it does not show again. **If a change to one of these pages' UI or logic would make its existing tutorial steps misleading, bump that page's entry in `TUTORIAL_PAGE_VERSIONS`** (`packages/shared/src/tutorials.ts`) — that is what re-shows it to users who already dismissed it. Editing the tutorial's own wording (via the admin editor at `/tutorials`) never needs this; only a page change that makes the _current_ steps wrong does.
  - **Adding a tutorial page is a migration, and the anchors are the one half no type can check** (#240, the evals page's walkthrough). `TutorialPageKey` is a Postgres enum, so a new key is an `ALTER TYPE … ADD VALUE` plus a `migrate deploy` against **both** the dev and the test database before a green suite means anything — the unit suites build their schema from the migration files and the E2E suite has its own database, so nothing in the validation loop touches the one the developer then opens the page against. The compiler covers the rest of the key set for free: `TUTORIAL_PAGE_LABEL`, `TUTORIAL_ANCHORS` and `TUTORIAL_PAGE_VERSIONS` are all `Record`s over it, and so is the seed's starter copy (`TUTORIAL_STARTER_CONTENT` in `apps/api/src/tutorial-starter-content.ts`), so a key with none **fails the typecheck**, which is what makes the copy part of the same change rather than a follow-up. What none of that reaches is the attribute: an id in `TUTORIAL_ANCHORS` that nothing on the page carries as `data-tutorial-anchor` is a step falling back to a centered callout, silently and by design (a page is allowed to re-tag itself under a saved step). Hold it with a test that reads the anchor list and asserts the rendered page carries every id — `EvalsPage.test.tsx` is the worked example.
- **The "new" nav badge** (issue #45): a small "New" text badge (`SidebarMenuBadge`, the same slot the unread-assignments count uses) on a `NavItem` (`apps/web/src/components/layout/nav-items.ts`), rendered by `AppSidebar` while `NEW_FEATURE_VERSIONS[key]` (`packages/shared/src/new-features.ts`) is ahead of what the signed-in user has seen, and dismissed permanently the first time they follow that link. To flag something new: add a key to `NEW_FEATURE_KEY`, give it a starting version in `NEW_FEATURE_VERSIONS`, and set `newFeatureKey` on the relevant `NavItem`. To re-flag something later (a page changed enough to be worth calling out again), bump its entry in `NEW_FEATURE_VERSIONS` — same trick as `TUTORIAL_PAGE_VERSIONS`, but there's no admin-editable content half here, only the code-level registry. Unlike `TutorialPageKey`, `NewFeatureKey` isn't a Postgres enum — the key set churns as things age out of "new", so it's a plain `String` column validated in code, and removing a key later needs no migration.
- **The "what's new" changelog** (issue #94): `ChangelogPopover` (`apps/web/src/components/layout/ChangelogPopover.tsx`), mounted once in `AppTopBar`. Unlike the tutorial and the "new" badge, its content is generated, not hand-authored or hand-versioned: `CHANGELOG_ENTRIES` (`packages/shared/src/changelog-entries.json`, read by `packages/shared/src/changelog.ts`) is appended to by CI's `bump-version` job (`.github/workflows/ci.yml`, via `scripts/ci/record-changelog-entry.mjs`) on every push to `develop`, one entry per `feat`/`fix` commit **since the previous bump** — a `chore`/`refactor`/etc. still bumps the version but adds no entry, because not every deploy is user-facing. **The bump runs on `develop`, and a release carries its version to `main` unchanged** (#410): it ran on `main` until then, nothing brought the commit back, and `develop` — staging's footer and popover with it — fell one version further behind on every release. The job checks out with `fetch-depth: 0` and reads `git log --no-merges <last bump>..HEAD`; each part is load-bearing. Under checkout's default shallow clone the range did not resolve, so the fallback then in place read the merge commit's own "Merge pull request #N" subject and _no merge ever recorded an entry_ (measured, #113) — there is no fallback now, so a shallow clone fails the job instead; reading only the branch tip drops the entry whenever a branch ends on a review fix-up over its `feat`, which is the ordinary shape of a branch here (#113 again); and reading only the triggering merge (`HEAD^2 --not HEAD^1`, what it did on `main`) loses a PR's entries whenever its run is cancelled by the next merge's, which `cancel-in-progress` does on every ref but `main`. A branch carrying two user-facing commits therefore yields two entries at the same version, and the popover lists both — `sort` there is stable, so they stay in the order CI recorded them. The popover reads entries straight out of `@ticket/shared` (no round trip for content); only the per-user "seen" flag is server state, `GET`/`POST /api/changelog/status` and `/seen`, mirroring the "new" badge's `NewFeatureSeen` shape but with one row per user rather than per key, since there is exactly one changelog stream. Versions compare numerically (`compareVersions`), not lexically — `"0.5.9"` sorts _after_ `"0.5.10"` as plain strings, which is backwards. **`CHANGELOG_LATEST_VERSION` is a sparse subsequence of deployed versions, not a second counter**: every entry's version is a genuine past value of `VITE_SENTRY_RELEASE` (see `releaseName()` in `apps/web/vite.config.ts`), so it can trail whatever's actually running in production after a `chore`-only deploy — that gap is intentional (nothing shipped worth telling a user about) and is not fixed by reading `VITE_SENTRY_RELEASE` into the seen-state comparison, which would light up the badge on deploys with no new content. See the doc comment on `ChangelogEntry` in `packages/shared/src/changelog.ts`.
- **A control that writes to a showcase screen asks `useDemoReadOnly()` itself, and a disabled one says why with `DemoReadOnlyNote`** (`apps/web/src/components/DemoReadOnly.tsx`, #326, PRD R5 and R15). A demo session sees Knowledge, Pipeline, Evals and the tutorial editor through `requireAdminView` and may change none of them, so on each the save, run and decide controls render disabled beside the note (`DEMO_READ_ONLY_NOTE` in `@ticket/shared`, which the E2E spec reads too). Each page, panel and dialog calls the hook itself rather than taking it as a prop from whoever mounts it: each is mounted from one page today, but a prop that a second mount site left out would default to writable. A row private to one file (`ArticleRow`, `PlannedRow`) takes it from the component above, since nothing else can mount it. The note renders nothing outside a demo session, like `DemoBanner`, so it needs no guard at the call site. A form puts its fields in a `<fieldset disabled>` rather than flagging each one, which reaches the Radix triggers and a field added later, and keeps Cancel outside it. What only opens something to read (Edit on an article, History) stays live. This is UX: `requireAdmin` on every write is the control, and a new write on a showcase screen gets both.
- **Respect `prefers-reduced-motion`** for any animation that isn't already covered by a library default (Recharts honours it itself via `isAnimationActive: 'auto'`). Use the `useReducedMotion` hook (`apps/web/src/lib/use-reduced-motion.ts`) rather than a fresh `matchMedia` query — it already handles the jsdom-has-no-`matchMedia` case (defaults to reduced) and the mount-vs-effect race. See the stat tiles' count-up for the pattern. The `prefers-reduced-motion` query string in any `.ts`/`.tsx` file under `src/` or `dev/` other than that hook and `src/test/setup.ts` fails the standards guard (`apps/web/dev/standards-guard.test.ts`); a CSS `@media` block is not read by it.
  - **The login strike and embers are the one effect with a chunk of their own** (#343). `LoginLockup` is in the entry chunk — `LoginPage` is a static import — so the effect lives in `LoginScene.tsx` and `login-scene.css`, reached only through `lazy()` and only while motion is allowed; anything imported statically from there would ship to every page. `login-scene.spec.ts` holds it by the module's name (`/LoginScene[.-]/`), so a rename breaks the check rather than the split. The scene's state is `data-strike` (`waiting` → `playing` → `cooled`) and the canvas publishes `data-ember-count`. The suite emulates reduced motion everywhere, so a test about the motion opts out with `test.use({ contextOptions: { reducedMotion: "no-preference" } })`.
- **Waiting states use `AiShine`** (`apps/web/src/components/AiShine.tsx`) — a light tracing the element's border, worn by the summary card and by both AI buttons so "a model is working" looks identical everywhere. Parent needs `relative`; the ring inherits the radius. The `ai-shine-ring` utility in `index.css` confines it to the border with a two-layer `mask` + `mask-composite: exclude`, and `ai-shine-beam` paints the gradient that travels inside it. Keep animations to `transform`/`opacity` per the note in that file: animating `background-position`, or spinning a conic gradient behind an `@property` angle, looks the same and repaints every frame. The beam uses its own `--ai-shine` / `--ai-shine-core` tokens rather than `--primary` — deliberately, and don't "fix" it back: `--primary` is oklch(0.5 …), a mid-dark temper blue picked to sit under near-white text, which reads as a dim slate line against the card, and these buttons are `disabled:opacity-50` for the entire time the shine is visible, so every colour is halved where it matters.
- **Each hue family means one thing, and a new use picks the family by meaning** (#342, the Cold iron palette). The map of temper blue, verdigris, ember and bronze is the comment at the top of `:root` in `index.css`; read it there rather than restating it here. `tests/e2e/brand.spec.ts` holds the families, the ember ramp as literals, and the rule that no control, count or status is bronze. **Temper blue as text is `text-link`, not `text-primary`**: `--primary` is a fill at 2.93:1 on the card, which is the violation `contrast.spec.ts` tolerated until #342 emptied its list. A `text-primary` class (but not `text-primary-foreground`) fails the standards guard (`apps/web/dev/standards-guard.test.ts`) before the E2E would see it. A new token defined with `var()` goes in the same `:root, .dark` block as what it references, since a custom property resolves where it is declared and one moved to another selector silently keeps the old value.
