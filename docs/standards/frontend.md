# Frontend standards (`apps/web`)

Client-side conventions: forms, styling, UI controls, data fetching, notifications, dev tooling. Component testing lives in [testing.md](testing.md).

- Forms: **react-hook-form** + **zod** via `@hookform/resolvers/zod`. Define the schema, infer the values type with `z.infer`, disable inputs on `isSubmitting`, surface server errors in local state.
- Icons: **lucide-react**. Use `Loader2` with `animate-spin` for pending/loading states.
- Tailwind v4 (CSS-first, no `tailwind.config`). Theme tokens are CSS variables in `apps/web/src/index.css` under `:root` / `.dark`; reference them as `var(--background)` etc. shadcn/ui components live in `apps/web/src/components/ui/`. `:root` / `.dark` also set `color-scheme`, which is what themes the remaining browser-drawn UI (scrollbars, the `type="search"` clear button) — don't remove it.
- **UI controls: shadcn/ui only.** Selects, checkboxes, radios, switches, tabs, tooltips, popovers, dropdown menus, comboboxes — all of it comes from shadcn. Add what's missing with `bunx --bun shadcn@latest add <component>` (the repo is already configured: `apps/web/components.json`, style `radix-nova`, `radix-ui` installed). **Never** reach for a native control instead: a native `<select>`'s popup is drawn by the OS, so it ignores `--popover`/`--radius`/font tokens and looks foreign next to the shadcn controls beside it. This is not a matter of taste — a native `<select>` in the filter bar shipped white-on-white options in dark mode. If shadcn genuinely has no component for the need, **ask** rather than inventing one. A native `<select>`, checkbox or radio outside `src/components/ui/` fails `apps/web/dev/standards-guard.test.ts` (#390).
  - Radix primitives that open a floating layer (Select, DropdownMenu, Popover, Combobox) need jsdom shims for the Pointer Capture API, `scrollIntoView` and `ResizeObserver`. They're already installed in `apps/web/src/test/setup.ts` — no per-test setup needed.
  - Radix rejects `value=""` on a `SelectItem` (it reserves the empty string for "cleared"), so an "any"/"all" row needs its own non-empty token mapped at the component boundary.
  - `SelectLabel` reads its id from `SelectGroup`'s context and **throws** without one. Nothing above the pages is an error boundary, so a stray `<SelectLabel>` inside a `SelectContent` blanks the whole app the moment the dropdown opens — always wrap it in `<SelectGroup>`.
  - Testing them: they are **not** native selects, so `selectOptions` (RTL) and `selectOption` (Playwright) do not work. Click the trigger, then click `getByRole("option", { name })`. Assert the current value from the trigger's text, not `toHaveValue`.
- Data fetching: **axios** + **@tanstack/react-query**. Don't use `fetch` directly. Use the shared axios instance from `@/lib/api` (preconfigured with `baseURL: VITE_API_URL` and `withCredentials: true` for cookie-based sessions). Wrap every server call in `useQuery` / `useMutation` — pass the `signal` from the query function into axios for automatic cancellation. The `QueryClientProvider` is wired in `apps/web/src/main.tsx`. A direct `fetch(` anywhere under `src/` or `dev/` fails the standards guard (`apps/web/dev/standards-guard.test.ts`).
- Notifications: **sonner** via the wrapper at `apps/web/src/components/ui/sonner.tsx` (re-exports `toast`, themes the `<Toaster />` from `useTheme`). The `<Toaster />` is mounted once in `apps/web/src/main.tsx`. Fire `toast.success(...)` on successful mutations and `toast.error(...)` on failure (in addition to surfacing the error inline in the form). Use `extractErrorMessage(err, fallback)` from `@/lib/errors` to pull the API error message out of axios errors consistently. In component tests, `sonner` is globally mocked in `apps/web/src/test/setup.ts` — `toast.*` are `vi.fn()` no-ops and `<Toaster />` renders `null`, so don't assert on toast DOM output.
- **A scrollable table goes in `<TableFrame label="…">`** (`apps/web/src/lib/table-frame.tsx`) — the shared border, rounding and `overflow-auto`, plus the three attributes that make the scroller operable: `tabIndex={0}`, `role="region"` and the required `label` as its `aria-label`. They are one decision, not three (issue #111): an `overflow-auto` div is not focusable, so a keyboard-only user cannot reach the columns that overflow right or the rows below the fold — sharpest on `UsersTable`, where scrolling horizontally at narrow widths _is_ the fix (#83) — but `tabIndex` alone buys an anonymous tab stop, and a `region` with no accessible name is not exposed as a landmark at all. `label` is required for exactly that reason; there is no class-string export to reach for instead. It is focusable whether or not it currently overflows: toggling on measured overflow makes a control appear and vanish as the window resizes, and jsdom reports every scroll dimension as `0`, so no test could hold it. Locked in by `tests/e2e/tickets.spec.ts` — focus the region, press PageDown, and the rows scroll while the sticky `<thead>` holds its place and the window stays put.
  - **The five desk tables use it; `ChartCard` does not, and that is a known gap, not the convention.** The dashboard's chart-to-table toggle (`apps/web/src/components/dashboard/ChartCard.tsx`) still renders its table into a bare `cn(CHART_HEIGHT_CLASS, "overflow-auto")` with no `tabIndex`, role or name — the same defect #111 fixed elsewhere, on a container that never shared `TABLE_FRAME` and so was outside that issue's scope. It bites harder there than it did here, because that table _is_ the chart's accessibility-relief path. Tracked as #123; don't read this bullet as saying the codebase is already uniform.
- **TanStack column sizing stays _uncontrolled_, and the reason is a race, not a preference** (issue #263). `TicketsTable` is the repo's only `useReactTable` call site and the only resizable table; it passes `state: { sorting }` and nothing else, and `columnSizing` must not be lifted back into a `useState` beside it. TanStack's resize handler fills a closure object with the new column sizes from **inside** the `setColumnSizingInfo` updater and reads that same object back from **inside** the `setColumnSizing` updater, so the two updates are a producer and a consumer that React only orders correctly when they share one update queue. Controlled, they did not share one: `columnSizing` was a hook declared above `useReactTable`, so React reached it first on every render where it could not eagerly evaluate the dispatches — which is any render with an update already pending on that fiber — and the consumer spread an **empty** object. The drag then applied nothing whatsoever and the column came back at the _exact_ width it started at, which is what made this read as a test flake rather than a bug: `data-resizing` still went true, the keyboard path (`nudge`, one plain `setColumnSizing`) was never affected, and it only fired under CI load. Uncontrolled, both updates land in the single `useState` inside `useReactTable` and are applied in dispatch order. Locked in by `apps/web/src/pages/TicketsTable.test.tsx`, whose three drag-race cases differ only in where React is allowed to flush: one event at a time (the control, which passed even before the fix), the whole drag batched into one `act`, and the whole drag batched behind an update already queued — Playwright cannot hold this, because in a browser the pending update is whatever the runner happened to be doing.
  - **The same symptom came back with the state right, and that is a different bug** (#313). Twice on CI after the fix (runs 35584773994 and 36008583266), a drag again read the default 227.36px. The second run kept traces, and their DOM snapshots held the dragged `<col>` widths while `getBoundingClientRect` still reported an older layout — the default in the failing attempt, and only the first half of the drag in a retry that passed because half was already "wider". It never reproduced locally: not under CPU throttling, and not in a static copy of the table on Windows or in the Linux Playwright image. So two defences went in without a red loop. Each `<th>` carries its column's width as well as the `<col>` (`HeaderCell`'s `width`, held by `TicketsTable.test.tsx`), so a resize restyles the measured cell too — nothing changes on screen, since fixed layout already reads the `<col>`, and whether it closes the lag is unproven. And the drag tests read `settledSubjectWidth` rather than one width straight after `mouse.up()`: it polls until Subject has moved in the expected direction _and_ its rendered width matches what the `<col>`s imply (`col × table ÷ Σcols`, fixed layout's proportional share). The second condition is the one that matters — a width that had merely moved and held steady would have passed on the first half of a drag, which one of the traces read. If it fires again, check a trace's DOM snapshots before the component: a `<col>` that moved means this bullet, and one that did not means #263's.
- **A route's path is declared once, in `ROUTE`** (`apps/web/src/lib/routes.ts`), together with the timing key it produces `performance` entries under. Nothing retypes a path: the router's `path`, `NavItem.to`, `<Link to>`, `navigate(...)`, a `pathname ===` comparison and the timing module's patterns all read `ROUTE.<name>.path`, and a ticket link goes through `ticketDetailPath(id)` rather than interpolating `/tickets/${id}`. `NavItem["to"]` is typed as `RoutePath` — the union of the record's paths — so a literal that no longer names a route stops compiling. `navigate()`, `<Navigate to>`, `<Link to>` and a `pathname ===` comparison get no such compile error, so a path literal in any of them under `src/` fails the standards guard instead (`apps/web/dev/standards-guard.test.ts`, #390) — five sites had retyped the dashboard's `"/"` before it existed. Issue #151 is what this is for: the user-timing module used to keep its own copy of the three instrumented patterns, and a rename anywhere else made the match miss, the render mark no-op and the measure **stop existing** — no build error, no failing test, nothing in the log. The E2E could not catch it either, because it restated the key strings too; it imports `navigateMarkName`/`renderedMarkName`/`timeToDataMeasureName` now. Two constraints follow. `routes.ts` is **import-free** — no `@/…` alias, no React, no router — which is what lets `tests/e2e/route-timing.spec.ts` reach into it the way `dashboard-layout.spec.ts` reaches into `dashboard-panels.ts`; and `timingKey` is present only on instrumented routes, so `as const satisfies` makes `ROUTE.users.timingKey` a type error rather than an `undefined` that flows on into a mark name. The `/__dev/map` scanner resolves `path: ROUTE.<name>.path` against the record (`readRouteRecord` in `dev/scan.ts`) — a new way of writing a route path needs teaching there, or that route silently drops out of the map.
  - The timing module is split for the same reason: `route-timing.ts` is the pure half (entry names, the pathname→key lookup, the awaiting-render set) and is unit-tested without a renderer in `route-timing.test.ts`; `route-timing-layout.tsx` holds `RouteTimingLayout` and the `useRouteRenderedMark` hook. A page calls the hook with `ROUTE.<name>.timingKey`.
- **A route that prefetches does it through `prefetchLoader`** (`apps/web/src/lib/route-prefetch.ts`), and supplies only which queries its URL implies: `export const ticketsLoader = prefetchLoader(({ request }) => [prefetchQuery(...)])`. The module owns the four decisions every prefetching route shares — await the queries (so the page mounts with its cache primed instead of rendering a skeleton), tolerate a rejection (the page owns its own error screen; throwing would hand the navigation to the router's error boundary, which has no way back), start several at once via `allSettled` (the pages fire theirs concurrently, so a serialized loader would be _earlier and slower_), and return `null` (react-query stays the cache layer). Issue #157 is what this is for: those four rules had been prose repeated once per route above four lines of code, and each route reached the module-level `queryClient` directly, so nothing could substitute it and none of the three had a test. Each query goes through `prefetchQuery(queryOptions(...))` — a closure, not the options object, because a query's key tuple and response type appear in contravariant positions in react-query's option types, so a heterogeneous list of them has no supertype short of `any`. The client is swappable (`setPrefetchQueryClient`), which is what makes a loader testable at all — see [testing.md](testing.md). Both the loader and the page must read the URL through the same parser (`parseTicketListParams`, `parseDashboardParams`), or a hand-edited `?sort=nonsense` primes one entry and the page reads a neighbouring one.
- **Dev-only tooling at `/__dev`** (never in a production build — Railway's `develop` environment runs the dev server itself, behind HTTP Basic Auth; see the #314 sub-bullet below). Three pages: `/__dev/map` is a project map — module graph, imports, layers, client routes, API endpoints with their guards, the Prisma models, and which client module calls which endpoint; `/__dev/tests` runs the repo's suites from the browser with streamed output; `/__dev/usage` reports what each GitHub issue was forecast to cost and what it actually cost in output tokens, read off this machine's Claude Code transcripts and one `gh issue list` call. All three are also linked from the sidebar's "Dev" group.
  - **Usage scans nothing until Scan is pressed, and nothing anywhere caches the answer — but since #417 the dev server keeps what each scan _read_, and since #419 one point per day for the trend.** The other two pages fetch on load; a scan here reads every transcript the machine holds, and its claim is that the figures on screen were gathered at a named moment from a named directory. So `useUsageScan` is a `useMutation` rather than a `useQuery` (a query is something react-query is entitled to run for you — on mount, on focus, on reconnect), and the page holds the last result until the next one. **Since #432 the page opens on the stored reading instead of empty**: `GET /__devtools/usage` (`readStoredUsage` in `dev/usage.ts`, through `useStoredUsage`, a query with `gcTime: 0` so a return asks again) computes the same report from the history's rows, its trend and the listing the last scan kept in it (or `GH_ISSUES_FILE`, which a push rewrites), opening the file read only — no transcript, no `gh`, no write, ~32-45ms over 14,352 rows. Its `transcripts` is null, which is how the page words it as "Stored at … by the last scan or push" rather than "Gathered at" — the moment being the store's stamp of when rows last arrived; Scan replaces it. It is null — the empty state — with no history configured (`pushHistoryFile`), no file or no rows, and a failed `GET` is a warning beside that empty state, not a toast. Nothing derived is persisted for it (ADR-0023's #432 section). What the middleware keeps between presses is the **usage history** (`dev/usage-store.ts`, ADR-0023): one SQLite row per API response at `~/.claude-usage-history/<project-slug>.sqlite`, outside the repo and outside `~/.claude`, so an issue keeps its spend after Claude Code deletes the transcript after 30 days. **The slug is the main worktree's root, not the working directory's** (#423): `resolveHistoryFile` asks `git rev-parse --git-common-dir` (async, through `childEnv`, falling back to the cwd's slug when git cannot answer), so every worktree of a clone shares one history while `resolveTranscriptDir` still reads each worktree's own transcripts; it is `async` for that reason, and both callers await it. It stores responses and never a row's answer — attribution and counting (`tallySpend` in `dev/transcripts.ts`) run over every stored row on every read, so a correction like #413's reaches rows whose transcript is gone — and it is opened per request and closed before the response, because a handle held between presses would stop a spec or a developer deleting the file on Windows. **On Bun, closing is not enough**: `bun:sqlite`'s `close` defers while any prepared statement is unfinalized, so the file stayed locked (EBUSY) after a scan until the garbage collector ran — the Bun opener finalizes what it prepared before it closes (#418), and the E2E, which runs Vite on Node, could never have seen it. **Since #418 a scan reads only what was appended**: the store also keeps a cursor per transcript (byte offset past the last newline, size, line count, and a hash of the first bytes), `readTranscripts` resumes from it, a file whose size has not changed is not opened, and a file that shrank or no longer starts the same way is re-read from the top, its overlap absorbed by the identity key. A trailing line with no newline is parsed but left in front of the cursor, so a half-written one counts once it is finished and a complete one counts once. Measured on 168 transcripts: a warm scan went from ~2.2s to ~60ms; a cold one still costs a full read (~2.2s before, ~2.3-2.4s after, the difference being the cursors' hashing and writes). The page names the history's earliest date (`historySince`) beside the reading. **Since #419 the history keeps one answer as well: a trend point per local calendar day, written by every scan that keeps a history (`bun run tokens` included)** (`trend_point`, the day's last scan replacing it) — the quartiles of output tokens, the accuracy tally and the band edges in force, because a past day's labels and bands cannot be asked again; never a row's verdict, so every verdict on the page is still judged against today's bands (ADR-0023's #419 section). The point is `trendPointFor` in `src/dev/usage-readings.ts`, built from the same `recordedSpend`/`percentiles`/`forecastAccuracy` calls the two panels make over the same rows, so today's point and the panels cannot disagree; the day is **local**, not `toISOString()`'s UTC date, and that boundary and the replace-not-append rule are vitest cases with a clock passed to `gatherUsage` (`dev/usage.test.ts`), since Playwright cannot move a day. The page draws it in `src/dev/UsageTrend.tsx` — two `ChartPanel`s and a `TableFrame` of points beneath them, which is the relief path and what `dev-usage-history.spec.ts` reads a day from. Their region names live in `USAGE_TREND_LABEL` and must not contain another region's name: Playwright matches names as case-insensitive substrings, so "Forecast accuracy over time" would put every `{ name: "Forecast accuracy" }` in `dev-usage.spec.ts` in strict-mode violation. Bun cannot resolve `node:sqlite` and Node cannot load `bun:sqlite`, and both run this code — the developer's dev server and `bun run tokens` on Bun, vitest and the E2E's `bunx vite` on Node — so the store speaks to a narrow `SqlDatabase` surface and `openUsageStore` imports whichever module the running process has, through a variable so neither resolver chokes on the other's; the `bun:sqlite` types are a minimal ambient declaration (`dev/bun-sqlite.d.ts`) rather than `@types/bun`. That is deliberately the opposite of the test runner beside it: a run is a long-lived process worth surviving a reload, a scan is a few seconds of reading that is cheaper to repeat than to invalidate. The join itself lives in `apps/web/dev/usage.ts` and is shared with `bun run tokens`, so the page and the terminal cannot report different figures for the same issue.
  - **Railway's `develop` history is fed by pushes, never by its own transcripts** (#428). It has none — they are on the developer's laptop — so `bun run tokens --push <url>` sends the local history's `response` rows and the issue listing to `DEVTOOLS_API.usagePush`, and that server's scans tally them like any other stored rows (the volume, the variables and the command are `DEPLOYMENT.md` §7). Four rules. **Rows, not transcripts**: the wire is `src/dev/usage-push.ts`, strict zod on both the rows (the six `TranscriptResponse` fields) and the issues, so a key nobody declared is a 400 rather than a stored column, and `buildPush` copies the six fields by name rather than spreading a row; `dev/usage-push.test.ts` asserts the payload's keys and that a transcript's text and paths are absent. The schema sits there rather than in `@ticket/core`, the one exception to [conventions.md](conventions.md)'s rule, and a forced one: `dev/` is loaded by Vite's native config loader, which resolves nothing extensionless (the sub-bullet below), and `@ticket/core`'s index re-exports extensionless — so it is defined once beside the other Usage contracts and parsed by both ends. **The listing rides along instead of `gh`**: the dev image has no `gh`, so the server writes the pushed listing to `GH_ISSUES_FILE` (temp file and rename) and the page reads it through the override that never falls back; a push carrying one with that variable unset is a 409 and stores nothing. **Re-pushing is free**: every row goes every time and the store's per-id `ON CONFLICT` is the dedupe (since #431 it raises a stored row's counts to a larger pushed one rather than doing nothing), so there is no second cursor to drift. **The develop server is marked, not inferred**: `Dockerfile.dev` sets `USAGE_HISTORY_PUSHED=1` (`PUSHED_HISTORY_ENV`), and only there does a missing (ENOENT) or empty transcript directory beside a history holding rows raise no warning (`gatherUsage`'s `pushedHistory`) and a push without `USAGE_HISTORY_FILE` get a 409, since the default file is inside the container. Inferring it from "the history holds rows" was the first cut and lost: since #423 the history is keyed on the main worktree and the transcripts on the cwd, so a laptop scan from the wrong directory would have dropped the very warning that says so. A directory that exists and cannot be read warns everywhere. The route is `/__devtools/usage-push`, a sibling of `usage` rather than a path under it, because connect mounts by prefix and the scan handler would answer it first.
  - **`CLAUDE_TRANSCRIPT_DIR` and `GH_ISSUES_FILE` are the two seams that make any of it testable, and `USAGE_HISTORY_FILE` is the third** (#417) — `playwright.config.ts` points it at `tests/e2e/fixtures/usage-history.local.sqlite`, which `resetTranscriptWorkingCopy` removes with the working copy, and every unit test and the guardrail's `bun run tokens` spawn set it too: unset, a fixture scan writes fixture spend into the developer's real history. Neither source is something an assertion can name — the real transcript directory is derived from `cwd` + `homedir` and holds this machine's own spend, and what this repo's issues are titled changes every time somebody files one. So `resolveTranscriptDir` honours an override and `playwright.config.ts` points the E2E web server at a copy of `tests/e2e/fixtures/transcripts` (totals written down in that checked-in directory's `README.md`, restated as literals in `tests/e2e/dev-usage.spec.ts`). The copy is `tests/e2e/fixtures/transcripts.local`, gitignored and remade by each Usage spec before it scans (`resetTranscriptWorkingCopy`, #416), so a spec may delete or append to a transcript without touching the checked-in one. Likewise `fetchIssueMetadata` (`dev/issues.ts`) honours an override naming a file holding what `gh issue list --json …` would have printed. The page prints the directory it read, and the fixture titles carry the word “Fixture”, for the same reason: locally, `reuseExistingServer` will adopt a leftover Vite on 4001 that was started without either override, and the page then reports the developer's own transcripts against GitHub's real titles — which looks like a missing row rather than the wrong server.
    - **The listing override never falls back to `gh`**, and the E2E's listing fixture is written by the spec rather than checked in (`tests/e2e/fixtures/gh-issues.ts`, gitignored as `*.local.json`). Both follow from the same constraint: a web server's environment is fixed when it starts, so the only honest way to reach the no-`gh` state through the real middleware is for the file it names to be missing — and a fallback would have that case read live GitHub and pass or fail depending on whose machine it ran on.
    - **`gh` is available from a dev-server child, sanitiser and all** (#249, measured): its credential comes from the OS credential store, and no `.env*` file here declares a GitHub token, so `configuredKeys` has nothing to strip. Two things that are easy to break — the spawn's `cwd` must be the repo root (`gh` resolves the repository from the git remote of wherever it runs), and it must be **one** `gh issue list` call rather than a loop of `gh issue view`, which costs ~0.9s per issue against ~1.7s for all of them.
  - **The Usage table opens on four columns, and one control appends the other three** (#271). `USAGE_SPINE` (`title`, `out`, `comparison`) is what a scan shows; `USAGE_DETAIL` (`turns`, `sessions`, `cacheRead`) comes back on a shadcn `Toggle` above the table, `variant="outline"` like the project map's pair, named by `aria-label` rather than by its chip. **The contract is two lists whose concatenation is the order, not one list with a `detail` flag**, and the reason is positional: detail columns _append_, so a spine cell sits at the same index in both states and the one `CELL` map each suite builds from `USAGE_COLUMNS` serves both. Two maps could disagree, and the suites that index a row by position would go on passing while asserting against a neighbouring cell. Bringing the three back is allowed to reintroduce horizontal scrolling — it is opt-in, and `TableFrame` already makes the scroller focusable and named. The E2E holds the width claim by comparing the scroller's `scrollWidth` to its `clientWidth` at 1280px rather than by counting columns — but **know what that assertion is worth before leaning on it.** Measured 2026-09-19 against a real scan (103 issues, 1280px window): the frame reads 1218/1218 with the detail columns _shown_, and 1248/1248 both ways on the E2E fixture. Seven columns already fit; the scroll the PRD complains about was **nine**, and #270's merged comparison cell is what removed it. The toggle buys less to read, not less to scroll, and the assertion is a regression guard — a `min-w` on the `<table>`, a column escaping `Title`'s `max-w-[26rem]` cap, a fifth column in the spine.
  - **Every figure column and the issue number rank the table from their header, and a row with no recorded spend sinks to the bottom in _both_ directions whatever column is sorted** (#272). The comparator is `src/dev/usage-sort.ts` — pure, and unit-tested over made-up rows, because the sink is a property of the comparator rather than of the output-tokens column: `usage-sort.test.ts` asks it of every key in both directions. The header markup copies `ModuleTable` exactly (`aria-sort` on the `<th>`, a button inside it, an `aria-hidden` `ArrowUp`/`ArrowDown`, clicking the active column flips it); a column nothing ranks by carries **no** `aria-sort` rather than `"none"`, which would advertise a control that is not there. The sink _is_ the ticket, not a detail of it. `bucketFor(0)` is `S`, so an unstarted row read as zero arrives first in an ascending sort as the cheapest work in the repository, and its band would then score it as having come in under — the same lie the cells refuse to tell (`NotStarted`), told in the ordering instead. A row that really spent zero is a measurement and still ranks as the cheapest work there is; nothing substitutes one for the other. The sortable set is a **record keyed by `"issue" | keyof IssueSpend`** (`SORTABLE`, with `USAGE_SORT_KEYS` as its walkable half), so it is exhaustive by construction — a list could only be checked for membership, and a fifth figure on `IssueSpend` would have arrived with no way to rank by it. `title` and `comparison` cannot be named by that key type at all, which is where their exclusion stops being a comment: a name nobody ranks a spend table by and one that can be absent (a second sink rule, for a different reason), and three facts in one cell. Which column offers which key is said once too — `COLUMNS` is typed so a column whose name is a sort key **must** carry `sort`, and it must be its own name, because the two lists were otherwise free to drift: dropping `sort` from `turns` left the comparator's tests green while no header offered it, and a copy-pasted `sort: "turns"` on `cacheRead` compiled and ranked the wrong column. The default is output tokens descending because that **is** the order `joinIssues` returns: since #286 the node half imports `DEFAULT_USAGE_SORT` and `sortIssues` and sorts the wire rows with them, so the first render after a scan is the order the server sent rather than an order that reproduces it. It had been `rank(b) - rank(a) || a.issue - b.issue` over there against the sink plus this key here — one claim written twice, and `dev-usage-guardrail.spec.ts` measured the cost: reversing either expression moved exactly one of the two surfaces, so nothing but inspection held them level. The issue-number tie-break sits **outside** the direction flip, which is what makes the order total, and that is now load-bearing rather than tidy: a default whose tie-break reversed with the direction would be total in one direction only, and `joinIssues` would need a rule of its own again for the other.
    - **The chosen sort is `UsagePage`'s state, not `SpendTable`'s, and the reason is measured rather than stylistic.** `useUsageScan` is a `useMutation`, and a mutation clears its `data` the moment it is fired (`case "pending"` sets `data: undefined` in query-core), so `report` is null for the length of the read, the `report &&` gate closes and the table unmounts. Anything kept inside it is thrown away by the press of Scan that re-asks the same question — which is exactly what the acceptance criterion "the sort survives a re-scan" is about. **#271's detail toggle moved up with it**, and had to: `turns`, `sessions` and `cacheRead` only have a header while it is on, so a sort on one of them surviving a re-scan _without_ the columns would satisfy "the chosen sort survives" and break "the active column shows its direction" in the same render — a ranking with no arrow, no `aria-sort` and nothing on screen saying why. The two are one `UsageTableView` for that reason. The same hole is reachable by hand, so hiding the detail columns while the sort is on one of them **returns the sort to the default**: going back to the order the rows arrived in is the one outcome that can still be announced, and it happens in the gesture that caused it.
  - **The Usage filter bar's reach is the table and nothing else, and that is the slice's decision rather than its implementation** (#273).
