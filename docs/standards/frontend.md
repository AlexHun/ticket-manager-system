# Frontend standards (`apps/web`)

Client-side conventions: forms, styling, UI controls, data fetching, notifications, dev tooling. Component testing lives in [testing.md](testing.md).

- Forms: **react-hook-form** + **zod** via `@hookform/resolvers/zod`. Define the schema, infer the values type with `z.infer`, disable inputs on `isSubmitting`, surface server errors in local state.
- Icons: **lucide-react**. Use `Loader2` with `animate-spin` for pending/loading states.
- Tailwind v4 (CSS-first, no `tailwind.config`). Theme tokens are CSS variables in `apps/web/src/index.css` under `:root` / `.dark`; reference them as `var(--background)` etc. shadcn/ui components live in `apps/web/src/components/ui/`. `:root` / `.dark` also set `color-scheme`, which is what themes the remaining browser-drawn UI (scrollbars, the `type="search"` clear button) — don't remove it.
- **UI controls: shadcn/ui only.** Selects, checkboxes, radios, switches, tabs, tooltips, popovers, dropdown menus, comboboxes — all of it comes from shadcn. Add what's missing with `bunx --bun shadcn@latest add <component>` (the repo is already configured: `apps/web/components.json`, style `radix-nova`, `radix-ui` installed). **Never** reach for a native control instead: a native `<select>`'s popup is drawn by the OS, so it ignores `--popover`/`--radius`/font tokens and looks foreign next to the shadcn controls beside it. This is not a matter of taste — a native `<select>` in the filter bar shipped white-on-white options in dark mode. If shadcn genuinely has no component for the need, **ask** rather than inventing one.
  - Radix primitives that open a floating layer (Select, DropdownMenu, Popover, Combobox) need jsdom shims for the Pointer Capture API, `scrollIntoView` and `ResizeObserver`. They're already installed in `apps/web/src/test/setup.ts` — no per-test setup needed.
  - Radix rejects `value=""` on a `SelectItem` (it reserves the empty string for "cleared"), so an "any"/"all" row needs its own non-empty token mapped at the component boundary.
  - `SelectLabel` reads its id from `SelectGroup`'s context and **throws** without one. Nothing above the pages is an error boundary, so a stray `<SelectLabel>` inside a `SelectContent` blanks the whole app the moment the dropdown opens — always wrap it in `<SelectGroup>`.
  - Testing them: they are **not** native selects, so `selectOptions` (RTL) and `selectOption` (Playwright) do not work. Click the trigger, then click `getByRole("option", { name })`. Assert the current value from the trigger's text, not `toHaveValue`.
- Data fetching: **axios** + **@tanstack/react-query**. Don't use `fetch` directly. Use the shared axios instance from `@/lib/api` (preconfigured with `baseURL: VITE_API_URL` and `withCredentials: true` for cookie-based sessions). Wrap every server call in `useQuery` / `useMutation` — pass the `signal` from the query function into axios for automatic cancellation. The `QueryClientProvider` is wired in `apps/web/src/main.tsx`.
- Notifications: **sonner** via the wrapper at `apps/web/src/components/ui/sonner.tsx` (re-exports `toast`, themes the `<Toaster />` from `useTheme`). The `<Toaster />` is mounted once in `apps/web/src/main.tsx`. Fire `toast.success(...)` on successful mutations and `toast.error(...)` on failure (in addition to surfacing the error inline in the form). Use `extractErrorMessage(err, fallback)` from `@/lib/errors` to pull the API error message out of axios errors consistently. In component tests, `sonner` is globally mocked in `apps/web/src/test/setup.ts` — `toast.*` are `vi.fn()` no-ops and `<Toaster />` renders `null`, so don't assert on toast DOM output.
- **Dev-only tooling at `/__dev`** (never shipped). Two pages: `/__dev/map` is a project map — module graph, imports, layers, client routes, API endpoints with their guards, the Prisma models, and which client module calls which endpoint; `/__dev/tests` runs the repo's suites from the browser with streamed output. Both are also linked from the sidebar's "Dev" group.
  - Browser half in `apps/web/src/dev/`, node half in `apps/web/dev/` (a Vite plugin, `apply: "serve"`), wire types shared in `apps/web/src/dev/protocol.ts`. `tsconfig.node.json` includes `dev` so both ends are checked.
  - **Relative imports in `dev/` and in `vite.config.ts` carry their `.ts` extension, and use `import.meta.dirname` rather than `__dirname`.** Both are required by Vite's `configLoader: 'native'`, which is announced to become the default in a later major; until then Vite 8 prints a warning naming every offending line on each dev start. `allowImportingTsExtensions` is already on in `tsconfig.node.json`, so the extension costs nothing. Keep new files in this directory to the same rule — the warning is per-import, so one extensionless addition brings the whole block back.
  - Kept out of production by `import.meta.env.DEV` in `App.tsx` and `nav-items.ts` — Vite folds it to `false`, so Rollup drops the `import()` and emits no chunk. If you add an entry point to this code, check `.vite/stats.html` after a build.
  - The scan is regex-over-source with comments stripped first (`dev/scan.ts`), not a TS AST. It handles the import styles this repo uses; anything it cannot parse lands in the map's `warnings` rather than being dropped silently.
  - The map's filter bar has **two different reaches, and a new view has to pick one deliberately.** The workspace `Select` and the two toggles stop at the Graph and Modules tabs — Overview and Wiring report whole-project totals, and a project that shrank because you hid the tests would be worse than useless. The **search reaches all four**, and every match goes through `matchesQuery` in `dev/module-match.ts` rather than an inline `id.includes(...)`: the inline version is exactly how the box came to do nothing on Overview and Wiring, which are the tabs written last and the first one the page opens on. Wire a new view in by naming the fields it searches. Two rules that follow from it — an empty query matches *everything*, so callers filter unconditionally instead of branching; and a card heading whose list can narrow shows `countLabel(shown, total)`, because a heading still reading `12` over three rows is the same lie the frozen module counter used to tell. Scan `warnings` are deliberately exempt: a warning says the map you are reading is incomplete, so it outranks whatever you typed.
  - Test runs belong to the **dev server**, not the tab: reloading reconnects and replays, only Cancel stops one (it kills the process tree). Editing anything under `apps/web/dev/` restarts the dev server — it is a `vite.config.ts` dependency — which cancels any run in flight.
  - Anything spawned from the dev server must sanitise its environment first (`childEnv` in `dev/suites.ts`). The dev script is `bunx --bun vite`, and `--bun` puts a fake `node` on PATH plus `NODE=…/bun-node-*/node.exe`; a child that inherits it sees Bun where it expects Node, and Vitest's `node --require …/suppress-warnings.cjs` worker launch turns into Bun trying to *install* that path as a package. It also strips every key the repo's `.env*` files declare, because `dotenv-cli` won't override an inherited value — otherwise `.env.test` loses to the dev `PORT`/`DATABASE_URL` and the E2E database reset points at the dev database.
- **The per-page tutorial**: `<Tutorial pageKey={TUTORIAL_PAGE_KEY.x} />` (`apps/web/src/components/Tutorial.tsx`) is mounted once near the top of each of the eight main pages. It fetches `GET /api/tutorials/:pageKey`, pops up unprompted when the API says `shouldShow`, and posts `/api/tutorials/:pageKey/seen` on dismiss/finish so it does not show again. **If a change to one of these pages' UI or logic would make its existing tutorial steps misleading, bump that page's entry in `TUTORIAL_PAGE_VERSIONS`** (`packages/shared/src/index.ts`) — that is what re-shows it to users who already dismissed it. Editing the tutorial's own wording (via the admin editor at `/tutorials`) never needs this; only a page change that makes the *current* steps wrong does.
- **The "new" nav badge** (issue #45): a small "New" text badge (`SidebarMenuBadge`, the same slot the unread-assignments count uses) on a `NavItem` (`apps/web/src/components/layout/nav-items.ts`), rendered by `AppSidebar` while `NEW_FEATURE_VERSIONS[key]` (`packages/shared/src/index.ts`) is ahead of what the signed-in user has seen, and dismissed permanently the first time they follow that link. To flag something new: add a key to `NEW_FEATURE_KEY`, give it a starting version in `NEW_FEATURE_VERSIONS`, and set `newFeatureKey` on the relevant `NavItem`. To re-flag something later (a page changed enough to be worth calling out again), bump its entry in `NEW_FEATURE_VERSIONS` — same trick as `TUTORIAL_PAGE_VERSIONS`, but there's no admin-editable content half here, only the code-level registry. Unlike `TutorialPageKey`, `NewFeatureKey` isn't a Postgres enum — the key set churns as things age out of "new", so it's a plain `String` column validated in code, and removing a key later needs no migration.
- **The "what's new" changelog** (issue #94): `ChangelogPopover` (`apps/web/src/components/layout/ChangelogPopover.tsx`), mounted once in `AppTopBar`. Unlike the tutorial and the "new" badge, its content is generated, not hand-authored or hand-versioned: `CHANGELOG_ENTRIES` (`packages/shared/src/changelog-entries.json`, re-exported from `packages/shared/src/index.ts`) is appended to by CI's `bump-version` job (`.github/workflows/ci.yml`, via `scripts/ci/record-changelog-entry.mjs`) on every push to `main`, one entry per `feat`/`fix` commit **on the merged branch** — a `chore`/`refactor`/etc. still bumps the version but adds no entry, because not every deploy is user-facing. The job checks out with `fetch-depth: 0` and reads `git log HEAD^2 --not HEAD^1`; both halves are load-bearing and were measured (issue #113). Under checkout's default shallow clone `HEAD^2` does not resolve at all, so the fallback read the merge commit's own "Merge pull request #N" subject and *no merge ever recorded an entry*; and reading only the branch tip drops the entry whenever a branch ends on a review fix-up over its `feat`, which is the ordinary shape of a branch here. A branch carrying two user-facing commits therefore yields two entries at the same version, and the popover lists both — `sort` there is stable, so they stay in the order CI recorded them. The popover reads entries straight out of `@ticket/shared` (no round trip for content); only the per-user "seen" flag is server state, `GET`/`POST /api/changelog/status` and `/seen`, mirroring the "new" badge's `NewFeatureSeen` shape but with one row per user rather than per key, since there is exactly one changelog stream. Versions compare numerically (`compareVersions`), not lexically — `"0.5.9"` sorts *after* `"0.5.10"` as plain strings, which is backwards. **`CHANGELOG_LATEST_VERSION` is a sparse subsequence of deployed versions, not a second counter**: every entry's version is a genuine past value of `VITE_SENTRY_RELEASE` (see `releaseName()` in `apps/web/vite.config.ts`), so it can trail whatever's actually running in production after a `chore`-only deploy — that gap is intentional (nothing shipped worth telling a user about) and is not fixed by reading `VITE_SENTRY_RELEASE` into the seen-state comparison, which would light up the badge on deploys with no new content. See the doc comment on `ChangelogEntry` in `packages/shared/src/index.ts`.
- **Respect `prefers-reduced-motion`** for any animation that isn't already covered by a library default (Recharts honours it itself via `isAnimationActive: 'auto'`). Use the `useReducedMotion` hook (`apps/web/src/lib/use-reduced-motion.ts`) rather than a fresh `matchMedia` query — it already handles the jsdom-has-no-`matchMedia` case (defaults to reduced) and the mount-vs-effect race. See the stat tiles' count-up for the pattern.
- **Waiting states use `AiShine`** (`apps/web/src/components/AiShine.tsx`) — a light tracing the element's border, worn by the summary card and by both AI buttons so "a model is working" looks identical everywhere. Parent needs `relative`; the ring inherits the radius. The `ai-shine-ring` utility in `index.css` confines it to the border with a two-layer `mask` + `mask-composite: exclude`, and `ai-shine-beam` paints the gradient that travels inside it. Keep animations to `transform`/`opacity` per the note in that file: animating `background-position`, or spinning a conic gradient behind an `@property` angle, looks the same and repaints every frame. The beam uses its own `--ai-shine` / `--ai-shine-core` tokens rather than `--primary` — deliberately, and don't "fix" it back: `--primary` is oklch(0.432 …), a deep low-chroma green that reads as a faint olive line against the card, and these buttons are `disabled:opacity-50` for the entire time the shine is visible, so every colour is halved where it matters.
