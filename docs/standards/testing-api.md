# API testing standards (`apps/api`)

The `apps/api` half of [testing.md](testing.md), split out so a task that touches
only the web suite, a script or a command does not pay for it. Test commands, the
component-test conventions and the script/env rules stay in [testing.md](testing.md).

- Tests: **`bun test`** (`bun run --filter @ticket/api test`), files next to the source as `*.test.ts`. `mock.module(specifier, factory)` must be registered _before_ the module under test is imported, so the module under test comes in through a dynamic `await import(...)` at the top of the file rather than a static import. Spread the real module into the factory (`{ ...actual, generateText }`) when only one export is being replaced — the constants and error classes the code branches on have to stay real or the test asserts against its own stub. `../middleware/auth` is the one mock almost every route test still needs — it pulls in `../auth`, which throws without `BETTER_AUTH_SECRET`. `../db` was the other, and since #175 no test file registers it at all: a preload binds it once for the whole process, below.
  - **The database is not mocked — it is real, and it runs in this process** (`docs/adr/0014`). `import { prisma, resetDb } from "../test/pg"` and call `await resetDb()` in `beforeEach` — that is the whole setup, because `../db` is already bound to that client before your file loads. That is a genuine `PrismaClient` on a genuine Postgres — PGLite, compiled to WASM — so `where`, `select`, `orderBy`, `$transaction`, unique constraints and a conditional `updateMany` all mean what Postgres means by them, and this repo's own migrations are what built the schema. **Write new API tests this way; do not add a new hand-written `prisma` fake.** What it costs, measured on both platforms because they differ by ~4x: on CI, ~2.65s once per run and ~26–39ms per route test (suite 0.85s → 4.09s with one file converted, projecting ~10s once all of them are); on a Windows dev machine, ~3.4s once and ~150ms per route test (4.07s → 10.0s). If a converted file feels slow locally, that is the machine, not the approach — check CI before optimising anything. `src/test/pg.ts` carries the caching, the reset and the reasoning; nothing above it knows PGLite exists, which is what keeps a swap to a real server a one-module change.
    - **The `../db` binding is registered once, in a preload, and no test file writes it** (#175). `apps/api/src/test/preload.ts` sets `DATABASE_URL` to an unreachable sentinel, then registers `mock.module("../db", () => ({ Prisma, prisma }))` for the whole process; `package.json`'s `test` script passes it with `--preload` and `apps/api/bunfig.toml` lists it under `[test]`, so both `bun run --filter @ticket/api test` and a bare `bun test src/routes/knowledge.test.ts` from that directory need no extra flag. **Both, deliberately.** The flag is what CI runs, and it fails loudly — module not found — if it is ever resolved from the wrong directory; the bunfig is what covers the `bun test <a> <b>` in both orders this section prescribes below. A run with no preload has no sentinel `DATABASE_URL` either, so it would link the real `../db` and quietly find the dev database. Bun evaluates a module once, so listing it twice registers the binding once. Sixteen identical registrations became one, and the two workarounds they forced went with them — a factory no longer re-exports a `Prisma` namespace the file never touches, and two suites that both reach the database no longer have to share a file. Two things it depends on, both worth knowing before moving that file. **The specifier resolves relative to the preload**, not to the module under test; `src/test/` and `src/routes/` are the same depth, so the string is `"../db"` in both by coincidence rather than by rule. And **the sentinel is a safety interlock, not tidiness**: a `mock.module` whose path matches nothing does not error, the modules under test then link the real `../db`, and on a developer's machine `DATABASE_URL` names the dev database — the #152 spike hit exactly that, with `new URL(…).pathname` yielding `/C:/…` on Windows. Pointing the variable at a closed port first turns a silent fallthrough into `Can't reach database server at 127.0.0.1:1` on the first query. Verified by hand: breaking the specifier takes the suite from 405 pass / 0 fail to 217 failures, all of them that message.
    - **A rule Postgres enforces rather than a module goes in `src/schema.test.ts`** (#169) — a cascade, a `SetNull`, a `Restrict`, a partial index. It mocks nothing and has no module under test, because there isn't one. The split is by _who_ enforces the rule, not by which table it is about: `routes/tutorials.test.ts` covers `PUT /:pageKey` writing `updatedById`, and `schema.test.ts` covers what becomes of that row when the editor's account is deleted. Asserted from inside the route test, a schema rule reads as though the route were responsible for it, and nobody can tell afterwards which assertions would survive the route being deleted. `src/test/fixtures.ts` seeds the rows both kinds of file need — the colleagues, (since #189) the customer and the ticket they opened, and (since #172) the assistant's account, which is a `user` row like the others and is what the two `rejectAssistant` refusals are read against. **Rows only**: the header constants stay beside the per-file `../middleware/auth` stub that reads them, for the registry reason below. Since #173 each colleague also carries a **pinned `createdAt`**, and the order of them is load-bearing: `now()` is transaction time, so `createMany` used to stamp every row with the same instant, and both `GET /api/users`'s "oldest first" and `automation.ts`'s longest-serving-admin fallback were reading a five-way tie.
    - **A route test does not stand up its own server** (#189). `serveRouter(mount, router)` from `src/test/route-app.ts` registers the `beforeAll`/`afterAll` and returns a `url(path)` builder — `const url = serveRouter("/api/tickets", ticketsRouter)`, then `fetch(url("/unread"))`. It replaced ten byte-identical copies of the same app-and-`listen(0)` block, and takes the `node:net` / `node:http` / `express` imports with it. What it deliberately does **not** cover is the `Sent<T>` type and the `get`/`post`/`patch` helpers beside it: those close over each file's own default headers and verbs, and one helper for all of them would be a lowest common denominator every caller worked around.
    - **`resetDb` deletes with `session_replication_role = 'replica'`**, and that is load-bearing rather than tidy. The delete list is built from `pg_tables`, which is in no useful order, and one relation in this schema is `onDelete: Restrict` — `KnowledgeArticleRevision.article`, which is what makes an article undeletable through the ORM (ADR-0006). Before the flag, the _first_ test to leave a revision behind broke `resetDb` for every file that ran after it, and the failures appeared everywhere except the file that caused them (found writing `jobs/sweeps.test.ts`, #158: 15 red tests in `routes/tickets.test.ts`). Restored to `origin` immediately, so nothing a test does is exempt from a constraint.
    - **A stub for a module two test files both need lives in `src/test/`, not copied into each of them.** `enqueueEmail` inserts the outbox row _into the caller's transaction_ and then hands pg-boss a job, so its stub keeps the insert (through the `Prisma.TransactionClient` it is given) and drops the nudge — and both `outbound.test.ts` and `routes/users.test.ts` need exactly that, so `src/test/send-email.ts` is where it is and `stubSendEmail()` is how it is registered — and **every file that installs it resets its switch in the same `beforeEach` that calls `resetDb()`**, not only the file that flips it, or the second file is relying on the first happening to reset first. Two copies would not do, and the reason is sharper than tidiness: unlike the four identical `../middleware/auth` stubs, this one holds **state** — the `failAfterWriting` switch a rollback test flips — and two copies are two boxes, of which the process-wide registry keeps one, leaving the other file's switch inert. Moving the seam one module down to `./jobs/boss` would run the real `enqueueEmail`, and is the thing not to do: `jobs/sweeps.test.ts` already registers a `./boss` factory, so that would put a second, differently-behaved factory on a specifier another file owns. What that seam buys is not optional, either — the real `enqueueEmail` wraps its insert in `prisma.$transaction` and then calls `getBoss()`, which throws with no queue started and **rolls the row back**, so an outbox row is unobservable without it.
    - **`auth.ts` is loadable by a unit test now, and `routes/users.test.ts` loads it for real** (#172). It used to be the one module a unit test could not reach — it opens a Better Auth instance over a Prisma adapter and reads two environment variables at import — and both halves of that are answered by ADR-0014: `mock.module("../db", …)` points the adapter at the in-process Postgres, and the variables are set in the test file above the `await import("../auth")`. The reason to bother is that the two claims that router exists to make are unreachable through a fake. **ADR-0011's claim is an absence** — `POST /api/users` creates an account with _no_ `credential` row, which is what stops anyone but the owner knowing the password and what `sendResetPassword` reads to tell an invitation from a reset; a fake `createUser` can only record that it was called. And **ADR-0009's outbox row is written two modules below the route**, by `sendResetPassword`, so asserting it against a stub would have been asserting a copy of `auth.ts` written in the test file. Two costs, both bounded and both worth naming: Better Auth's admin plugin answers `UNAUTHORIZED` to `createUser`/`adminUpdateUser` whenever headers are present with no session behind them, so the file mints a real one in `beforeAll` (one scrypt hash, one `signInEmail`, ~700ms) and **replays the session row** in `beforeEach` rather than signing in again — `resetDb()` truncates it, and the cookie is signed over the token, so the same token stays valid; and the route's own guard is still the shared `../middleware/auth` stub while Better Auth's permission check is not, so a request carries both the `x-test-*` headers and a genuine cookie, which must name the same admin.
    - **A feature's config guard is its own one-line export, and that is a testability rule rather than a style one** (#174). `ai/polish.ts` has `isPolishConfigured()` and `ai/summarize.ts` has `isSummarizeConfigured()`; both are one line over `isAiConfigured` in `ai/provider.ts`, because there is one key behind every AI feature and "can polish" and "can summarise" are the same question. A route that skips them and calls `isAiConfigured` directly — which the summary endpoint did until its tests were written — forces its test file to register `mock.module("../ai/provider", …)`, and `jobs/sweeps.test.ts` already owns that specifier with a **stateful** stub. Two stateful copies are the `../test/send-email` situation two bullets down: two boxes, of which the registry keeps one, leaving the other file's switch inert. The one-line guard gives each route's test a specifier nothing else touches, so neither file has to know the other exists. Same shape for any shared module a route consults through a narrow question. **The alternative was tried and lost** (`docs/adr/0016`, spike #209): passing the answer in as a value instead. It works at a route and it is worse everywhere else — `serveRouter` mounts one app per file, so the value cannot be a `boolean` captured at construction (measured: 34 pass / 0 fail becomes 32 pass / 2 fail) but a mutable object read per request, which is a worse production invariant bought for a test; and one of the three eval callers is `EVAL_NIGHTLY_SWEEP.run`, whose `SweepSpec` contract is `() => Promise<void>` and has nowhere to receive a value at all. The module is not the line, it is the place the two rules are written down, and converting the route had to move both rather than delete them. Read the ADR before re-suggesting it.
    - **"How many times did one request read that row" is `dbCalls` from `src/test/pg`.** Against a hand-written client the counts came free, because every method _was_ a `mock()`; #115's guard-shape rule (`rejectAssistant` takes the row its caller already read, not an id it fetches for itself) is invisible to every other kind of assertion, because a route that reads a row twice returns exactly the same response. The client is wrapped in a proxy that increments a counter and hands back the delegate's own return value **untouched** — not a client extension, which was tried and discarded: an extension replaces each operation's `PrismaPromise` with an ordinary one, and the _array_ form of `$transaction` needs the former to batch, so `prisma.$transaction([...])` then fails with a validation error naming a column from another model. It does not see operations issued on the `tx` handle inside an interactive `$transaction`. And it **throws on an operation name the client does not have**, because every assertion it backs is a `toBe(n)` and half of them are `toBe(0)`: a mistyped key would satisfy the assertion instead of failing it, and a test that has quietly stopped counting reads exactly like a route that has quietly stopped querying.
  - **No test file mocks the Prisma client any more** (#152 and its follow-ups), and the migration is done: everything in `apps/api` that reaches the database reaches the one shared client from `../test/pg`, and since #175 no file even names it. It went in batches. The four leaf route tests went in #169 (`routes/{changelog,dashboard-layout,new-features,tutorials}`), each one router over one or two tables of its own; the two knowledge-base readers went together in #170 (`routes/knowledge`, `ai/knowledge-base`) — batched because a converted file and an unconverted one reaching the same modules is the registry hazard below rather than half a migration; the two on the ticket write path went in #171 (`outbound`, `routes/activity`); `routes/users` went alone in #172; and `automation` went in #173, which **split the file in two** — `automation.test.ts` for the resolution rules and `routes/automation.test.ts` for the router — because the merge that put them together was a workaround for the registry hazard and the conversion is what removes it; `routes/ai` closed the conversions in #174; and #175 collected the payoff — the binding moved into the preload above and the CI job started caching the baked schema. #171 is what the migration was for twice over: `routes/activity.ts`'s five-way `UNION ALL` is now **executed** rather than string-matched, so a mistyped column alias, the `CASE` reading the wrong side, and `ts()`'s `::timestamptz AT TIME ZONE 'UTC'` landing a day out are all failures instead of assertions nobody could write; and `outbound.ts`'s two rows — the message and the outbox row beside it — are asserted to commit or roll back together, which is ADR-0009's whole claim. `routes/tickets.test.ts` and `routes/knowledge.test.ts` are the files to copy from: the two that exercise a transaction and a relation, and the second is the one that asserts a **rollback** — a `$transaction` that fails partway leaves nothing behind, which is the assertion a fake client cannot make and the reason ADR-0006's audit rule is testable at all. **#174 is the one worth reading for what the two seams can and cannot each see.** `routes/ai.test.ts`'s nested `messages` query had been asserted as the _arguments_ it was called with — `where: { direction: inbound }`, `take: 1`, `select: { textBody: true }` — and against a real database the first becomes a fact about which sentence reached the model (an outbound reply is not a candidate at all), alongside a `[createdAt desc, id desc]` tie-break that no argument assertion could reach at all. The other two do not survive, and **the honest move is to record that in the file rather than write a comment implying otherwise** — both measured by mutating the route and re-running. `take: 1` was never coverage: the handler reads `messages[0]`, so the file is green at `take: 5`. `select: { textBody: true }` is the sharper case, because it is a real loss: it is ADR-0008's "never render email HTML" rule reaching into a prompt, the handler only ever reads `textBody`, so `htmlBody: true` beside it is green too — the column never reaches the response and **no test at the database seam can observe it**. A hand-written client could watch a query the caller cannot otherwise inspect; a real database cannot. That is the one thing ADR-0014 costs, it is worth knowing before reaching for a fake to "get the assertion back", and the answer if such a select must be guarded is a check that reads the query, not a route test pretending to. The registry hazard below is what the whole migration was for, and it is now closed for `../db`: every file binds the same client, so no file can be handed a stranger's. It still applies in full to every other specifier a factory replaces, so keep reading it.
  - **A stub answers in the module's own type, never in a local copy of it** (#211, `docs/adr/0018`). `runner.test.ts` declared a structural twin of `AutoReplyResult` whose one difference was a widened `reason: string`, and no test in the file ever needed the widening. What it cost was exhaustiveness: `test.each(Object.values(AI_FAILURE))` is how you ask "and what about the other four", and against a `string` parameter it proves nothing because a typo compiles — so nobody wrote it, and the two reasons the file did cover happened to be two of the five on which the defect was invisible. A type a test re-declares is a type a test cannot be exhaustive over, and a widened field is a stub being allowed to answer things production cannot. Import the real type; if it genuinely will not accept what the test needs to say, that is a finding about the type.
  - **The registry is one process wide and nothing resets it between files.** Every test file's `mock.module` calls and every module they import share it, so two files that mock the same specifier and import the same module are not independent: the module binds to whichever fake was registered when it was first imported, and the other file's tests then run against a stranger's stub. Two consequences, both learned the hard way. A factory that does not spread the real module _is_ that module for every file loaded afterwards — `routes/ai.test.ts`, `routes/automation.test.ts`, `routes/knowledge.test.ts`, `routes/activity.test.ts`, `routes/tutorials.test.ts` and `routes/users.test.ts` therefore ship the **same** `../middleware/auth` stub, identical headers and defaults, and export `requireAuth` and `requireAdmin` whether or not the file under test uses both. And when two suites would need the same module bound to different fakes, the answer is a **narrower seam**, not one bigger file: give the thing each of them actually asks a one-line export of its own, the way `isPolishConfigured()` and `isSummarizeConfigured()` split `../ai/provider` above, so neither file has to know the other exists. Merging them into one file was the old answer — `automation.test.ts` carried `automation.ts` and `routes/automation.ts` together until #173 for that reason — and it is not one to reach for again; both halves are separate files now, each named after the module it covers. The failure mode to watch for is a file that passes alone and fails in the suite; run `bun test <a> <b>` in both orders before believing a new mock. **CI runs the whole suite a second time in reverse file order** (`.github/workflows/ci.yml`, ~30s), which is that check without the honour system — and it reaches the case the pair run cannot, where the file that poisons the specifier is a _third_ one that no pair ever loads into the same process. That is what #158 was, green three runs in a row on Windows and red on ubuntu-latest. It is a backstop, not a substitute: the pair run is still what you do before you believe a new mock, because a red reverse-order job tells you the suite is order-dependent and not which two files disagree. `../db` is out of this entirely since #175: the preload binds it once, before any test file loads, so there is no longer a _first_ file to bind it and nothing left for two files to disagree about. That is what ADR-0014 was for. **`../db` is the exception, not the rule**: `../middleware/auth`, `../ai/polish`, `./boss` and every other specifier a factory replaces are still one registry deep, so a new mock still gets `bun test <a> <b>` in both orders before it is believed.
