# Deployment standards

**Target is Railway, three services: `postgres`, `api`, `web`.** Full runbook in `DEPLOYMENT.md`; what follows is only what a change to this repo could break.

- Both images build from the **repository root** (`apps/api/Dockerfile`, `apps/web/Dockerfile`) because `packages/core` and `packages/shared` are workspace dependencies — a context scoped to one app cannot see them. So **Root Directory stays empty** on both services, and each Dockerfile copies every workspace's `package.json` before installing, the web app's included in the API image and vice versa: `bun install --frozen-lockfile` resolves the whole graph and fails on a missing manifest. Dockerfiles rather than Railway's own builder because **Railpack does not detect Bun projects**.
- Railway's config-as-code path is **absolute and does not follow Root Directory**, so a single root `railway.json` would apply to both services. Each carries its own (`apps/api/railway.json`, `apps/web/railway.json`) and each service is pointed at it in its settings. `watchPatterns` there is what stops a web-only change rebuilding the API.
- Migrations run as the API's **pre-deploy command** (`prisma migrate deploy`), so a failed migration aborts the release instead of half-applying it under live traffic. The generated Prisma client is built inside the image — `prisma generate` needs *a* `DATABASE_URL` to load `prisma.config.ts`, so the Dockerfile passes a placeholder that never opens a connection. pg-boss still provisions its own `pgboss` schema on boot and needs nothing from the deploy.
- **The browser talks to one origin, and that is a cookie decision.** `apps/web/Caddyfile` proxies `/api/*` to the API service over Railway's private network (`API_UPSTREAM`, a reference variable), so `VITE_API_URL` is **empty** in production and the session cookie is first-party. It was not always: the app called the API's own domain, and because `up.railway.app` is on the Public Suffix List those are two *sites*, so the cookie had to be `SameSite=None; Secure` — a **third-party** cookie, which Chrome incognito and Safari block by default. That presents as a `200` from sign-in and a user who is still signed out, with nothing in the API log, because server-side it worked. Measured, and the only per-user workaround was to allow third-party cookies for the site. Don't undo the proxy to "simplify" the topology.
- **`COOKIE_DOMAIN` picks between the remaining two arrangements and is validated at boot against `TRUSTED_ORIGINS`.** Empty is right behind the proxy — `sameOriginApi` in `auth.ts` sees `BETTER_AUTH_URL` inside `TRUSTED_ORIGINS` and keeps `SameSite=Lax`. `.example.com` is right once both services sit under a domain you own and the browser calls the API directly. Empty *and* direct cross-site calls is the third case, which falls back to `SameSite=None` — it still signs in, so a misconfiguration degrades rather than locks out, but it is the case to move off. `BETTER_AUTH_URL` is therefore the *web* origin on this deployment, not the API's own.
- `NODE_ENV=production` is set **in the API Dockerfile, not as a service variable**: it gates secure cookies, the rate limiter and the seed script's behaviour, none of which may depend on a dashboard field someone forgot. It is also what makes `prisma/seed.ts` skip the demo `agent@example.com` / `password123` account — sign-up is disabled, so seeding a deployed database is a normal thing to do and must not leave a published-password account behind.
- `VITE_API_URL` is **baked in at build time** and is both the axios baseURL and the CSP's `connect-src` entry, so changing it is a rebuild, not a redeploy. It must be declared as an `ARG` in `apps/web/Dockerfile` to be visible to the build at all. Empty — the production value now — means relative URLs and `connect-src 'self'`; setting it re-points the app at a separate API origin and brings the cross-site cookie problem above back with it.
