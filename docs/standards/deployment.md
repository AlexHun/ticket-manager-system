# Deployment standards

**Target is Railway, three services: `postgres`, `api`, `web`.** Full runbook in `DEPLOYMENT.md`; what follows is only what a change to this repo could break.

- Every image builds from the **repository root** (`apps/api/Dockerfile`, `apps/web/Dockerfile`, and `apps/web/Dockerfile.dev` on develop) because `packages/core` and `packages/shared` are workspace dependencies — a context scoped to one app cannot see them. So **Root Directory stays empty** on both services, and each Dockerfile copies every workspace's `package.json` before installing, the web app's included in the API image and vice versa, and the lint tooling's `tools/lint/package.json` and the repo scanner's `tools/repo-scan/package.json` in all three: `bun install --frozen-lockfile` resolves the whole graph and fails on a missing manifest. The two web images also copy `tools/repo-scan` itself (#565), because `vite.config.ts` loads the dev-tools plugin for a build as well as for `vite dev`, and the project map's scanner imports its comment stripper from there; the API image needs only the manifest, since nothing the server runs imports it. Dockerfiles rather than Railway's own builder because **Railpack does not detect Bun projects**.
- **The three images pin the Bun CI runs, `oven/bun:<BUN_VERSION>-slim`, and a Bun upgrade moves all four lines together.** A floating `oven/bun:1-slim` let production and CI run different releases, and #651 was a `node:http` bug in one of them: Bun 1.3.13 fired no `close` when a browser hung up on a route that had read its body, so polish and summarise never abandoned a model call. `routes/ai.test.ts`'s hang-up tests are what go red on a Bun that does that again, and `apps/api/src/standards-guard.test.ts` fails a `FROM oven/bun` line that names anything but `oven/bun:<BUN_VERSION>-slim`, since those tests only ever run on CI's Bun and cannot see an image drift from it.
- Railway's config-as-code path is **absolute and does not follow Root Directory**, so a single root `railway.json` would apply to both services. Each carries its own (`apps/api/railway.json`, `apps/web/railway.json`) and each service is pointed at it in its settings. `watchPatterns` there is what stops a web-only change rebuilding the API.
- Migrations run as the API's **pre-deploy command** (`prisma migrate deploy`), so a failed migration aborts the release instead of half-applying it under live traffic. The generated Prisma client is built inside the image — `prisma generate` needs _a_ `DATABASE_URL` to load `prisma.config.ts`, so the Dockerfile passes a placeholder that never opens a connection. pg-boss still provisions its own `pgboss` schema on boot and needs nothing from the deploy.
- **The browser talks to one origin, and that is a cookie decision.** `apps/web/Caddyfile` proxies `/api/*` to the API service over Railway's private network (`API_UPSTREAM`, a reference variable), so `VITE_API_URL` is **empty** in production and the session cookie is first-party. It was not always: the app called the API's own domain, and because `up.railway.app` is on the Public Suffix List those are two _sites_, so the cookie had to be `SameSite=None; Secure` — a **third-party** cookie, which Chrome incognito and Safari block by default. That presents as a `200` from sign-in and a user who is still signed out, with nothing in the API log, because server-side it worked. Measured, and the only per-user workaround was to allow third-party cookies for the site. Don't undo the proxy to "simplify" the topology.
- **`COOKIE_DOMAIN` picks between the remaining two arrangements and is validated at boot against `TRUSTED_ORIGINS`.** Empty is right behind the proxy — `sameOriginApi` in `auth.ts` sees `BETTER_AUTH_URL` inside `TRUSTED_ORIGINS` and keeps `SameSite=Lax`. `.example.com` is right once both services sit under a domain you own and the browser calls the API directly. Empty _and_ direct cross-site calls is the third case, which falls back to `SameSite=None` — it still signs in, so a misconfiguration degrades rather than locks out, but it is the case to move off. `BETTER_AUTH_URL` is therefore the _web_ origin on this deployment, not the API's own.
- `NODE_ENV=production` is set **in the API Dockerfile, not as a service variable**: it gates secure cookies, the rate limiter and the seed script's behaviour, none of which may depend on a dashboard field someone forgot. It is also what makes `prisma/seed.ts` skip the demo `agent@example.com` / `password123` account — sign-up is disabled, so seeding a deployed database is a normal thing to do and must not leave a published-password account behind.
- `VITE_API_URL` is **baked in at build time** and is both the axios baseURL and the CSP's `connect-src` entry, so changing it is a rebuild, not a redeploy. It must be declared as an `ARG` in `apps/web/Dockerfile` to be visible to the build at all. Empty — the production value now — means relative URLs and `connect-src 'self'`; setting it re-points the app at a separate API origin and brings the cross-site cookie problem above back with it.
- **A missing `/assets/*` file must 404, never fall back to `index.html`.** Every page in `App.tsx` is `lazy(() => import(...))`, so a stray dynamic `import()` for a route a visitor hasn't opened yet is a real, common request — not a hypothetical one. Vite content-hashes those filenames and each deploy replaces the container's filesystem outright, so a tab left open across a deploy (or a bookmark/cached HTML from before one) can ask for a chunk that's simply gone. The SPA-fallback `try_files {path} /index.html` in `apps/web/Caddyfile` exists for client-side _routes_, and without the nested `handle @assets { file_server }` in front of it, it also answers a missing asset with `index.html` — `200`, `Content-Type: text/html` — which is exactly the shape of `TypeError: 'text/html' is not a valid JavaScript MIME type`. Either way the stale tab is stuck until a hard reload fetches a fresh `index.html` naming the _current_ hashes; a retry asks for the same missing chunk. **Since #452 the app makes that reload itself.** `releasePlugin` (`apps/web/release.ts`) names the server's release at the web origin, `NewReleaseToast` offers a reload when it differs from the tab's, and a route error reaches `AppErrorBoundary` through the root route's `RethrowRouteError` — without it a data router renders its own error page and the boundary sees nothing — where the fallback reloads once per release on a mismatch and its "Try again" reloads for any route error.
- **The `develop` environment's `web` runs the Vite dev server, not the static build** (#314), so the `/__dev` tools exist there. `develop` is a second Railway environment deploying the git branch `develop`, with its own Postgres — seeded with the §5 commands of `DEPLOYMENT.md` plus `--environment develop`; §7 there is the runbook. Its `web` is the same service pointed at a different config — `/apps/web/railway.dev.json`, which builds `apps/web/Dockerfile.dev` — and production's `web` keeps `/apps/web/railway.json`, so **switch that path only once the branch it deploys carries the file**, or the next develop deploy fails. The dev image copies every app and package workspace, and `tools/repo-scan`, whose stripper the map and both guards import (the project map scans `apps/api` and the Prisma schema, and the typecheck and API-unit suites need the generated client) and must **not** set `NODE_ENV=production`. Without Caddy, four variables take over: `DEV_API_PROXY` replaces `API_UPSTREAM` (a full URL, scheme included), `__VITE_ADDITIONAL_SERVER_ALLOWED_HOSTS` must list the public domain **and `healthcheck.railway.app`**, and the two basic-auth credentials, without which the server refuses to start — the gate and why each of those holds is in [dev-tools.md](dev-tools.md). It copies only those workspaces and the root manifests, and the root `.dockerignore` applies to it too, so `.git`, `.claude/`, `.mcp.json`, `tests/`, `scripts/`, `*.md` and `playwright.config.ts` are absent there, and the image has no `git`. **So it sets `PARTIAL_CHECKOUT=1` and copies in a real Node** (#585), the two halves of what [dev-tools.md](dev-tools.md)'s test-runner section calls a run there: the unit tests that read those files skip under the marker, the E2E suite is shown as unavailable, and Vitest gets the Node its `#!/usr/bin/env node` asks for. Without that, the Bun image's own `node` is a link to `bun`, and 31 of 86 web test files failed to load. Its Usage history lives on a volume (`USAGE_HISTORY_FILE`, with `GH_ISSUES_FILE` beside it) and is fed by `bun run tokens --push`, which `.claude/hooks/push-usage.mjs` runs at the end of every Claude Code session on a machine holding the two credentials (#557), because the image has neither transcripts nor `gh` (#428, `DEPLOYMENT.md` §7); the image sets `USAGE_HISTORY_PUSHED=1` to say so, which a developer's machine must not.
