# Backend (`apps/api`)

- DB: Postgres (Neon/Supabase) via **Prisma 7** with the `@prisma/adapter-pg` driver adapter. Schema at `apps/api/prisma/schema.prisma`; CLI config at `apps/api/prisma.config.ts` (this is where `DATABASE_URL` is wired in — Prisma 7 no longer accepts `url` inside `datasource`). Generated client lives at `apps/api/src/generated/prisma` (gitignored, recreate with `bun run db:generate`). Import the singleton from `./db`, not the generated path directly.
- CORS: cross-origin in dev → API uses `cors` middleware in `apps/api/src/index.ts` with `origin: trustedOrigins` (exported from `auth.ts`) and `credentials: true`. Mounted before the Better Auth handler. Frontend uses `credentials: "include"`.
- Tests: **`bun test`** (`bun run --filter @ticket/api test`), files next to the source as `*.test.ts`. `mock.module(specifier, factory)` must be registered *before* the module under test is imported, so the module under test comes in through a dynamic `await import(...)` at the top of the file rather than a static import. Spread the real module into the factory (`{ ...actual, generateText }`) when only one export is being replaced — the constants and error classes the code branches on have to stay real or the test asserts against its own stub. `../db` and `../middleware/auth` are the two mocks almost every route test needs: the first opens a database connection at import, the second pulls in `../auth`, which throws without `BETTER_AUTH_SECRET`.
- Background jobs: **pg-boss**, in `src/jobs/`. `boss.ts` owns the lifecycle plus the generic `ensureQueue` helper and knows no queue by name; `index.ts` wires registrations (one line per consumer); one file per consumer beside them, with `ai-retry.ts` holding the one `Record<AiFailure, boolean>` they share. Started before `app.listen` and stopped in the SIGINT/SIGTERM handler *before* `prisma.$disconnect()` — a job finishing gracefully still needs the database. A failure to start takes the boot down on purpose: an API that is up but silently running no background work is the hardest kind of broken to notice. **To enqueue from inside a request, pass `fromPrisma(tx)`** so the job and the row it refers to commit together (see `routes/webhooks/inbound-email.ts`). Handlers must be idempotent — delivery is at-least-once — and must throw only for failures worth retrying; returning normally means "done, do not retry".
  - **`Processing` is a claim, not a phase.** `auto-reply-ticket.ts` takes a ticket by moving it `New → Processing` in a single conditional `updateMany`, and `GET /api/tickets` refuses to return that status — so for the seconds a worker holds a ticket, no agent can open it and write a second reply to the same customer. Every write after the claim is conditional on still holding it, so a duplicate delivery or a released ticket costs nothing. Release on **every** exit path: `New` when a retry is coming (so the retry has something to claim), `Open` when it is over. A claim that leaks is a ticket nobody can see.
  - That is also why `recoverStuck` exists. pg-boss re-offers an expired *job*, but the re-delivery cannot claim a ticket that is already `Processing`, so the two would wait for each other forever after a hard kill. The cron sweep reads staleness off `updatedAt` (the claim moves it) and puts the ticket back to `New`. Any future status-as-claim needs the same pairing — the claim and the thing that undoes it are one design, not two.
- Ingestion: **`src/ingest.ts` is the only path into the ticket table.** `ingestInboundEmail` is called by the Postmark webhook and by the `/pipeline` simulator, and each caller keeps only what is genuinely its own (the webhook: Basic Auth, a 45mb body limit, the Postmark adapter; the simulator: `requireAdmin`, a pinned sender domain, a rate cap). `findParentTicketId` is exported alongside it because the simulator has to ask the same threading question *before* ingesting, in order to refuse an `inReplyTo` that lands on a real customer's thread — asking twice is two indexed lookups and no duplicated rules.
- Express 5 auto-forwards rejected promises from `async` route handlers to the error pipeline — don't wrap `await` calls in `try/catch` just to translate the error into a response. Let it throw. Only catch when you actually need to branch on the error (e.g. map a specific error type to a custom response, or recover and continue) — never to re-throw or to manually call `next(err)`.
